# PRD 写作规范 v0.3 Candidate：让读者真正形成产品理解

## 1. 读者读完后应该能做什么

PRD 是否成功，首先看一位聪明但没有参加过前置讨论的产品经理读完后能做什么，而不是看作者是否填完模板或逐条提到写作规则。

读者应当能够：

- **看懂（`UNDERSTAND`）**：说清谁遇到什么问题，以及本 PRD 想改变什么结果。
- **看见（`SEE`）**：从实际呈现中看出主要关系、流程、分支、责任或取舍；确实不需要图时，也能说明为什么。
- **建模（`MODEL`）**：说出三到五个关键组成部分或阶段，以及每一部分的作用。
- **复述（`RETELL`）**：用自己的话解释主路径和重要的失败、恢复路径。
- **判断（`DECIDE`）**：找到当前选择、成立条件、后果、风险，以及什么信息会改变判断。
- **定位（`LOCATE`）**：不用重读全文，就能找到精确规则、验收、风险、未知和下一步的正式位置。

真实性边界横切以上六个结果：事实、产品判断、假设、未知和可变状态必须可以区分。读者复述得很流畅，却把 `NOT_RUN` 理解成“已经通过”，仍然是不合格。

**正例：** 读者能先说“高价值消息被低价值通知淹没”，再指出本期规则、失败恢复和验收分别在哪一节。

**反例：** 文档列齐字段、状态和接口，但读者无法说出用户问题、主流程或现在究竟决定了什么。

## 2. 先给读者一张地图

首屏应当独立回答六件事：谁遇到什么问题、希望改变什么结果、方案由哪三到五部分组成、主流程怎样走、本期明确不做什么、下一步由谁做什么。

先用一个具体事件让读者看见问题，再给当前结论。复杂 PRD 随后提供一张小型全景图或一条短流程，让读者先获得全局坐标，再进入模块、规则和异常分支。地图只负责建立方向，精确合同仍放在后文唯一的正式位置。

**正例：** 首屏用“用户不敢批量清理消息，因为担心漏掉风险提醒”开场，随后展示“识别 → 分级 → 处理 → 恢复”四个阶段，并说明本期不重做消息发送系统。

**反例：** 开头连续给出十几个 Schema、Machine Name 和内部模块，直到第五页才说明用户为什么需要这个产品。

## 3. 按理解顺序展开

从具体事件和用户结果开始，一次引入一个概念。读者建立整体模型后，再逐层展开产品规则、边界、例外和验收。摘要只引用精确合同，不在多个章节改写同一规则；一项精确规则只能有一个正式位置。

### 辅助写作规则

以下十三条规则继续帮助作者降低理解成本，但它们是实现读者结果的手段，不是文档成功的一级定义：

- 从具体事情开始，再命名抽象问题。
- 先给结论，再解释原因和成立条件。
- 先建立全局框架，再进入局部细节。
- 一个段落只讲一个重点。
- 一次只引入一个新概念。
- 术语第一次出现时先说人话，再保留精确机器名称。
- 普通叙述优先使用中文，正式字段、枚举和 Schema 保持精确。
- 用例子解释抽象规则，并说明例子与真实机制的对应关系。
- 非平凡关系使用真正有用的图，不画装饰图。
- 区分事实、判断、假设和未知。
- 简化表达时保留权限、状态、风险、恢复和验收边界。
- 正文省略真正不适用的内容，覆盖 Checklist 保留具体处置理由。
- PRD 定义产品要求，Engineering SPEC 决定不影响外部行为的内部实现。

渐进披露不是删除细节。首屏给地图，正文解释产品逻辑，精确字段和追溯信息放到读者能够定位的层级；任何会改变范围、风险、权限、决策或下一步的内容都不能隐藏。

**正例：** 正文先解释“系统必须允许用户撤销误操作”，再在规则区给唯一的恢复条件和验收 ID，首屏只链接该规则。

**反例：** 首屏、模块说明和验收区分别写出略有不同的恢复时限，读者无法判断哪一处才是正式要求。

## 4. 什么时候用图

只有关系本身会增加理解负担时才用图。默认触发场景包括：

- 非平凡的顺序或转化；
- 分支、失败和恢复；
- 三个以上相互作用的模块或参与者；
- 责任归属或包含关系；
- 状态迁移；
- 方案比较或取舍；
- 一个原因影响多个下游结果。

选择能回答当前问题的最小形式：顺序用流程图，变化用前后对比，方案用比较图，归属用层级图，影响扩散用因果链，模块连接用带标签的系统图。优先显示三到五个关键阶段。

图中的每个框、箭头、颜色和空间分组都必须承担语义职责。图旁边要写清它回答什么、覆盖和不覆盖什么，并提供不看图也能理解的文字替代。颜色不能是区分含义的唯一方式。

**正例：** 四阶段流程图用带文字的箭头标明正常流与失败回退，并在图下说明“不覆盖研发内部重试算法”。

**反例：** 把正文每个标题复制成一排彩色方框，既没有关系含义，也没有降低读者的记忆负担。

## 5. 图怎样交付

Markdown PRD 的解释型图默认交付确定性静态 SVG，并提供同名 `@2x.png` 兼容回退，例如 `review-flow.svg` 与 `review-flow@2x.png`。`@2x` 是命名和兼容交付约定；没有显式逻辑显示尺寸时，不能根据 SVG `viewBox` 数值宣称 PNG 真正达到两倍像素。

SVG 必须自包含、无脚本、无外部资源，有 `viewBox` 和可理解的文字标签。Mermaid 可以作为创作源，但不是默认最终读者资产。真实界面截图或照片使用 PNG/WebP。只有用户明确要求 HTML 解释器时，才交付自包含、响应式 HTML/CSS 与 inline SVG；HTML 截图不能取代 HTML 正文。

每张图都要有文字替代，并绑定 PRD 自包含目录中的精确归档资产。Reviewer 必须观察实际渲染结果后才能判断图是否有效；文件存在、源码可读或 hash 正确都不能代替视觉观察。

**正例：** PRD 引用自包含目录中的 `review-flow.svg`，提供 `review-flow@2x.png` 和等价文字摘要，Reviewer 在目标 Markdown 预览中实际查看后再给结论。

**反例：** 只提交 Mermaid 源码或一个外部图片链接，并因为文件通过 hash 校验就声称读者已经看懂。

## 6. 怎样保留精确性

好读不能改变事实。文档必须明确区分：

- **事实**：有来源、适用范围和时效边界的可核查信息。
- **产品判断**：由谁基于哪些依据作出的选择。
- **假设**：当前暂时采用、仍需验证的前提。
- **未知**：当前没有答案，并说明影响、Owner 或下一步。
- **可变状态**：例如 `REVIEW_PENDING`、`NOT_RUN`、已交付或已上线，必须与当前权威记录一致。

不同产物各自承担自己的精确内容：

- PRD 定义产品问题、用户结果、范围、产品规则、外部行为和可观察验收。
- Eval Pack 定义怎样验证这些可观察结果，不把 `NOT_RUN` 写成 PASS/FAIL。
- Controller companion 提供运行时权威状态，不让 PRD 正文成为第二条可变状态真源。
- Review Policy 定义审查和 Finding 处置，不让 Reviewer 获得产品批准权。
- Engineering SPEC 决定内部 Schema、存储、类和算法等不改变产品行为的实现选择。

**正例：** PRD 写“用户提交后必须看到成功或可恢复失败结果”，把数据库事务和锁策略留给 Engineering SPEC，并把测试状态明确写成 `NOT_RUN`。

**反例：** 为了显得完整，PRD 预选内部表结构，又把尚未执行的 Eval 写成“已验证通过”。

## 7. Reviewer 怎样判断

Writing Reviewer 必须独立于 PRD 作者，并针对同一个 exact Candidate 执行两遍阅读：

1. **读者遍：** 先只作为零背景读者阅读并写出自己的 readback，回答六个读者结果；不能先照着诊断清单拼答案。
2. **诊断遍：** 对失败结果指出精确理解断点，再选择一个主要修订手段：重排、解释、举例、可视化、分层、合并、移动、删减或补边界。

断点使用固定诊断类别并链接正常 Writing Finding，Finding 包含 exact basis、影响、严重级别和最小有效修改。Reviewer 保持 `ADVISORY_ONLY`：它提出可审计建议，但不能批准、阻塞、Release 或标记 Ready。

Candidate 实质变化后，旧 Review 对新 hash 失效，必须重新执行两遍阅读。确定性 Validator 只检查身份、引用、结构、资产安全和 Finding 关联；它不能冒充人去判断文字或图是否真正清楚。

**正例：** Reviewer 先独立复述后发现无法解释失败恢复，引用确切段落创建 `FLOW` Finding，并建议补一条最小回退路径。

**反例：** Reviewer 返回一张“十三条规则全部 PASS”的矩阵，却没有独立复述，也没有说明读者实际在哪里失去理解。

本 Candidate 的 Agent Product Eval 与观察式真人阅读验证当前都为 `NOT_RUN`。合同完整不等于实际效果已通过；只有后续独立评测达到预先定义的晋级阈值，v0.3 才能成为默认 Profile。
