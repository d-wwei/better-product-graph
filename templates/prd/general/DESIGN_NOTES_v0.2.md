# 通用 PRD 模板 v0.2：Review 工作记录

## 1. 当前结论

`PRD_TEMPLATE_v0.2.md` 是通用模板的唯一人类编辑源。它从冻结的 v0.1 创建，现已作为 `general@0.2.0 / RELEASED_DEFAULT` 进入运行时；项目模板仍可覆盖，旧模板仍可显式选择与回滚。

当前已开始逐项语义修订。后续每项结构或内容变更都应先在本文件记录理由，再修改 v0.2；不得回写 v0.1。

## 2. 已确认方向

1. Better Product Graph 应提供一份领域无关的通用 PRD 模板。
2. 项目可以显式配置自己的专属模板。
3. 模板选择的产品语义是“项目指定模板优先，允许回退时回到 BPG 通用模板”。项目模板缺失 / 暂不可用或显式不适用，只有配置 `GENERAL_ON_UNAVAILABLE` 时才回退并写 exact fallback lock；路径逃逸、symlink、hash / schema 异常、配置冲突和通用模板异常一律 fail closed。
4. 冻结的 Better-Product-Plan 模板保留为 legacy compatibility profile，不再作为默认模板。既有 Run 和显式 pin 继续保持原 exact identity，不随默认切换静默迁移。
5. 顶层 `templates/prd/general/` 是人类维护的唯一模板源；`scripts/promote_prd_template.py` 负责 exact-byte 同步到 `src/core/templates/`，构建除 parity / hash 外还实际执行 Template Registry、output-contract schema 与 released-default governance 校验，不在打包时修改 source。
6. v0.2 已注册为 `general@0.2.0 / RELEASED_DEFAULT`。项目可显式 pin 专属模板或 legacy profile，并按 exact hash 回滚。
7. 正式 PRD 的 Markdown 文件名仅去除最后一个 `.md` 扩展名后得到的文件名主体，必须与文档唯一 H1 标题逐字符完全一致；文件名主体沿用 `<PRD-ID>_<short-title>_v<version>_<YYYY-MM-DD>` 合同。Validator 已在 assemble 与 archive 两层强制校验，并同时拒绝残留占位、裸 `TBD` 与可靠可判定的空 Markdown 表。
8. 正文不设置独立的“文档信息与来源”metadata 区。PRD ID、版本、状态、机器维护的 Owner、模板身份、上游 Exact refs 与 Review / Ready / Release 生命周期 refs 属于系统 frontmatter、sidecar 或 manifest；适用端和范围、发布目标、当前状态、当前版本变化与下一动作分别只在其自然正文位置表达。
9. `阅读摘要` 的“当前状态”“当前版本主要变化”“下一步”分别优先从系统 metadata、附录 C 当前版本记录和当前 Run 派生；当前只定义语义，暂不实现 renderer。版本变化只提供当前 delta 的一屏视图，完整历史以 `附录 C：文档变更日志` 为唯一正文来源并保持 append-only，两处不得复制完整历史。
10. 第 1 节按“问题 → 目标 → 价值与时机 → 证据边界”组织。问题定义必须兼容用户 / 客户、商业、内部运营 / 团队效率、风险 / 合规、平台 / 技术演进等驱动，不默认所有 PRD 都是终端用户需求，也不得把实现方案写成问题。
11. 目标分为必填的定性目标和条件式定量目标。定性目标描述结果、对上层 / 阶段目标的贡献、可观察成功状态与不可牺牲的护栏；定量目标允许使用已确认的可靠目标，或有明确依据和验证窗口的假设目标，后者必须标记为“假设待验证”。缺少有权事实时标记“待确认”，不得把它伪装成已承诺数字。暂不量化时必须记录原因、替代观察证据和重新评估量化的触发条件 / 时点。
12. 用户价值、商业价值、团队 / 内部组织价值是三项必查视角，不是三项必须虚构的收益；任一层不适用时需给出具体理由，并标明证据或假设状态。“值得做”的价值判断与“现在做”的时机判断分开表达。
13. 第 1.2.2 节是定量目标的唯一正文来源，以 METRIC-ID 统一维护指标、基线、目标、观察窗口、数据来源和状态。第 8 节仅定义数据如何上报、校验、分析和消费，并引用 METRIC-ID；不得重新定义目标值。若测量设计发现目标有误，必须返回第 1.2.2 节修订唯一来源，而非在第 8 节静默分叉。
14. 第 2.5 节以条件式摘要向研发提供与当前切片直接相关的演进脉络，并区分“已确认下一阶段”“条件触发”“候选，尚未承诺”。它不复制 Product Plan / Roadmap，不将候选方向变成本期承诺；没有已确认后续时明确写“暂无已确认的后续规划”。当前实现只能为已确认的兼容 / 演进边界做必要预留，不能用未来可能性合理化推测性过度设计。
15. 第 3 节采用“模块结构 + 按问题选择行为视图”的可视化规则。第 3.2 节在多模块，或职责、所有权、边界、关系、依赖不直观时建议提供模块结构图；单一简单模块或关系显然的独立模块可省略，模块表仍作为可检索、可 diff 的文字补充。第 3.3 节不把流程图误作唯一表达：步骤 / 判断 / 分支使用流程图，交互顺序与时序使用时序图，数据来源 / 处理 / 存储 / 去向使用数据流图，参与者 / 能力 / 范围边界使用用例图，生命周期与状态转换使用状态图，也可选择项目支持且更合适的其他图型；流程图和数据流图不被统称为 UML。非平凡行为至少提供一张合适的可视化图，多图只用于回答不同问题，不得重复同一信息。每张图须明确标题、目的和范围，并保留项目支持的可编辑源；图片需有图注 / 替代说明及可复现引用，另配简短文字摘要支持检索、diff 和无障碍阅读。只有步骤少、单一主要参与者、严格串行且不存在决策分支、并行 / 异步、状态转换、跨系统交接、循环、重试、失败、退出、回滚或恢复路径时，才允许仅用编号文字。所有图必须与其对应的详细规则一致，发现不一致时必须显式修正，不能静默择一。
16. 第 2.4 节与模块级依赖采用“全局总览 + 局部交付细节”的分层：第 2.4 节继续记录跨 PRD、跨模块或共享合同级依赖；每个模块可按需增加 `4.x.5 依赖关系（条件式）`，记录该模块对其他模块、业务、系统、数据、接口、团队或外部能力的依赖，也记录其他模块或消费者对本模块的反向依赖。模块表明确关系方向、所需能力 / 条件、状态及未满足时的影响与处理；已有全局条目只引用 DEP-ID，不复制全文。没有模块专属依赖时删除整个小节和空表，避免无意义骨架增加阅读负担。
17. 附录 D 改为“交付检查与覆盖索引”，按“通用交付 Check / 项目专属 Check / 法律、合规与权利 Check”分类。它只证明 review 视角已覆盖并指向自然正文或证据，不复制需求、约束或完整分析；第 5、7、8、9、10、11 节仍是相应实质内容的正文来源。`待确认` 必须带有效 Owner / 来源、未完成影响和动作，`已考虑` 不构成完成、批准或授权。
18. 项目专属 Check 只能由已配置的项目 Profile / Knowledge 与已确认事实生成，允许引用产品类型、市场 / 终端、领域风险、历史问题、依赖或灰度约束，但不得由 Agent 猜测；没有适用项时明确写明理由和依据，不保留空占位。公司、券商、金融或教育等上游模板专属项不得进入通用固定清单。
19. 法律、合规与权利 Check 只允许使用“不涉及 / 可能涉及 / 待专业确认 / 已取得专业结论（附 ref）”结论，并要求有权限的专业 Owner / 有效来源。本模板、Agent 和产品 Owner 均不能代替法务、隐私、合规、安全、版权等专业判断；索引记录不等于法律批准、业务授权或专业意见。
20. 第 3、4 节支持两种等价的输出结构。多个有意义模块、跨模块关系 / 共享规则、多个不同流程，或全局视角与施工细节回答不同问题时，使用“第 3 节全局概览 + 第 4 节模块详述”的标准拆分模式；仅当 PRD 是一个可独立交付、高内聚模块 / 切片，只有一个主导场景 / 流程，且拆分主要造成重复时，才可使用 `3. 方案与功能规则` 的紧凑合并模式并删除独立第 4 节。字数短不是合并依据；存在有意义模块边界、共享合同、跨模块规则或多视图全局关系时仍须拆分。合并只能去掉重复表达，必须保留两节全部适用语义，包括方案说明、按问题选择的全局与模块级可视化、模块职责 / 目标 / 参与者场景、触发和前置条件、业务规则、交互 / 状态 / 权限、模块依赖、分支 / 异常 / 恢复及可观察验收标准；既有可视化与模块依赖规则在两种模式中同样生效。紧凑模式可在同一视图小节中呈现端到端行为与模块内部机制，但各图必须回答不同问题。独立、hash-pinned 的 `OUTPUT_CONTRACT_v0.2.json` 已接受 `split | compact`，禁止混用两组 H2，并要求两种结构映射相同核心产品语义；紧凑模式允许总览与模块详情同时映射合并后的第 3 节。
21. 每个模块可条件式提供模块级可视化。当模块内存在多个子组件、复杂状态转换、交互时序、数据流、关键分支 / 决策或跨边界交接时，选择模块结构 / 组件关系、局部流程、时序、数据流、状态、用例或其他项目支持的图型；单一简单模块已能由文字和规则表清楚表达时删除整节，不留空占位。第 3 节图回答全局结构与端到端行为，模块图只回答内部机制 / 边界；全局图已完整覆盖时引用图标题 / Exact ref 并补充局部差异，不重复绘制。每张模块图需说明标题、目的、范围，保留可编辑 / 可复现来源与必要文字摘要 / 替代说明，并与该模块规则、状态权限、依赖、异常恢复和 AC 一致。未来 Validator 应检查图的适用性说明、与规则的一致性及引用完整性，而不能机械要求每个模块都有图。
22. 第 1.1 节新增“目标对象规模与单位价值分析”，且不假设对象必须是终端用户。对象可按问题选择用户、客户、商户、员工、团队、业务实体、系统、设备、交易或其他可计量对象 / 风险暴露单位；规模需明确对象 / 细分、当前受影响规模、本期预计覆盖规模、单位与时间 / 地域 / 渠道口径、证据来源和结论状态。单位价值分别记录“单个对象自身获得的价值”和“单个对象对业务 / 组织的价值（适用时）”，避免把对象结果改善与收入、成本、风险或战略价值混为一项。未知规模、TAM、覆盖率和单位价值不得编造；内部、平台、风险 / 合规 PRD 使用合适的对象或风险暴露单位，确实不适用时说明具体理由。规模与单位价值只是优先级、第 1.2 节目标和第 1.3 节三层价值的分析输入，口径不一致或证据不足时不得机械相乘，也不得复制目标或价值结论。阅读摘要只保留“主要对象、规模与场景”的一句话结论。未来 Validator 仅在该分析适用时检查字段完整性、口径、来源和状态，不能强制所有 PRD 伪造定量值。
23. 保留模板中“用户结果”“用户如何”“用户故事”“用户操作”“老用户”等自然、面向人类的表达，不做机械的全局泛化。只有原模板已经明确允许非用户场景的字段，才按具体上下文替换对象，不强制把全文改写为“目标对象 / 参与者 / 调用方”。
24. 第 2.1 节只允许本 PRD 已确定交付的 SCOPE 项，取消“可后置”状态；不交付内容进入第 2.2 节，与当前切片有关的未来方向进入第 2.5 节或上游 Roadmap。第 3.2 节的模块角色限定为“本期交付 / 复用既有 / 外部依赖”，不得把未来模块包装成本期模块。
25. 正文采用最小跨章节追溯，不给所有句子编号。稳定 ID 至少覆盖 GOAL、SCOPE、MOD、DEP、METRIC、RULE、AC、RISK、ASM、UNK、OPEN 和 LEGAL；第 5.1 节只用一张最小表连接“目标 / 范围 → 模块 / 规则 → AC → Eval / Test ref”，不复制需求。第 8 节通过 METRIC-ID 连接数据事件与分析，模块依赖通过 DEP-ID 连接全局依赖。附录 D 只引用正文 ID / ref。
26. 第 1.4 节只表达支撑问题、目标、价值判断的证据边界；第 11.2 节只记录仍影响本期交付的 ASM / UNK；第 11.3 节只记录必须由 Owner / 有效来源在时点前行动的 OPEN，并引用其来源 ID。三处共用稳定 ID，不复制同一结论全文。
27. 第 10.1 节是法律、合规、权利与内容安全实质要求的正文承载面，以 LEGAL-ID 记录司法辖区 / 对象、严格状态、实质约束、专业 Owner / 有效 ref 与交付动作。法律状态仍只允许“不涉及 / 可能涉及 / 待专业确认 / 已取得专业结论（附 ref）”，Agent 与产品 Owner 无权自批。附录 D.3 保留分类检查，但主要引用 LEGAL-ID / 外部专业 ref。
28. 每份 PRD 必须判断 Product Evals 适用性并说明理由，只有需要 Evals 时才要求准备状态与 Eval Pack；普通 AC 足够时统一记录不适用理由，且不声称测试已经执行或通过。第 5.3 节新增仅 `delivery intent = EXPERIMENT` 适用的实验交付合同，通过 ASM / UNK、SCOPE、METRIC、护栏 / 回滚与 Decision ref 买信息并返回产品决策，不复制其他章节。Product Evals 与产品实验目的不同，可同时适用。
29. 正文不再使用英文不适用缩写，统一写为 `不适用｜理由：...`；未决格式统一为 `待确认｜Owner / 有效来源：...｜影响：...`，并区分缺少有权事实 / 决定的“待确认”和已有假设待证据检验的“待验证”。条件式内容默认删除空表后保留不适用理由；局部明确要求删除整个小节时局部规则优先。
30. Candidate 阶段已落地 output contract、项目模板 / fallback、默认 exact pin、Validator、Ready / receipt 绑定与本地 Golden fixture。2026-08-21 的收敛版本在保留这些安全边界的前提下，将 v0.2 切换为 released default；Profile status 只是治理标签，真正的迁移身份仍由路径、版本与 hash 共同决定。Renderer 仍未实现，不属于模板默认切换的前置条件。

## 3. 本轮 Review 顺序

1. 定义所有 PRD 都必须具备的最小核心正文。
2. 将数据、多语言、无障碍、合规、Evals 等改为真正的条件式内容。
3. 合并重复信息，明确每类信息的唯一正文位置与派生摘要。
4. 检查小型、前端、后端服务、AI/内容处理和实验型 PRD 是否都能表达。
5. 再定义 Template Profile 的必需字段、条件字段、fallback 和兼容校验。
6. 用真实 PRD 样本验证可读性、完整性和研发可交付性。

## 4. 当前主要问题

- v0.1 的必需标题过多，条件章节仍会强迫轻量 PRD 保留完整骨架。
- 阅读摘要、证据 / 假设 / 未决、依赖和验收已通过“正文唯一来源 + 稳定 ID + 附录覆盖索引”建立边界，但仍需用真实 PRD 试跑验证是否足够轻量、可读。
- Evals、Test Design Contract、Exact ref 等系统术语对普通读者可能偏重。
- AI/内容处理需求的来源范围、处理要求、输出合同和评测边界需要确认是否以条件式 Profile 补充。
- 人类源到运行时副本已形成 exact-byte sync + build check 链路；真实 Host 试跑属于整包发行验收，不由模板同步脚本自报。

## 5. Release 与兼容边界

`general@0.2.0` 是新 Run 的通用默认模板；项目专属模板、显式 legacy pin 和 rollback 继续保留。Output Contract 的 `legacy` 模式只用于让旧 Host 结果和旧 Run 可继续验证，新生成内容应使用 `split` 或 `compact`。模板同步命令只证明源码、运行时副本与治理指针一致，不替代真实 Host 质量验收，也不能据此声称某次 PRD 已经 Ready 或 Released。
