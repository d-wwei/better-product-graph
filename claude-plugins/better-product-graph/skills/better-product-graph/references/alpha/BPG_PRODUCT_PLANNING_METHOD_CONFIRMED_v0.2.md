## 0. 本文档如何使用

本文档只做一件事：保存当前已经讨论并确认的结论，作为后续逐阶段设计的共同基线，避免结论在继续讨论中丢失或发生含义漂移。

本文档遵循三条规则：

1. 已确认的原则、边界和结构，写入正文。
2. 五个阶段已经逐阶段确认；后续修改必须原位更新对应阶段的内部动作、工作产物、退出标准和角色边界，不能只修改总览而造成合同漂移。
3. 本决策记录采用持续更新方式。普通结论直接原位追加或修订；只有重大阶段正式冻结、确实需要保留不可变基线，或产品责任人明确要求时，才新建版本文件。

这条维护规则只适用于本决策记录。进入正式审查的候选版本仍然保持不可变，认知发生实质变化时仍需生成新的候选版本，以保证审查对象没有被静默替换。

五个阶段均已经按以下结构完成当前基线冻结：

- 必须执行的内部动作。
- 必须产出的工作产物（Artifact）。
- 条件式工作产物及其触发条件。
- 退出标准。
- 退回与重做条件。
- 执行者、独立审查 Agent（Reviewer）和决策者。

### 0.1 中文优先表达要求

BPG 的用户可见内容、正式文档、图表、状态说明和交接材料以中文为主要表达语言，但不机械翻译已经约定俗成或项目内高频使用的英文术语和缩写。

具体规则：

- BPG、PRD、Agent、Reviewer、Owner、Candidate、Review、Artifact、Ready、Handoff 等常用术语可以直接使用，不要求每次附加中文翻译。
- 项目内已经明确含义、不会造成理解障碍的英文缩写和机器枚举可以直接使用。
- 生僻、专业度较高、跨领域含义不一致，或可能产生歧义的英文表达，第一次出现时采用“中文含义（英文术语）”。
- 标题、结论和主要解释仍然以自然、清晰的中文为主，避免出现只有英文术语、没有实际解释的内容。
- 如果某个英文词没有稳定译法，需要明确本方法采用的中文含义。
- 面向用户展示不常见的机器状态值时，需要同时解释其中文含义；内部已经熟悉的状态值不必重复翻译。

### 0.2 Agent 优先执行要求

BPG 默认让 Agent 完成尽可能多的工作。只要 Agent 能够在可接受的可靠性、成本和时间范围内完成，就不应为了形式上的“确定性”增加程序化脚手架。

动作分配的默认顺序是：

1. 主 Agent 直接完成。
2. 主 Agent 调用专业子 Agent 完成有边界的工作。
3. 使用现有通用工具辅助 Agent。
4. 只有前三种方式不能可靠解决，而且程序具有不可替代优势时，才增加最小程序化脚手架。

以下工作原则上由 Agent 完成：

- 理解语义、补充背景和识别未知。
- 调研、分析、推理、比较和综合判断。
- 选择和调用产品分析方法。
- 形成建议、工作产物和候选版本。
- 独立审查、归纳问题和定向修订。
- 根据新证据和人类输入动态调整工作路径。
- 判断某项分析或工作产物是否适用。

程序化脚手架只有在具有 Agent 难以替代的独特优势时才允许引入。当前认可的优势类型包括：

- 精确对象、身份、版本和引用绑定。
- 权限、授权和责任边界校验。
- 当前状态、合法状态迁移和正式状态提交。
- 幂等性、重复副作用和不可逆操作防护。
- 哈希、格式、结构和确定性机械校验。
- 运行恢复所必需的最小持久化。
- 大规模、重复、规则明确的机械处理，并且程序能显著降低错误或成本。

每次准备增加程序化脚手架时，必须先说明：

1. 它具体防止什么失败。
2. 为什么 Agent 或现有工具不能以合理可靠性完成。
3. 它的最小实现是什么。
4. 它会增加什么复杂度、维护成本和运行负担。
5. 什么条件下可以删除或不启用它。

如果不能证明独特且不可替代的优势，默认不增加脚本、结构模式（Schema）、关口（Gate）、状态控制器（Controller）或新的运行层。

程序化脚手架不得：

- 替代 Agent 对问题、价值、方案和文档质量的语义判断。
- 与 Agent 重复完成同一份认知工作。
- 把内部实现字段的完整度伪装成产品质量。
- 因为自身能力不足而把本可由 Agent 完成的工作转嫁给人类 PM。

这条原则不是“不要程序”，而是“Agent 负责认知和语义工作；程序只负责它确实更可靠、且不可替代的确定性工作”。

## 1. 方法目标与责任边界

### 1.1 最终目标

BPG 产品规划方法的目标，是把一个 Signal 经过充分的产品认知、问题判断、方案选择和产品系统规划，形成高质量、可理解、可执行、可验证，并可以本地交接的 PRD 或 PRD 组合。

这套方法不是为了最快写出一份文档，而是为了提高以下结果的质量：

- 问题是否定义正确。
- 目标用户和真实需求是否理解正确。
- 当前选择是否是现有条件下最好的方案。
- 产品体验和产品系统能否完整运转。
- 需求是否清晰、完整、可验证、可交接。

### 1.2 当前产出边界

BPG 当前负责：

- 产品背景、目标、用户、需求、问题和价值分析。
- 方案探索、比较、决策与不确定性处理。
- 目标用户体验、产品范围、逻辑产品系统和功能需求规划。
- 产品需求文档生成、独立审查、可交接就绪与本地交接。

BPG 当前不负责：

- 工程规格说明（Engineering SPEC）、代码设计、部署方案和技术实现细节。
- 研发、测试和发布执行。
- 完整商业化方案、市场推广方案或 GTM 执行方案。
- 通用项目管理、组织管理和产品经理领导力体系。
- 独立知识库的设计、存储、生命周期和跨项目同步。

产品需求文档（PRD）可以定义用户可观察的产品行为、业务规则、逻辑对象、状态、前后台责任和验收结果；具体技术栈、内部代码结构、存储实现、算法、并发和原子性机制属于工程规格说明（Engineering SPEC）。

当前 BPG 2.0 的正式终点是：

```text
PRD 候选版本（PRD Candidate）
→ 独立审查（Review）
→ 可交接就绪（Ready）
→ 本地交接（Local Handoff）
```

不在当前流程中虚构 Release、外部发送、SENT 或 RECEIVED 状态。

### 1.3 产品规划（Product Planning）的位置

产品规划（Product Planning）是 BPG 内部使用的一套规划方法，不是一个独立的正式文档产物。

正式交付物是：

- 未拆分时：一份完整 PRD。
- 拆分时：一份总 PRD，加一组存在明确关系的子 PRD。
- 实验路径：一份实验型 PRD。

## 2. 总体运行结构

### 2.0 需求信号与路由（Signal & Route）

所有产品规划从“需求信号与路由（Signal & Route）”进入。路由负责识别产品规划信号，并紧凑保留“收件箱（Inbox）/ 事故（Incident）/ 缺陷（Bug）”三类旁路；当前主框架不展开这些旁路的内部过程，也不让它们干扰产品认知与决策主循环。

### 2.1 一个宏观认知与决策循环

问题发现、问题审查、决策候选版本（Decision Candidate）、决策审查和正式路线提交，不是一条只能向前的流水线，而属于同一个“产品认知与决策循环（Product Cognition & Decision Loop）”。

```text
需求信号与路由（Signal & Route）
      ↓
产品认知与决策循环（Product Cognition & Decision Loop）
  主 Agent 调研、分析
      ↕
  人类 PM 补充认知，并接受主 Agent 的深度质询（PM Grilling）
      ↓
  主 Agent 形成候选版本（Candidate）
      ↓
  独立审查 Agent（Reviewer）挑战候选版本
      ↓
  Agent 在预授权范围内自动决定，或条件式升级给 Owner
      ↓
  主 Agent 重新整合认知
      └───────────────↺
```

人类 PM 的补充与修正、Agent 在授权范围内的自动决策，以及产品责任人的正式选择，都可能改变目标、用户、问题定义、价值权重、方案判断和不确定性处置，因此它们都位于循环内部，而不是流程末尾只选择菜单。

这里拆分的是责任语义，不默认拆分成多个人：人类 PM 参与认知形成，Owner 拥有最终产品责任，Agent 可以在 Owner 或项目预先授权的低风险范围内自动提交继续规划的决定。默认由同一个人同时承担 PM 和 Owner；只有组织权限或责任归属确实不同时，才映射给不同的人。

《产品规划主记录》在分析和协作过程中保持可持续修改，不为每次编辑、补证据或内部推演创建不可变版本。只有准备进入 Problem Review、Decision Review 或 PRD Review 时，才冻结对应的正式 Candidate；Candidate 一旦进入审查便不可静默改写。Review 后发生实质性认知变化时，主 Agent 先更新主记录，再形成新的不可变 Candidate 进入下一轮审查。

### 2.2 六类产品决策结果

Product Decision 可以形成六类结果：

- 停止（`STOP`）：确认停止，不继续投入。
- 等待（`WAIT`）：当前不承诺，等待明确的重启条件。
- 继续研究（`RESEARCH`）：补充研究，继续留在认知循环。
- 开展实验（`EXPERIMENT`）：用实验型产品需求文档验证关键假设。
- 立即投入（`COMMIT NOW`）：进入完整产品规划和产品需求文档；这里只代表继续本地规划，不代表批准研发、预算投入、发布或外部副作用。
- 未来路线（`FUTURE ROADMAP`）：确认方向，但延迟到未来执行。

`RESEARCH` 不离开认知循环。只有问题与行动已经稳定并获得授权，才进入后续规划或形成明确的停止、等待、未来路线结论。

当前确认的自动决策只覆盖 `COMMIT NOW → 进入本地完整规划`：Decision Review 获得 PASS，且满足项目预授权、低风险、可逆、无重大未知、无 `NEEDS_OWNER`、不改变目标和价值权重、不形成真实资源或外部承诺等条件时，Agent 可以自动提交该路线。在未来另行确认前，`STOP / WAIT / RESEARCH / EXPERIMENT / FUTURE ROADMAP` 必须由 Owner 对当前 Decision Candidate 作出精确选择；不得因为 Agent 高置信度或路线看似低风险而自动扩张权限。

六类结果采用以下统一生命周期合同：

| 决策结果 | 当前 Run 的状态与最低记录 | 后续进入方式 |
|---|---|---|
| `STOP` | 当前 Run 终止；记录停止原因、关键证据、被否决的行动和改判条件 | 未来重新考虑时创建新 Signal 和新 Run，并引用本次决定 |
| `WAIT` | 当前 Run 进入等待；记录等待条件、允许触发的证据、检查时间、责任来源和恢复阶段 | 只有满足明确 Trigger 才恢复同一 Run；普通 `resume` 不能绕过等待条件 |
| `RESEARCH` | 当前 Run 保持活动；形成有界研究任务、停止条件、证据要求和返回阶段 | 研究完成后返回最早受影响的阶段一、二或三 |
| `FUTURE ROADMAP` | 当前 Run 以未来路线结论结束；记录方向、延后原因、前置条件和重启信号 | 未来启动时创建新 Signal 和新 Run，并引用本次路线；不得把陈旧结论直接当作当前授权 |
| `EXPERIMENT` | 形成实验型 PRD；完成 PRD Review、Ready 和 Local Handoff 后结束 | 实验执行及结果不属于本次 BPG Run；未来结果作为新 Signal 进入新的认知循环 |
| `COMMIT NOW` | 进入阶段四和阶段五；完成 PRD Review、Ready 和 Local Handoff 后结束 | 后续产品变化、研发反馈或新证据通过新 Signal 重新进入 BPG |

`WAIT` 与运行时暂停必须严格区分：`WAIT` 是产品决策结果，需要明确重启条件；`PAUSE / RESUME` 只是运行过程中的临时控制，在安全边界保存并恢复工作，不能改变 Product Decision，也不能把等待中的 Run 擅自恢复为活动状态。

### 2.3 一个通用候选版本审查（Candidate Review）机制，多次复用

整个 Graph 不是只有一次审查，也不是为每种文档分别设计一套审查系统。

同一个通用候选版本审查机制可以被多次调用，至少用于：

- 问题候选版本（Problem Candidate）。
- 决策候选版本（Decision Candidate）。
- 实验型产品需求文档的完整 PRD Release Set Candidate。
- 单份产品需求文档，或总产品需求文档与全部子产品需求文档组成的完整 PRD Release Set Candidate。

通用审查规则：

- 独立审查 Agent 只读取精确、冻结、不可变的候选版本。
- 独立审查 Agent 不替主 Agent 修改文档，也不写运行状态。
- 结果只有“通过（`PASS`）/ 修订（`REVISE`）/ 需要产品责任人处理（`NEEDS_OWNER`）”。
- 自动修订最多两轮。
- 每轮修订产生新的候选版本。
- 两轮后仍不能通过时停止自动修订；需要价值取舍、风险接受或授权时进入 `NEEDS_OWNER`，证据不足时进入 `RESEARCH` 或 `WAIT`，上游认知或规划错误时返回最早受影响阶段，只有非阻断改进项时才允许 `PASS`。
- Reviewer 和主 Agent 必须为非 `PASS` 结果给出返回目标（`return_target`）、返回原因（`return_reason`）和影响范围（`affected_scope`）。它们属于语义判断；Controller 只验证目标是当前 Graph 中允许的合法位置并绑定精确 Candidate，不推断问题归属。
- 完整 PRD Release Set 获得 `PASS` 后，只有满足第 11.6 节唯一 Ready 合同，才自动进入“可交接就绪（Ready）”，然后只做本地交接。

决策候选版本获得“通过（PASS）”，只证明建议已经通过当前审查，不替代产品责任人的产品决策权。

## 3. 角色与权限

### 3.1 主 Agent（Lead Agent）

主 Agent 贯穿整个产品规划运行（Product Run），是产品语义工作的唯一整合责任人。

主 Agent 负责：

- 主动检查项目材料、历史、数据和公开资料。
- 识别事实、推断、假设、冲突和未知。
- 使用认知内核和适用的产品分析方法。
- 形成完整判断、推荐方案和候选版本。
- 调用必要的专业 subagent，但不把整合责任外包。
- 根据审查和产品责任人输入重新整合全局认知。
- 保持从目标到验收标准的完整追溯关系。

### 3.2 专业子 Agent（subagent）

专业子 Agent 是主 Agent 按需调用的有限范围专家，可以覆盖用户、市场、竞品、用户体验（UX）、商业、数据、技术可行性、风险等视角。

它们只返回有边界的 Findings 或 Proposals：

- 不拥有完整产品结论。
- 不直接修改正式候选版本。
- 不直接写运行状态。
- 不替代主 Agent 的综合判断。

### 3.3 独立审查 Agent（Reviewer）

独立审查 Agent 是一个独立角色，运行时通常由独立的审查子 Agent 执行。

“独立审查 Agent 是角色”与“由子 Agent 执行审查”并不矛盾：前者定义权限与责任，后者定义执行方式。

独立审查 Agent 必须：

- 使用独立 Agent 实例或独立上下文。
- 只读精确候选版本和绑定的证据。
- 独立挑战作者的前提、证据、推理、遗漏和可执行性。
- 返回明确结论（Verdict）和发现（Findings）。
- 不替作者改稿，不替产品责任人决策，不提交状态。

### 3.4 人类产品经理（PM）与产品责任人（Owner）

BPG 区分人类 PM 与 Owner 的责任语义，但不默认要求由两个人执行。

默认角色映射为：

> **PM = Owner：一个人、一个身份、两种责任。**

人类 PM 负责参与认知形成：

- 补充私有、内部或尚未成文的背景。
- 提供目标、用户、团队分工、资源和时机等内部现实。
- 接受主 Agent 对背景、目标、用户、需求、问题、价值、方案、取舍与风险的持续追问。
- 纠正主 Agent 的认知，提出反例、异议和新的未知。
- 与主 Agent 共同进行 PM Grilling；这些讨论输入本身不自动构成正式决策。

Owner 负责承担正式产品责任：

- 明确改变目标或价值权重。
- 接受普通产品风险和关键不确定性。
- 否决、延后或授权产品行动。
- 在精确决策候选版本上作出正式的 Owner Choice，并决定六类结果之一。
- 为低风险、可逆、只继续本地规划的行动定义 Agent 自动决策范围，并保留收回、缩小或修改授权的权力。

当 PM 与 Owner 是同一个人时，不增加人员交接、第二次人工确认或额外审批。系统仍必须区分“正在参与讨论”和“已经明确作出决定”：PM Grilling 可以多轮发生；正式路线必须绑定当前 Decision Candidate，并明确记录决策来源是 Agent 在预授权范围内自动提交，还是人类 Owner Choice。

Agent 的高置信度本身不构成授权。只有 Decision Review 已经通过，且行动处于预授权范围、低风险、可逆、没有重大未知、不产生真实资源或外部承诺时，Agent 才能自动选择 `COMMIT NOW` 进入阶段四。任一条件不满足时，必须升级给人类 PM / Owner。

只有在组织中的产品经理没有最终方向、预算、风险或资源授权时，PM 与 Owner 才映射给不同的人。无论是否同一人，独立审查 Agent 仍必须与候选版本作者保持独立。

人类 PM / Owner 只处理 Agent 无法自行获得的信息，以及真正需要人类价值判断、风险承担或授权的事项；不承担 Agent 能自行完成的资料整理和公开调研。

### 3.5 状态控制器（Controller）/ 机器

状态控制器只负责确定性控制：

- 当前对象与精确版本。
- 合法状态迁移。
- 候选版本与审查的绑定。
- 幂等性和重复副作用防护。
- 正式状态提交。

状态控制器不做产品语义判断，不根据字段完整度冒充产品质量判断。

### 3.6 宿主适配器（Host Adapter）

宿主适配器只负责不同宿主（Host）的协议映射，不承载产品语义，不拥有状态与决策权。

## 4. 五个正式阶段

整体工作方法压缩为五个阶段：

1. `理解（UNDERSTAND）`：理解背景、目标、用户、需求、现状与差距。
2. `诊断与价值判断（DIAGNOSE & VALUE）`：诊断真正问题，建立因果和价值判断。
3. `探索解决方案与决策（DISCOVER SOLUTIONS & DECIDE）`：寻找最好方案，比较选择，形成决策。
4. `规划产品系统（PLAN THE PRODUCT SYSTEM）`：规划范围、目标体验、逻辑系统和功能模块。
5. `产品需求文档与交接（PRD & HANDOFF）`：形成产品需求文档，完成审查、可交接就绪、本地交接和规划复盘。

五阶段只是图式流程（Graph）的导航层和表达压缩，不代表减少认知工作。

必须坚持：

> 合并流程表达，不合并认知责任；减少重复写作，不减少证据、分析、图表和检查。

默认使用完整方法。只有主 Agent 能证明不会损失重要语义时，才可以压缩表达或合并工作产物，并且必须：

- 说明合并或省略了什么。
- 说明为什么不影响结论。
- 保留必要的证据与追溯关系。
- 接受独立审查 Agent 对压缩合理性的检查。

无法证明时，回到完整方法。产品责任人可以要求任何产品规划运行使用完整流程。

## 5. 贯穿全程的认知架构

认知能力由三个相互独立但协同工作的部分组成。

### 5.1 强制推理内核（Cognitive Kernel）

认知内核不是一个阶段，而是在重要判断中持续运行。

对重要主张至少检查：

1. **认知分型**：事实、来源陈述、推断、假设、价值判断、约束、决定，还是未知。
2. **证据检查**：依据是什么，来源是否可靠、直接、足够和仍然有效。
3. **前提下钻**：判断依赖哪些更底层的前提。
4. **因果检查**：相关性是否被误当成因果，机制是否成立。
5. **竞争解释**：最强的替代解释是什么。
6. **反证检查**：什么证据会推翻当前判断。
7. **第一性原理**：剥离历史做法后，必要条件和真实约束是什么。
8. **跨学科迁移**：其他领域是否存在可迁移的结构或机制。
9. **敏感性分析**：哪个前提改变会导致行动改变。
10. **行动路由**：接受、继续调研、做实验、询问 PM、等待，还是停止。

### 5.2 方法路由器（Method Router）

方法路由器根据当前未知和所需决策选择分析方法，而不是把所有框架机械执行一遍。

每次调用方法前，需要明确：

- 当前要解决的未知。
- 方法需要的输入。
- 预期输出。
- 方法的局限。
- 何时停止。

### 5.3 产品与商业分析方法库（Product & Business Analysis Library）

方法库可以包含但不限于：

- 用户与需求：用户分群、Persona、JTBD、需求优先级、用户研究分析。
- 体验设计：用户体验五层、当前/目标用户旅程、用户故事地图（Story Map）、服务蓝图（Service Blueprint）、信息架构。
- 行为设计：Fogg、COM-B、游戏化八角模型等。
- 价值判断：KANO、四类产品风险、价值因果链、机会成本。
- 市场与方案：竞品、行业最佳实践、相邻领域案例、跨学科机制迁移。
- 产品系统：能力地图、领域对象、状态、规则、模块和依赖。
- 决策：竞争性假设、假设映射（Assumption Mapping）、多方案比较、取舍分析（Trade-off）、敏感性分析。

框架只在适用时调用。框架本身不是证据，多个框架得出相同结论也不会自动提高事实可信度。

### 5.4 跨学科思考操作

跨学科思考是认知基座中的核心能力之一，不只是竞品分析的补充。

统一操作为：

```text
ABSTRACT → ANALOGIZE → EXTRACT → TRANSFER → CHALLENGE → TEST
抽象问题 → 寻找同构场景 → 提取机制 → 迁移到本问题 → 挑战适用前提 → 验证
```

目标不是寻找表面相似案例，而是寻找可以解释或改善当前问题的底层结构、约束、激励、反馈和行为机制。

### 5.5 整体—局部—整体规划循环（Whole–Part–Whole Planning Loop）

BPG 的产品规划不能在确定整体方向后直接逐模块写到底，也不能等所有局部都完成后才象征性检查一次。核心方法是：先形成可工作的整体框架，再深化关键局部，并在每次重要深化后返回整体协调。

```text
整体框架 v0
  → 选择高价值 / 高风险 / 高依赖 / 高未知的模块或决策点
  → 逐块详细规划
  → 返回整体协调
  → 修订受影响的局部与共享契约
  → 稳定整体 Candidate
  → 决定是否拆分以及如何拆分 PRD
```

多模块、跨角色、跨系统或存在复杂依赖的规划必须执行完整循环。简单需求可以在一次紧凑 Pass 中完成，但仍必须覆盖“整体假设—局部验证—整体协调”的完整逻辑，不能因为压缩步骤而降低分析效果。

初始整体框架至少包括：目标结果、目标用户、范围与非目标、核心体验路径、主要模块和决策点、关键对象与状态、共享规则、主要依赖、当前与目标状态，以及会改变规划的关键未知。它是一张可被局部规划检验和修订的工作地图，不是预先冻结的结论，也不能直接按其中的模块机械拆分 PRD。

局部深化按价值、风险、依赖、未知和结构影响排序，不按页面、章节或组织顺序机械展开。每个模块或决策点都必须继承同一份背景、目标和约束，并说明：

- 责任边界以及服务的用户和场景。
- 输入、输出、触发条件和结束状态。
- 功能、规则、对象、状态和权限。
- 主路径、重要分支、异常与恢复方式。
- 对其他模块和共享契约的依赖。
- 已确认决定、关键未知和产品层验收条件。

专业子 Agent 可以对有边界的模块或决策点给出 Findings 和方案，但不能各自形成彼此割裂的最终规划。主 Agent 始终负责把局部结果合并回同一套产品系统。

每完成一个会改变范围、流程、对象、状态、权限、共享规则或依赖的重要局部，或者完成一组相互独立的小局部后，必须回到整体协调，至少检查：

- 端到端体验能否完整运行，用户目标和需求是否仍被覆盖。
- 模块之间是否存在重复、冲突、空缺、责任不清或输入输出不匹配。
- 对象、状态、权限、术语、数据语义和共享规则是否一致。
- 是否出现循环依赖、错误顺序、局部最优损害整体结果，或当前迭代无法接入目标系统。
- 新的局部结论是否推翻上游背景、目标、用户、问题、价值或方案选择。

问题优先返回最早受影响的层级修复：局部问题返回对应模块；跨模块问题同时修改相关模块与共享契约；结构性问题返回整体框架；出现新的重大产品取舍时返回阶段三；目标用户、问题或价值判断失效时返回更早阶段。

只有整体 Candidate 稳定后，才能决定是否以及如何拆分 PRD。拆分后，正式 PRD Review 仍需从全局视角审查整个 PRD Release Set，不能用每份子 PRD 分别成立代替整体成立。

本循环不增加顶层 Graph 节点、独立物理文件或新的程序化工作流。《产品规划主记录》在同一真源中保存整体框架、模块与决策点细化、共享契约、整体协调结论及重要变化。模块—决策矩阵、依赖图、覆盖图和端到端走查记录只在复杂度确有需要时作为条件式 Artifact 生成。语义规划和协调由 Agent 完成；Controller 只在需要时绑定精确 Candidate、轮次和影响关系。

## 6. 主动调研与产品经理提问关口（PM Question Gate）

### 6.1 Agent 先调研，再询问产品经理（PM）

遇到必要信息缺失时，主 Agent 的默认顺序是：

1. 检查项目现有材料、历史记录、数据和已提供来源。
2. 调研可以访问的公开资料和一手来源。
3. 按需调用专业 subagent。
4. 判断信息是否已经足以支持当前决策。
5. 只有自己无法安全、高效获得，或信息本来就只有产品责任人掌握时，才询问产品经理。

### 6.2 有界调研，不无限研究

针对一个关键未知，最多进行五个有效的内部研究或前提下钻层级。

“最多五层”是上限，不是必须做满，也不是连续向 PM 提问五轮。应在以下任一条件出现时提前停止：

- 已达到当前决策所需的充分程度。
- 新一层不再产生会改变决策的信息。
- 已经到达基础事实、根本价值判断或硬约束。
- 可用来源已经耗尽。
- 研究成本高于预期信息价值。
- 只能通过真实用户行为或实验继续验证。

开始一项实质调研前，主 Agent 应明确：

- 研究问题（Research Question）。
- 决策关联（Decision Link）。
- 充分条件（Sufficiency Condition）。
- 来源范围（Source Scope）。
- 深度预算（Depth Budget）。
- 停止条件（Stop Condition）。
- 备选处理（Fallback）。

### 6.3 PM 问题必须成批、少量、高价值

需要询问 PM 时，主 Agent 应一次合并提出通常 1–3 个高影响问题，并同时说明：

- 当前已经知道什么。
- 已经查过什么。
- 缺少什么。
- 为什么它会影响判断。
- 不同回答会改变什么决定。
- 主 Agent 当前的建议是什么。

PM 可以：

- 直接补充。
- 指向资料或其他专业人员。
- 让 Agent 继续调研。
- 明确表示当前未知。
- 选择跳过并接受不确定性。

### 6.4 跳过不等于信息充分

PM 选择跳过时，必须记录：

- 缺失的信息。
- 跳过原因。
- 当前采用的假设或安全默认值。
- 对目标、方案、范围和风险的影响。
- 主 Agent 的建议。
- 产品责任人接受的风险。
- 重新打开问题的条件。

同一问题在没有新证据或风险变化时不重复追问。

对于高影响未知，主 Agent 应明确建议“继续研究（RESEARCH）/ 开展实验（EXPERIMENT）/ 等待（WAIT）”，并至少做一次实质性挑战。产品责任人仍可在接受普通产品风险后授权继续，但不得把未知伪造成事实，也不得把不可豁免的专业、法律或安全条件写成已经满足。

所谓“背景完整”，不是所有信息都已经知道，而是所有可能改变问题定义或行动选择的高影响未知，都已经有明确处置。

## 7. 阶段一：理解（UNDERSTAND）的已确认方法

### 7.1 决策背景模型（Decision Context Model）

背景是整个规划的起点，至少需要理解：

- Signal 的来源、历史和为什么现在出现。
- 用户、提出者、决策者、执行者和成本承担者。
- 用户真实场景、当前完整旅程和现有行为。
- 现有产品、流程、系统、数据和运营方式。
- 替代方案、绕行方法和用户自己的补偿行为。
- 组织目标、利益关系和激励。
- 历史方案、过去结论、失败原因和遗留约束。
- 市场、行业、竞争和环境变化。
- 技术、资源、政策、合规、安全等真实约束。
- 冲突信息、证据缺口和关键未知。

### 7.2 目标状态模型（Goal State Model）

目标需要形成完整的结果链：

```text
用户结果
  → 用户行为或状态变化
  → 产品结果
  → 业务或组织结果
```

同时明确：

- 当前基线。
- 目标状态。
- 时间与人群范围。
- 成功指标。
- 不能被牺牲的保护性指标或约束（Guardrails）。
- 多目标之间的优先级。
- 谁拥有目标和取舍权。

目标状态模型回答“要到达什么状态”；后面的价值模型回答“为什么这个变化值得做、价值如何产生”。两者不能合并。

### 7.3 目标用户与需求模型（Target User & Needs Model）

目标用户与需求分析必须发生在详细问题诊断之前。

候选分群属性包括：

- 自然和社会属性。
- 目标与动机。
- 认知水平。
- 行为习惯。
- 使用成熟度。
- 使用场景。
- 风险、付费或组织角色。

应选择在当前场景下最能解释需求差异的属性作为分类依据：可以是一维程度，也可以是二维象限，但通常不超过二维。

每个用户群需要分析：

- 规模和战略价值。
- 画像、目标、动机和典型场景。
- 当前路径和替代方案。
- 未满足需求。
- 需求频率、严重度和证据。
- 该用户群内的需求优先级。

最后结合用户群规模和价值权重，形成整体需求优先级。权重用于帮助判断，不制造虚假的数学精确度；安全、隐私、无障碍等少数用户的底线需求不能因为人数少而被投票消失。

### 7.4 现状与差距模型（Current State & Gap Model）

现状不能简化为“目前没有某个功能”。需要还原：

- 当前完整流程。
- 每一步的行为、成功率、时间、成本、错误和流失。
- 哪些部分已经运行良好。
- 用户和团队如何补偿现有系统缺陷。
- 不同用户、场景和时间下的差异。
- 当前系统为什么形成现在的状态。
- 目标与现状之间的真实差距。

差距只是需要解释的现象，不自动等于真正的问题。

当前状态的用户旅程属于 `UNDERSTAND`；未来目标旅程属于产品系统规划，两者不能混为一张图。

### 7.5 必须执行的内部动作

阶段一采用内部理解循环，不作为单向流水线执行：

```text
明确规划对象与初始决策问题
→ Agent 自主发现背景和证据
→ 建立初步目标
→ 目标用户分群
→ 用户需求 ↔ 当前行为与现状
→ 形成差距和关键未知
→ 一致性检查
```

主 Agent 必须完成：

1. 明确本次规划对象、初始决策问题、范围和暂不处理的内容。
2. 自主检查项目材料、历史文档、用户反馈、数据、当前产品、流程、系统、运营方式、替代方案和相关外部背景。
3. 区分事实、来源陈述、推断、假设、冲突和未知。
4. 建立目标结果链，以及基线、目标状态、人群、时间、候选指标、Guardrails、目标优先级和目标责任人。
5. 选择最能解释需求差异的一维或二维用户分群方式，识别核心、次要和暂不服务的用户群。
6. 结合用户场景、当前行为、替代方案和实际困难，提炼各用户群的需求、证据和优先级。
7. 还原当前流程、表现良好部分、时间和成本、错误和流失、补偿行为、群体差异，以及当前状态形成的原因。
8. 描述现状与目标之间的可观察差距，不提前断言根因或解决方案。
9. 继续调研 Agent 能够自行解决的未知；只把无法自行获得的 Owner-only 信息合并询问 PM。
10. 检查背景、目标、用户、需求、现状和差距之间是否一致，并确保高影响未知都有明确处置。

用户需求和当前状态必须来回校验，不能脱离用户实际行为凭空总结需求。

### 7.6 必须产出的 Artifact

阶段一固定产出五个逻辑 Artifact。它们默认作为同一个 Product Run 的《产品规划主记录（Product Planning Record）》中的独立章节持续维护，不单独生成《UNDERSTAND 理解工作包》：

| 必须 Artifact | 最低内容 |
|---|---|
| 背景与证据简报 | 规划对象、Signal、历史、相关方、现有产品/流程/系统/运营、约束、证据来源和冲突信息 |
| 目标契约 | 结果链、基线、目标状态、人群、时间、候选指标、Guardrails、优先级和目标责任人 |
| 目标用户与需求矩阵 | 分群依据、用户群规模与价值、场景、当前行为、替代方案、需求、证据、群内和综合优先级 |
| 现状与差距模型 | 当前过程、表现良好部分、成本/错误/流失、补偿行为、形成原因和可观察差距 |
| 未知项与处置清单 | 未知内容、决策影响、Agent 已完成的调研、当前假设、PM 处置、接受风险和重新打开条件 |

Artifact 是逻辑上可独立检查的内容，不等于必须单独建立文件。目标、用户、需求、现状与差距最终应进入或被总 PRD 吸收；详细证据和未知项可以作为内部附件，但高影响内容必须在 PRD 中披露。

### 7.7 条件式 Artifact

当前用户旅程分析是必须动作，但是否画图由复杂度决定。

| 条件式 Artifact | 触发条件 |
|---|---|
| 当前用户旅程图 | 当前过程跨越多个步骤、时间、渠道、角色，或者存在明显分支、中断和恢复 |
| 相关方与利益关系图 | 用户、提出者、决策者、执行者、成本承担者不同，或者存在明显利益冲突 |
| 基线数据分析 | 目标和用户选择依赖规模、转化、时长、错误率、成本等定量数据 |
| Persona / 场景卡 | 不同用户群的动机、认知和行为差异无法通过需求矩阵清楚表达 |
| 当前系统与生态关系图 | 涉及多个产品、前后台系统、数据源、渠道或外部合作方 |
| 当前服务蓝图 | 现状高度依赖客服、运营、人工流程或跨组织协作 |
| 领域概念与约束图 | 领域复杂、术语容易混淆，或存在金融、医疗、法律、安全等专业约束 |
| 补充研究简报 | 高影响未知无法通过现有材料解决，需要专项用户研究、数据分析或外部调研 |

### 7.8 退出标准

满足以下条件，阶段一才可以正常进入阶段二：

1. 规划对象和边界已经明确，或者明确标记为暂定。
2. 重要背景有来源，事实、推断、假设和未知已经区分。
3. 所有可能改变问题定义或行动选择的高影响未知都有明确处置。
4. 目标结果链可以使用，目标责任人和主要取舍权明确。
5. 用户分群能够解释需求差异，而不是随意分类。
6. 核心用户群的主要场景、需求、证据和优先级已经明确。
7. 当前行为、流程、替代方案、补偿行为和表现良好部分已经还原。
8. 差距被描述为可观察现象，没有被提前写成根因或解决方案。
9. 背景、目标、用户、需求、现状和差距之间不存在未解释的重大矛盾。
10. Owner-only 信息已经由 PM 补充、明确跳过或接受风险。
11. 主 Agent 能清楚说明阶段二接下来需要诊断什么。

关键目标仍不清楚时，默认不能正常退出阶段一。Owner 可以强制继续，但必须把目标标记为暂定，明确接受风险，并保留重新打开条件。

### 7.9 角色与 Review

| 角色 | 阶段一职责 |
|---|---|
| 主 Agent | 完成背景发现、分析、分群、需求提炼、现状还原、Artifact 编写和一致性检查 |
| 专业子 Agent | 按需完成有边界的用户、数据、领域或市场研究，只返回 Findings |
| 人类 PM / Owner | 补充内部信息，纠正背景，确认目标权、用户权重和取舍，处置 Owner-only 未知 |
| Reviewer | 阶段一默认不做独立正式 Review；复杂、高风险或矛盾较多时，条件式进行理解挑战 |
| Controller | 只记录精确来源、Artifact 引用和阶段位置，不判断背景是否足够深 |

阶段二形成完整问题诊断后，再对阶段一和阶段二的整体 Candidate 进行一次独立 Problem Review，避免重复审查。

### 7.10 Agent 与程序化脚手架分工

阶段一的发现、理解、分群、需求分析、现状还原、未知判断和 Artifact 编写全部由 Agent 完成。

程序只在精确来源和版本绑定、大规模确定性数据处理或必要的机械校验中使用。不得通过字段完整度评分、自动分群结果或 Schema 校验代替语义判断，也不为阶段一新增独立运行层。

## 8. 阶段二：诊断与价值判断（DIAGNOSE & VALUE）的已确认方法

### 8.1 竞争性问题诊断（Competing Problem Diagnosis）

不能直接把第一个解释写成根因。至少同时维护：

- `H1`：当前首选的问题诊断。
- `H2`：最强的竞争诊断。
- `H3`：问题可能不存在，或不值得现在解决。

每个诊断都要说明：

- 通过什么机制形成当前差距。
- 哪些证据支持。
- 哪些证据冲突。
- 什么证据能区分不同诊断。
- 什么证据会推翻它。
- 它是否可干预、是否有足够杠杆。

### 8.2 第一性原理分析协议（First-Principles Protocol）

第一性原理分析至少回答：

- 用户最终真正要获得的结果是什么。
- 实现结果的必要条件是什么。
- 哪些是客观约束，哪些只是历史习惯或现有解法。
- 如果不存在当前产品和行业惯例，会怎样重新构建。
- 最小但最有杠杆的改变是什么。
- 什么证据会证明这套推理错误。

### 8.3 价值因果模型（Value Causal Model）

价值不能只罗列“用户价值、商业价值、团队价值”。每种价值都要形成因果链：

```text
解决问题的机制
  → 改变用户或团队行为
  → 改善可观察的产品结果
  → 产生用户 / 商业 / 团队 / 效率 / 风险 / 能力价值
```

同时分析：

- 谁获益，谁承担成本。
- 价值规模、频率和持续时间。
- 不做的成本。
- 做错的成本。
- 机会成本。
- 二阶影响和潜在伤害。
- 最脆弱的因果连接。
- 当前证据可信度。

KANO 等模型可以条件式使用。例如，需要区分基础因素、期望因素和激励因素时使用 KANO；但结论必须绑定具体用户群、场景和时间，不能把模型标签当作普遍事实。

### 8.4 成功标准与保护性约束（Success & Guardrail）

阶段二需要把目标、问题和价值落到可观察的成功标准，同时保留不能被成功指标掩盖的保护性约束（Guardrail）。

“成功”必须能回溯到目标用户的行为或状态改善，不能只使用功能交付、页面上线或文档完成作为成功指标。

### 8.5 阶段边界与内部诊断循环

阶段二只回答三个问题：

1. 现象背后的真正问题是什么。
2. 为什么这个问题最值得解决。
3. 解决到什么程度才算成功。

阶段一说明“发生了什么、希望到达哪里”；阶段二判断“真正阻碍目标的是什么、为什么值得解决”；阶段三才回答“什么解决方案最好”。阶段二不得重新发明用户和目标，也不得提前把某个功能方案写成问题。

阶段二按以下内部循环运行：

```text
阶段一输出：背景、目标、用户、需求、现状与差距
                    ↓
差距现象 → 候选问题 → H1 / H2 / H3 竞争诊断
                    ↕
          补证据 / PM Grilling / 返回阶段一
                    ↓
因果机制 → 第一性原理 → 问题优先级 → 价值因果
                    ↓
          成功标准、Guardrails、反证条件
                    ↓
             冻结 Problem Candidate
                    ↓
                Problem Review
```

### 8.6 必须执行的内部动作

主 Agent 必须完成：

1. 精确继承并校验阶段一的背景、目标、用户需求、现状差距和未知项；发现上游错误时返回阶段一，不能在阶段二静默修改。
2. 区分现象、需求、问题和解决方案，避免把指标下降、用户提出的功能或当前缺少的页面直接写成问题。
3. 从不同用户群、需求权重、场景和差距中建立候选问题集合，不立即锁定第一个解释。
4. 建立 H1 / H2 / H3 竞争诊断，并为每个诊断说明支持证据、冲突证据、因果机制、判别证据和反证条件。
5. 对能够改变诊断的未知进行有界补充研究；优先由 Agent 自行调研，并遵守已经确认的最多五个有效下钻层级。
6. 完成因果与第一性原理分析，区分客观约束、历史惯例和现有解法造成的限制，识别最底层且最有杠杆的可干预点。
7. 综合用户需求权重、影响规模、频率、严重度、战略价值、紧迫性、因果杠杆、证据强度、机会成本和潜在伤害，选择必须优先解决的核心问题；不得用单一总分制造虚假精确度。
8. 建立价值因果链，说明解决问题如何改变行为和可观察结果，以及谁获益、谁承担成本、不做和做错的代价是什么。
9. 定义成功结果、可观察指标、Guardrails、关键未知、停止条件和会推翻当前判断的新证据。
10. 完成整体一致性检查并冻结精确 Problem Candidate，准备进入独立 Problem Review。

### 8.7 必须产出的 Artifact

阶段二固定产出五个逻辑 Artifact。它们默认继续写入同一份《产品规划主记录》，作为阶段二的独立章节，而不是新建《DIAGNOSE & VALUE 诊断与价值工作包》：

| 必须 Artifact | 最低内容 |
|---|---|
| 问题定义与范围 | 目标用户、场景、差距、核心问题、问题边界、不处理内容，以及为什么它不是表面现象或预设方案 |
| 竞争诊断与证据矩阵 | H1 / H2 / H3、支持证据、冲突证据、判别证据、反证条件和当前可信度 |
| 因果与第一性原理模型 | 因果链、底层前提、硬约束、历史惯例、关键杠杆点和最强竞争解释 |
| 价值与问题优先级模型 | 获益者、成本承担者、价值类型、规模、频率、持续时间、不做成本、做错成本、机会成本和二阶影响 |
| 成功、Guardrails 与改判契约 | 成功结果、指标、保护性约束、关键未知、停止条件、重新打开条件和推翻当前判断的证据 |

进入审查时，冻结《产品规划主记录》的精确版本，并把其中阶段一与阶段二的相关章节共同视为不可变的 Problem Candidate。无需复制成另一套手工维护文档，但 Problem Candidate 必须能够形成完整、可独立审查的问题叙事。

### 8.8 条件式 Artifact

| 条件式 Artifact | 触发条件 |
|---|---|
| 系统因果循环图 | 存在多因素反馈、延迟、强化、抵消或非线性影响 |
| 定量诊断简报 | 判断依赖漏斗、留存、队列、分群、成本或行为数据 |
| KANO / 价值类型分析 | 需要判断基础因素、期望因素和激励因素，并且结论可以绑定具体用户群、场景和时间 |
| 机会规模分析 | 问题价值高度依赖用户规模、频率或经济影响 |
| 风险与伤害模型 | 涉及安全、隐私、金融、医疗、法律或其他不可逆影响 |
| 专项研究简报 | 当前证据无法区分 H1 与 H2，且该差异会改变后续行动 |
| 相关方价值冲突图 | 获益者、使用者、付款者、执行者和成本承担者明显不同 |

### 8.9 退出标准

阶段二不能直接进入阶段三。满足以下条件后，才能把 Problem Candidate 提交给独立 Problem Review：

1. 阶段一输入仍然有效，或者已经返回阶段一完成必要修订。
2. 现象、需求、问题和解决方案已经区分。
3. H1 / H2 / H3 均得到实质处理。
4. 首选问题存在可以解释、可以反证的因果机制。
5. 已说明为什么它比竞争问题更重要。
6. 问题绑定明确的用户群、场景和需求。
7. 价值因果链成立，并说明成本承担者和潜在伤害。
8. 成功标准来自用户、产品或业务状态变化，而不是功能上线。
9. Guardrails、关键未知、反证和改判条件已经明确。
10. 主 Agent 能说明阶段三需要寻找什么类型的解决方案。

Problem Review 的正式结果及回流规则为：

- `PASS`：进入阶段三。
- `REVISE`：返回阶段二生成新的 Problem Candidate。
- 发现上游认知错误：返回阶段一。
- `NEEDS_OWNER`：由默认同一位 PM / Owner 处理价值、风险或目标取舍；发生实质认知变化后重新生成 Candidate。

### 8.10 角色与 Review

| 角色 | 阶段二职责 |
|---|---|
| 主 Agent | 完成诊断、补充研究、因果分析、价值判断、Artifact 编写、自我挑战和 Candidate 冻结 |
| 专业子 Agent | 按需完成有边界的数据、用户、领域、商业价值或风险分析，只返回 Findings |
| 人类 PM | 补充内部认知并接受主 Agent Grilling；普通讨论不自动构成正式决定 |
| Owner | 仅在目标、价值权重、风险接受或继续投入发生实质取舍时承担正式责任；默认与 PM 是同一个人 |
| Reviewer | 在 Problem Candidate 冻结后，独立审查阶段一与阶段二的整体认知，不替主 Agent 修改 |
| Controller | 只绑定精确输入、Candidate 版本、Review 结果和流程位置，不判断哪个问题是真的 |

Problem Review 是阶段二之后的一次独立 Graph 调用，不塞进阶段二内部。它审查阶段一与阶段二共同形成的完整问题认知，因此不需要在阶段一单独重复一次正式 Review。

### 8.11 Agent 与程序化脚手架分工

问题诊断、因果分析、第一性原理、价值判断、问题优先级、成功标准和 Artifact 编写全部由 Agent 完成。

程序只用于精确输入与 Candidate 版本绑定、必要的确定性数据计算、格式检查和状态提交。程序不得通过评分模型、字段完整度或自动根因分类替代 Agent 的产品判断。

## 9. 阶段三：探索解决方案与决策（DISCOVER SOLUTIONS & DECIDE）的已确认方法

### 9.1 方案情报与跨领域迁移（Solution Intelligence & Cross-domain Transfer）

寻找方案时不能只看直接竞品。应按问题需要研究：

- 直接竞品。
- 行业最佳实践。
- 相邻领域的优秀案例。
- 跨学科可迁移的机制。

目的不是只做到比竞品更好，而是找到当前条件下最好的解决方案。

需要分析：

- 对方服务哪类目标用户。
- 解决了什么问题，使用什么机制。
- 用户体验达到了什么水平。
- 哪些是行业基础能力，哪些是差异化能力。
- 成立依赖哪些前提。
- 有什么代价、不足和仍未满足的需求。
- 哪些可以迁移，哪些因用户、战略或资源不同而不适用。

最终明确我们的目标水平：

- 必须达到。
- 需要持平。
- 重点超越。
- 有意不做。
- 重新定义。

### 9.2 替代解决方案概念（Alternative Solution Concepts）

不能只比较几个功能方案。候选解法可以包括：

- 产品功能或产品体验改变。
- 流程、规则或政策改变。
- 运营或人工方案。
- 合作方或外部能力。
- 不新增功能的方案。
- 延迟或不做。
- 最小实验。

每个候选至少比较：

- 解决机制。
- 预期改变的行为和价值。
- 核心假设。
- 用户体验水平。
- 价值、易用性、可行性和商业合理性风险。
- 成本、时间和长期维护。
- 风险与可逆性。
- 放弃条件（Kill Condition）和改判条件。

“最好方案”是指在当前目标、证据、约束和风险下最优，不是永远最优。决策候选版本必须写明什么变化会导致改判。

### 9.3 决策候选版本（Decision Candidate）

主 Agent 必须给出明确首选建议，而不是只列选项让产品责任人自己分析。

决策候选版本至少表达：

- 推荐的行动。
- 最强替代方案。
- 不做或等待方案。
- 关键证据和未知。
- 主要取舍。
- 风险与保护性指标或约束。
- 改判条件和下一步。

随后调用通用候选版本审查。人类 PM 可以继续在认知循环中接受和参与深度质询（Grilling）；Review PASS 后，由 Agent 在预授权范围内自动提交 `COMMIT NOW`，或在不满足自动条件时升级为明确的 Owner Choice。

### 9.4 阶段边界与内部方案循环

阶段三负责找到当前条件下最好的解决机制，形成明确的 Agent 推荐，并交给 Reviewer 挑战；Review 通过后，由 Agent 在预授权范围内自动提交，或条件式升级给 Owner 决策。它必须区分：

- 解决机制：为什么这个方向能够改变问题。
- 解决方案概念：产品、体验、流程、规则或服务准备如何解决。
- 产品系统规划：具体范围、流程、结构和模块，留到阶段四。

阶段三按以下内部循环运行：

```text
Problem Review PASS
        ↓
明确方案决策问题与约束
        ↓
竞品 / 最佳实践 / 跨学科方案情报
        ↓
提取底层解决机制
        ↓
生成有意义且结构不同的候选方案
        ↓
比较价值、体验、可行性、风险和可逆性
        ↓
选择推荐行动与最强替代方案
        ↓
冻结 Decision Candidate
        ↓
Decision Review → 自动决策条件判断 → Agent 提交 / Owner Choice
```

任何方案研究如果推翻了背景、目标、用户或问题诊断，必须返回阶段一或阶段二；不能用一个看似优秀的方案掩盖上游认知错误。

### 9.5 必须执行的内部动作

主 Agent 必须完成：

1. 精确绑定已经通过 Problem Review 的 Problem Candidate，并确认当前需要决定的方案问题、约束、允许的行动范围和暂不决定的内容。
2. 按问题需要研究直接竞品、行业最佳实践、相邻领域、跨学科机制、用户当前替代方案、失败案例和反模式；目标是理解机制和适用前提，不是制作功能对比表。
3. 从案例中抽象降低认知负担、减少步骤、改变激励、提供反馈、建立信任、降低风险、重分配责任或改变默认选项等底层解决机制。
4. 进行替代方案搜索和反事实检查，至少回答：是否存在机制不同的合理替代、最小改变或非产品方案是什么、延迟或不做会怎样、当前方案是否受既有产品或行业惯例限制。
5. 生成真正有意义的候选方案。存在两个或三个合理方向时应完整呈现；只有一个明显成立的方向时可以只输出一个，但必须解释其他方向为什么不成立；没有值得投入的方向时可以推荐 STOP、WAIT 或 RESEARCH，不能为了有方案而制造伪方案。
6. 在高投入、长周期、难回退、高不确定性、平台锁定、重大风险、战略影响、不同用户群对应不同机制，或 Owner 明确要求扩大方案空间时，至少形成三个机制明显不同的方案。
7. 明确必须达到、需要持平、重点超越、有意不做和需要重新定义的目标解决水平。
8. 比较候选方案对问题机制的覆盖、用户价值与体验、不同用户群影响、战略一致性、可行性、依赖、成本、时间、维护、假设、证据、风险、伤害、可逆性和机会成本；不得用一个加权总分替代产品判断。
9. 明确每个主要方案的 Guardrails、Kill Condition、改判条件和下一步验证方式。
10. 主 Agent 选择一个明确推荐行动，并将其映射到 STOP / WAIT / RESEARCH / FUTURE ROADMAP / EXPERIMENT / COMMIT NOW 六类结果之一。
11. 完成自我挑战，说明最强替代方案、为什么暂不选择它、最大风险和未知，以及什么变化会推翻当前推荐。
12. 冻结精确 Decision Candidate，准备进入独立 Decision Review。

### 9.6 必须产出的 Artifact

阶段三固定产出五个逻辑 Artifact，默认继续作为同一份《产品规划主记录》中的阶段三章节维护：

| 必须 Artifact | 最低内容 |
|---|---|
| 方案情报与目标水平 | 相关竞品、最佳实践、跨领域案例、底层机制、适用前提，以及必须达到、持平、超越、有意不做和重新定义的水平 |
| 解决原则与设计约束 | 方案必须遵守的用户价值、体验原则、业务约束、Guardrails 和禁止采用的反模式 |
| 替代解决方案概念 | 每个实质候选的目标用户、解决机制、核心体验、价值、关键假设、依赖、代价和风险；方案数量由真实问题决定，不为凑数生成 |
| 方案比较与取舍分析 | 首选方案、最强替代、最小改变或不做基线，以及主要 Trade-off、机会成本、可逆性、Kill Condition 和改判条件 |
| Decision Candidate | Agent 的明确推荐、六类行动之一、核心依据、最大风险与未知、最强反方、改判条件和下一步 |

进入 Decision Review 时，冻结《产品规划主记录》的精确版本，并把阶段一至阶段三的相关章节及其附件引用共同视为不可变 Decision Candidate。无需新建另一套手工维护的方案工作包。

### 9.7 条件式 Artifact

| 条件式 Artifact | 触发条件 |
|---|---|
| 竞品体验对比图 | 竞品体验水平直接影响目标方案水平或关键取舍 |
| 跨学科机制迁移图 | 主要创新来自相邻领域或其他学科，需要验证迁移前提 |
| 概念草图、线框或体验故事板 | 纯文字无法表达或比较核心体验差异 |
| 技术可行性简报 | 关键方案受技术能力、数据或外部依赖决定；只描述可行性与约束，不写 Engineering SPEC |
| 运营或人工流程概念图 | 方案依赖客服、运营、审核、服务或其他人工流程 |
| 经济性分析 | 成本、收益、单位经济性或长期维护成本会改变方案选择 |
| 风险决策树 | 方案高风险、不可逆或存在多种重大失败后果 |
| 原型或用户验证计划 | 核心未知只能通过用户实际反应判断 |

如果最终选择 EXPERIMENT，阶段三不再生成独立 Experiment Brief；后续直接形成实验型 PRD。

### 9.8 退出标准与 Decision Review

阶段三不能在独立 Decision Review 之前提交正式路线。满足以下条件后，才能把 Decision Candidate 提交给独立 Decision Review：

1. 精确绑定已通过审查的 Problem Candidate。
2. 方案研究范围与当前问题和决策需要相称。
3. 已研究真正相关的直接竞品、最佳实践、相邻领域和跨学科机制，或说明某类情报为什么不适用。
4. 已完成替代方案搜索和反事实检查，没有用固定数量要求制造伪方案。
5. 每个实质候选都能解释如何改变问题机制。
6. 最强替代、最小改变或不做基线已经得到处理。
7. 关键用户体验、价值、可行性、成本、依赖、风险和可逆性已经比较。
8. 关键假设、未知、Guardrails、Kill Condition 和改判条件明确。
9. 主 Agent 给出一个明确推荐，而不是把分析责任交给 Owner。
10. 推荐行动能够映射到六类产品决策结果之一。

Decision Review 的正式结果及回流规则为：

- `PASS`：进入“自动决策条件判断”；满足预授权条件时由 Agent 自动提交 `COMMIT NOW`，否则进入 Owner Choice。PASS 只证明建议经受了独立挑战，不自动等于任何路线已经获准。
- `REVISE`：返回阶段三生成新的 Decision Candidate。
- 发现问题诊断错误：返回阶段二。
- 发现背景、目标或用户错误：返回阶段一。
- `NEEDS_OWNER`：处理价值权重、风险、资源、权限或其他只能由 Owner 承担的取舍。

### 9.9 Agent 自动决策、Owner 升级与分歧处理

Decision Review 获得 PASS 后，主 Agent 先判断是否可以在预授权范围内自动选择 `COMMIT NOW` 并进入阶段四。

Agent 自动提交必须同时满足：

1. 当前 Decision Candidate 与 Review 精确绑定，且 Verdict 为 PASS。
2. 没有 `NEEDS_OWNER` Finding 或尚未处置的重大 Reviewer 分歧。
3. 推荐没有改变已经确认的目标、目标用户、价值权重或战略方向。
4. 行动只进入本地完整产品规划和 PRD 编写，不批准研发、预算、团队资源、跨团队承诺、发布、用户暴露或外部副作用。
5. 行动处于项目或 Owner 已经明确的 Agent 自主决策范围内。
6. 风险较低、行动可逆，且没有会改变行动选择的高影响未知。
7. 主 Agent 已把自动决策依据、风险、授权来源、改判条件和重新检查条件写入《产品规划主记录》。

以上条件是否在产品语义上成立，由主 Agent 判断并写出依据，Reviewer 负责挑战。全部满足时，Agent 可以申请自动提交 `COMMIT NOW`。Controller 不判断“低风险、可逆、无重大未知或未改变价值权重”等语义；它只验证当前 Decision Candidate、绑定的 `PASS` Review、没有正式 `NEEDS_OWNER`、精确预授权记录所允许的路线与本地无外部副作用边界，以及状态迁移是否合法，并记录决策来源为“Agent 在授权范围内自动决定”。缺少可绑定的明确预授权时默认升级 Owner，不得让 Controller 猜测自然语言授权，也不得把 Agent 决定伪装成人类 Owner Choice。

以下任一情况出现时，必须升级给人类 PM / Owner：

- 改变产品方向、目标用户、价值权重或战略优先级。
- 需要真实预算、团队资源、跨团队承诺或产品组合取舍。
- 涉及外部发布、用户暴露、不可逆操作或其他真实副作用。
- 存在高风险、重大未知、`NEEDS_OWNER` 或 Agent 与 Reviewer 的实质分歧。
- 超出预授权范围，或 Agent 推荐与 PM 已明确表达的意图冲突。

需要人类时，Owner 默认查看 Agent 首选建议、最多三项核心依据、最强替代、最大未知与风险、改判条件和推荐下一步，并可以展开查看完整《产品规划主记录》和相关附件。Owner 对当前允许的人类决策路线作出清晰选择，并绑定当前 Decision Candidate。

如果 Owner 选择与 Agent 推荐不同，主 Agent 必须进行一次有实质内容的挑战，聚焦证据差距、主要风险、推荐理由和改判条件，不能只问“是否确定”，也不能无限争论。Owner 拥有最终决定权；系统保留双方理由、Owner 接受的风险和重新检查条件，但不得因此提高 Agent 对原判断的置信度。

Owner Choice 如果改变目标、用户、问题或价值权重，必须返回对应前置阶段重新形成 Candidate；如果只是在已充分披露的选项之间承担责任并作出选择，则直接进入相应正式路线。

### 9.10 角色与 Review

| 角色 | 阶段三职责 |
|---|---|
| 主 Agent | 完成方案研究、机制抽象、替代方案搜索、比较、推荐、自我挑战、Artifact 编写、Candidate 冻结，并在 Review PASS 后判断自动决策条件或升级 Owner |
| 专业子 Agent | 按需完成有边界的竞品、用户体验、技术可行性、运营、经济性或风险研究，只返回 Findings |
| 人类 PM | 补充内部约束、资源现实和方案偏好，并接受主 Agent 对方案偏见和预设答案的 Grilling |
| Owner | 定义 Agent 自主决策边界；在超出边界或出现重大风险、未知、资源与价值取舍时明确选择行动并承担责任；默认与 PM 是同一个人 |
| Reviewer | 独立挑战推荐方案、替代方案、证据、假设、取舍和改判条件，不替主 Agent 修改或替 Owner 决策 |
| Controller | 只绑定精确 Candidate、Review、自动决策授权或 Owner Choice，以及合法路线和决策来源，不判断哪个方案更好 |

### 9.11 Agent 与程序化脚手架分工

方案情报研究、机制抽象、方案生成、替代搜索、比较、推荐、分歧挑战和 Artifact 编写全部由 Agent 完成。

程序只用于精确 Candidate / Review / 授权范围 / Owner Choice 绑定、版本冻结、合法路线、决策来源和正式状态提交。程序不得通过固定方案数量、加权总分、字段完整度或自动推荐模型替代 Agent 的方案判断。

### 9.12 实验（Experiment）路径

产品责任人选择“实验（EXPERIMENT）”时，交付物不是独立的实验摘要（Experiment Brief），而是使用项目默认产品需求文档模板形成的实验型产品需求文档。

实验型 PRD 至少需要覆盖：

- 待验证假设。
- 实验对象和暴露范围。
- 实验体验和需求范围。
- 成功指标。
- 伤害保护性指标或约束。
- 停止与回滚条件。
- 不同实验结果如何映射到后续决策。
- 结果责任人（Owner）。

实验型产品需求文档使用同一套候选版本审查，获得“通过（PASS）”后自动进入可交接就绪，并只做本地交接。

## 10. 阶段四：规划产品系统（PLAN THE PRODUCT SYSTEM）的已确认方法

阶段四内部不是单向瀑布，而是一个持续细化循环（Refinement Loop）。它是 5.5 所定义“整体—局部—整体规划循环”在产品系统规划阶段的主要落点：

```text
范围
 ↔ 目标用户体验与核心路径
 ↔ 体验结构和信息结构
 ↔ 服务蓝图（Service Blueprint）
 ↔ 逻辑产品系统结构
 ↔ 能力与功能模块
 ↔ 模块详细需求
 ↔ 全局一致性检查
```

任何一处发现矛盾，都可以返回修改其他部分。主 Agent 应先形成整体框架 v0，再按价值、风险、依赖和未知深化重要模块与决策点；每轮重要局部深化后返回全局协调。只有整体 Candidate 稳定后，才决定是否以及如何拆分 PRD。

### 10.1 产品范围（Scope）

范围层回答“为了实现目标、解决问题，需要做哪些事情”，不是直接列功能清单。

范围必须保持与目标用户、需求优先级、问题机制、价值和方案选择的对应关系，并明确：

- 范围内（In Scope）。
- 范围外（Out of Scope）。
- 非目标（Non-goals）。
- 当前迭代与未来演进边界。

### 10.2 体验视图必须区分

不同体验视图解决不同问题，不能互相替代：

- 当前用户旅程：用户现在怎样完成事情，属于阶段一。
- 目标用户旅程：未来整体体验应怎样变化。
- 产品用户流程 / 任务流程（Product User Flow / Task Flow）：用户在产品内如何完成核心任务。
- 用户故事地图（Story Map）：用户活动、任务和迭代范围如何组织。
- 服务蓝图（Service Blueprint）：用户触点背后的人、流程和系统如何协同。

### 10.3 逻辑产品与系统结构（Logical Product/System Architecture）

系统结构只规划产品逻辑和需求责任，不写成工程规格说明（Engineering SPEC）。

需要按适用性说明：

- 产品能力。
- 领域对象。
- 输入、输出和状态。
- 数据、事件和业务规则。
- 外部接口和依赖。
- 前台与后台的产品责任。
- 性能、安全、隐私、可用性等产品级非功能要求。

### 10.4 模块拆分（Module Decomposition）

模块拆分优先依据：

- 业务能力。
- 领域边界。
- 共享规则。
- 数据责任。
- 内聚与耦合。
- 独立演进需要。

不能机械地按前端、后台或技术层拆成功能模块。

### 10.5 模块详细规划（Module Detail）

每个模块按适用性规划：

- 负责与不负责的内容。
- 用户任务和使用场景。
- 输入、输出和接口关系。
- 对象、数据、生命周期和状态。
- 规则与不变量。
- 权限、隐私和审计要求。
- 主流程、替代流程、异常、失败与恢复。
- 依赖与失败策略。
- 具体功能和信息内容。
- 验收标准和验证方式。

### 10.6 持续全局校验

全局校验不是阶段末尾才做一次，而是贯穿规划过程。

纵向追溯链：

```text
目标
→ 用户群
→ 需求
→ 问题
→ 价值
→ 方案
→ 用户旅程
→ 产品能力
→ 系统责任
→ 模块
→ 功能
→ 验收标准
→ 指标
```

横向场景穿行至少按适用性检查：

- 正常路径（Happy Path）。
- 替代路径。
- 错误路径。
- 中断与恢复。
- 多角色协同。
- 权限差异。
- 数据缺失和冲突。
- 外部依赖失败。
- 运营或人工兜底。

### 10.7 已确认的运行与表达原则

阶段四确认以下规则：

1. **不设置固定独立 Plan Review。** 阶段四通过主 Agent 的持续 Refinement Loop、按需专业子 Agent 挑战，以及后续独立 PRD Review 保证质量。只有出现新的重大目标、方案、范围、风险或承诺变化时，才返回前置 Decision Review / 决策环节；不为普通规划增加一个重复 Review Gate。
2. **语义内容必须完整，图示只为辅助表达。** 核心流程和逻辑产品系统结构必须在语义上规划清楚，但不要求在内部思考过程中机械画图。只有当关系、分支、状态、角色或文字量使人类阅读负担明显升高时，才使用流程图、系统图、状态图等视觉表达。画图的主要目标是提高最终 PRD 的理解效率，不是证明 Agent 做过思考。
3. **完整目标系统必须规划，当前迭代可以只交付其中一部分。** BPG 采用“完整规划、小步交付”：先保证目标系统、共享规则、依赖和未来演进关系完整，再确定当前迭代和 PRD 范围。不得因为小步交付只规划眼前功能，也不得因为完成了完整规划而强制一次性交付全部范围。

4. **阶段四采用 Agent 优先、条件式人类升级。** Decision Review 获得 PASS 后，如果 `COMMIT NOW` 只代表继续本地产品规划和 PRD 编写，并同时满足预授权、低风险、可逆、无重大未知、无 `NEEDS_OWNER`、不改变目标与价值权重、不形成真实资源或外部承诺等条件，Agent 自动进入阶段四。Agent 置信度本身不构成授权；任一条件不满足时，必须升级给人类 PM / Owner。
5. **产品形态识别先于场景方法，专项推演按需触发。** 主 Agent 必须轻量识别当前产品的主要形态和适用特征，并判断是否需要场景完整性与韧性推演；“必须判断是否适用”不等于“必须执行整套方法”。专项推演、专项 Artifact 和专业 Reviewer 均只在能够实质减少遗漏、风险或歧义时触发。

### 10.8 必须执行的内部动作

1. **绑定正式路线来源。** 精确关联 Agent 自动选择或 Owner 选择的 `COMMIT NOW`、通过审查的 Decision Candidate，以及已经确认的目标用户、需求、问题、价值、成功指标、保护性约束、风险和未知项。
2. **定义完整目标系统与迭代边界。** 明确完整目标状态、当前迭代、后续演进、范围外内容和非目标，避免把当前迭代误当成完整产品。
3. **建立范围与需求链。** 从目标、用户、需求、问题和方案机制推导产品范围；每个范围项都要有来源，不能直接堆功能清单。
4. **规划目标体验。** 说明目标用户体验、关键体验时刻，以及采用、信任、控制和反馈机制。
5. **识别产品形态并规划目标旅程与核心流程。** 先使用“一个主要形态 + 多个特征标签”形成轻量产品形态画像，再判断是否需要场景完整性与韧性推演；触发时按产品形态选择和组合相关场景知识，覆盖适用的正常、替代、异常、中断与恢复、首次使用、空状态、多角色、权限差异、数据冲突、外部依赖失败和人工兜底。
6. **规划体验结构与信息结构。** 明确用户任务、内容、导航、层级、对象和关键关系如何支持目标流程。
7. **规划服务协同。** 当产品涉及后台、运营、人工处理或外部系统时，明确触点背后的责任和交接关系。
8. **规划逻辑产品系统。** 明确产品能力、领域对象、角色、输入输出、状态与生命周期、规则与不变量、数据与事件、前后台责任、外部依赖和产品级非功能要求；不进入数据库、算法、代码结构等工程规格。
9. **拆分能力与功能模块。** 优先按业务能力、领域、用户任务、共享规则、数据责任、独立演进和团队责任拆分，不机械按技术层拆分。
10. **完成模块详细规划。** 逐模块说明责任、用户与场景、功能与内容、输入输出与触发、对象与状态、规则、权限、隐私与审计、主要与异常路径、依赖与失败策略、验收标准。
11. **规划完整系统并安排小步交付。** 当前迭代可以只覆盖完整目标系统的一部分，但不得丢失共享背景、目标、需求分析、整体关系和未来演进约束。
12. **持续执行全局校验。** 同时完成纵向追溯和横向场景穿行；发现上游认知或决策失效时，返回最早受影响的前置阶段重新处理。
13. **按需规划使用数据采集。** 判断当前需求是否需要新增或调整曝光、点击或交互、后台调用及必要结果数据；优先遵守项目级数据采集配置，并只选择支持明确分析目的的必要字段。未触发时不生成数据采集内容。

### 10.9 必须产出的工作产物（Artifact）

以下工作产物默认作为同一份《产品规划主记录》的逻辑章节持续形成，不按步骤机械拆成多个文件：

1. **范围与需求矩阵（Scope & Requirements Matrix）**：范围项与目标用户、需求、问题、价值、方案机制和迭代的对应关系。
2. **目标体验与核心流程（Target Experience & Core Flow）**：目标体验原则、目标旅程和关键产品流程的完整语义说明。
3. **产品体验与信息结构（Product Experience & Information Structure）**：任务、内容、导航、信息层级和关键对象关系。
4. **逻辑产品系统结构（Logical Product System Structure）**：产品能力、对象、状态、规则、数据、事件、责任和依赖如何组合。
5. **模块图与模块详细规划（Module Map & Module Details）**：模块边界、关系，以及每个模块应完成的产品责任和详细需求。
6. **全局规则与共享契约（Global Rules & Shared Contracts）**：跨模块共享的状态、权限、数据、异常、恢复、审计和产品级非功能要求。
7. **完整系统与迭代结构（Complete System & Iteration Structure）**：完整目标系统、当前迭代、后续迭代及其依赖和价值贡献关系。
8. **一致性、覆盖与追溯检查（Coherence, Coverage & Traceability Check）**：纵向追溯、横向场景穿行、缺口和处置结果。

### 10.10 条件式工作产物

以下内容只在确实能降低理解成本、消除歧义或支持后续 PRD 时形成，可以作为主记录章节或被精确引用的视觉附件：

- 核心场景与韧性覆盖模型。
- 数据采集需求表。
- 目标用户旅程图。
- 详细任务流程图。
- 信息架构图。
- 服务蓝图。
- 领域对象关系图。
- 状态机。
- 角色与权限矩阵。
- 数据流或事件流。
- 外部依赖图。
- 失败与恢复图。
- 线框图、原型或故事板。
- 用户故事地图或迭代地图。
- 产品级非功能要求检查表。

条件式图示仍遵守 10.7：只有它能实质降低最终 PRD 的人类阅读负担时才制作，不能把“画过图”当成思考完成的证明。

### 10.11 退出标准

只有同时满足以下条件，阶段四才能进入 `READY_FOR_PRD_AUTHORING`（可开始编写 PRD），该状态不等于产品已经 Ready：

1. 已绑定精确的 `COMMIT NOW` 路线来源和通过审查的 Decision Candidate。
2. 完整目标系统、当前迭代、后续演进、范围外内容和非目标清楚。
3. 每个重要范围项都能追溯到目标用户、需求、问题、价值和方案机制。
4. 已识别足以支持规划的产品主要形态和相关特征，场景完整性与韧性推演的适用性已经得到处置；如果触发，目标体验与核心流程语义完整，并已经处理重要异常和恢复路径。
5. 体验结构和信息结构能够支持目标任务。
6. 前台、后台、人工与外部系统的产品责任边界清楚。
7. 产品能力、对象、状态、规则、数据、事件和依赖可以组合成可运行的逻辑整体。
8. 模块边界不存在未处置的重大缺口、重复或冲突。
9. 当前迭代涉及的模块已经详细到足以形成 PRD。
10. 跨模块的共享规则和契约一致。
11. 适用的产品级非功能要求已经处理。
12. 当前迭代能产生有意义的结果，或明确说明其对完整用户价值的贡献。
13. 高影响未知项已经被消除、降级、接受或升级。
14. 纵向追溯和横向场景穿行不存在未解决的重大断点。
15. 主 Agent 能够判断形成一份 PRD，还是需要进入“总 PRD + 子 PRD”的条件式拆分评估。
16. 数据采集适用性已经得到处置；如果触发，采集目的、行为或调用语义、必要字段、项目配置和隐私边界清楚。

### 10.12 审查机制与角色分工

阶段四不设置固定独立 Plan Review，但不代表没有质量挑战：

- 当涉及复杂体验、多角色权限和状态、多外部系统、监管或高风险领域、大型多团队系统，或者主 Agent 对关键规划结论存在实质不确定性时，按需调用专业子 Agent 做边界明确的挑战。
- 场景与韧性专项审查不作为所有 PRD 的固定 Review 维度。简单需求可以不触发；一般复杂度由通用 PRD Reviewer 按需检查；强离线、复杂状态机、金融或法律结果、多端同步、Agent 自主执行、大量外部依赖、内部高权限运维或安全域隔离等高复杂度与高风险情况，才条件式调用专业 Reviewer。
- 正式的独立审查发生在后续 PRD Review；如果阶段四出现会改变目标、方案、重大范围、风险或承诺的变化，必须返回 Decision Review 或最早受影响的前置阶段。
- 主 Agent 负责完成和整合全部产品规划，不把核心判断责任外包给子 Agent。
- 人类 PM 主要补充 Agent 无法自行获得的内部团队分工、流程、资源、政策和运营约束。
- Owner 只在出现重大改变、重大风险、超出预授权或不可逆承诺时介入，不设置固定的阶段末确认。
- Reviewer 在阶段四没有固定审查节点，不参与共同撰写；其正式职责保留到 PRD Review。
- Controller 只绑定精确决策、主记录版本、附件和阶段状态，不做语义判断。

### 10.13 Agent 与程序化脚手架的分工

主 Agent 负责所有语义规划、推理、整合、追溯和适用性判断。程序化脚手架只用于冻结版本、生成精确引用、维护文件关系、执行格式或结构检查和提交状态；除非程序在一致性、可重复性或可验证性上具有不可替代的优势，否则不得用程序生成语义产品方案。

### 10.14 产品形态识别与条件式场景韧性推演

阶段四采用三层路由：

```text
轻量识别产品形态
→ 判断专项场景分析是否适用
    → 不适用：继续正常规划
    → 适用：选择场景知识包并完成场景与韧性推演
```

#### 10.14.1 产品形态画像

产品形态画像不是互斥的产品分类树，而是“一个主要形态 + 多个特征标签”。同一个产品可以同时是 macOS 桌面客户端、本地与云端混合、多人协作并包含 Agent 能力。主 Agent 至少按以下四层判断：

1. **交互载体**：桌面客户端、iOS、Android、Web、Agent 或对话式产品、API / SDK 或无界面产品，以及跨端组合产品。
2. **运行与部署形态**：纯本地、纯云端、本地与云端混合、离线优先、强在线依赖、单机、单租户或多租户。
3. **交互与任务形态**：即时同步操作、异步长任务、后台持续运行、多步骤事务、自主 Agent 执行、多人协作和多设备同步。
4. **风险、治理与信任边界**：数据修改或删除、金融或法律结果、隐私与敏感信息、真实外部副作用、不可逆操作、高容量或高并发、安全相关操作、内部运维或管理需求、生产与高权限操作、仅限内网或受控网络访问、数据分类与安全域隔离、租户隔离、审计和其他合规约束。

阶段一可以先记录已经确定的终端、运行环境和治理背景；阶段三选择方案后，阶段四必须重新确认产品形态，因为解决方案可能改变载体、部署、交互和风险特征。该画像默认是《产品规划主记录》中的轻量判断，不要求生成独立 Artifact。

访问与隔离要求仍遵守 PRD / Engineering SPEC 边界：产品规划和 PRD 定义谁可以访问、可以从什么受控环境访问、哪些数据或操作必须隔离、隔离失败会造成什么产品风险，以及必须达到的可观察约束；网络拓扑、身份基础设施、具体安全域实现、存储和部署机制由 Engineering SPEC 负责。

#### 10.14.2 产品形态场景知识包

主 Agent 根据产品形态画像选择并组合相关场景知识，不能把一个通用 Checklist 不加判断地应用于所有产品：

- 桌面客户端重点考虑进程退出与崩溃恢复、窗口状态、文件和系统权限、本地存储、升级迁移、资源占用与离线运行。
- iOS 重点考虑前后台切换、系统权限、网络切换、系统中断、设备空间、交互习惯和平台生命周期。
- Android 除移动端通用问题外，还重点考虑设备与系统版本差异、系统返回行为、后台限制、权限差异和低性能设备。
- Web 重点考虑刷新、返回、深链接、多标签页、会话失效、浏览器与屏幕差异、本地浏览器状态和网络变化。
- Agent 或对话式产品重点考虑意图不明确、工具不可用、部分执行、错误事实、权限越界、重复副作用、长任务中断、取消与恢复以及人类接管。
- 本地产品重点考虑文件损坏、磁盘空间、设备丢失、本地数据安全、升级迁移和缺少云端恢复。
- 云端产品重点考虑身份与会话、服务不可用、配额、数据延迟、并发冲突、租户隔离、外部依赖和降级运行。
- API、SDK 或无界面产品重点考虑调用者身份、版本兼容、重复调用、部分成功、限额、状态可观察性、错误语义和恢复合同。
- 内部运维或管理产品重点考虑高权限访问、内网或受控网络边界、生产操作防误触、职责分离、数据安全域、审计、应急访问和人工回退。

场景知识包是可扩展的方法知识，不是固定 Graph 节点。Agent 可以根据实际产品组合多个知识包、删除无关项并补充当前领域特有场景。

#### 10.14.3 通用场景面与关键分支契约

产品形态知识包决定“重点看什么”；通用场景面用于防止遗漏。触发专项推演时，主 Agent 按适用性检查：

1. 进入条件：首次、再次、未登录、无权限、已有数据和空数据。
2. 输入与边界：缺失、无效、最小、最大、超过上限和重复提交。
3. 用户中断：返回、取消、关闭、切换、重复操作和长时间离开。
4. 执行状态：加载、长时间等待、排队、部分完成、成功、失败和结果未知。
5. 环境与依赖：断网、弱网、外部服务失败、容量不足、数据过期和并发冲突。
6. 恢复与结束：重试、继续、撤销、回滚、修改后重交、人工兜底和安全停止。

每个需要进入产品规划的关键分支至少说明：触发条件、用户可观察状态、允许与禁止的动作、已有数据和真实副作用如何处理、恢复方式，以及最终成功、可恢复或安全停止状态。PRD 只定义这些产品行为；缓存、重试算法、队列、存储、网络和其他内部机制移交 Engineering SPEC。

#### 10.14.4 触发、产物与 Review 分级

以下任一情况出现时，应考虑触发专项推演：存在多个产品状态或合法分支；存在异步、加载或长任务；依赖网络、云端或外部系统；涉及本地数据、同步、多端一致性、容量、次数、时间、金额、权限、多角色、外部副作用、不可逆性、高风险操作；失败后用户不能自然恢复；或者不同平台会产生明显不同的产品行为。

触发后的产物按复杂度决定：

- 少量重要分支直接写入相关模块规划和 PRD，不生成专项 Artifact。
- 中等复杂度在《产品规划主记录》中形成简短的场景与恢复章节。
- 复杂状态、平台差异或恢复关系形成条件式《核心场景与韧性覆盖模型》，并按需配状态机、决策表、容量与上限策略、离线与同步产品契约、失败与恢复图或权限矩阵。

Review 同样按需分级：不触发专项分析的简单需求不增加专项审查；一般复杂度由通用 PRD Reviewer 检查；只有专业审查具有明显额外价值时，才调用场景与韧性专业 Reviewer。所有适用性、场景选择、风险判断和产品行为设计由 Agent 完成；程序化脚手架不得自动选择产品类型、穷举分支或替代语义判断。

### 10.15 条件式使用数据采集

本方法中的“数据上报”特指为了后续产品分析而采集的使用数据，不扩张为完整产品指标体系、数据平台、系统可观测性或商业分析方案。成功指标和 Guardrails 仍由阶段二负责；本节只判断为了观察实际使用是否需要新增或调整采集。

#### 10.15.1 基础采集类型

1. **GUI 产品**：主要采集曝光数据，以及点击、选择、输入、提交、取消等有分析意义的用户交互数据；不要求记录所有原始点击。
2. **后台服务或非 GUI 服务**：主要采集 API、工具、任务、命令或服务能力的调用数据。
3. **必要结果数据**：当曝光、点击或调用本身不能证明任务结果时，按需补充成功、失败、取消、超时或最终状态。结果可以是独立事件，也可以是调用记录中的结果字段，不固定为新的事件类别。

#### 10.15.2 上报字段与项目级配置

常见候选字段包括：UID、匿名用户 ID、Session ID、账号、租户、用户角色、平台、设备、产品版本、页面、模块、功能对象、时间、语言或地区、实验分组、成功或失败结果、错误类别、IP 和设备标识等。

这些字段只是候选，不是 BPG 的全局默认必填项。主 Agent 必须根据具体分析目的、产品形态、现有数据、数据敏感性和项目政策选择最小必要字段，尤其不能因为“以后可能有用”而默认收集 UID、IP、设备标识、自由文本或完整行为轨迹。

项目可以配置自己的**数据采集配置（Data Collection Profile）**，至少可以声明：

- 项目通用必填字段。
- 按场景选用的可选字段。
- 禁止采集字段。
- 需要额外隐私、安全、地区或 Owner 确认的敏感字段。
- 不同平台、事件类型或用户角色的差异要求。
- 组织已有的事件分类、字段命名和数据责任规范。

主 Agent 优先读取并遵守当前项目配置，再根据具体需求补充必要字段；配置缺失不阻止 Agent 完成低风险判断，但配置冲突、敏感字段必要性或内部政策无法自行确定时，才向人类 PM / Owner 请求信息或决定。项目配置约束字段边界，不替 Agent 判断当前需求是否真的需要采集。

#### 10.15.3 PRD 表达与工程边界

数据采集是条件式 PRD 内容。少量采集要求直接写在对应功能或模块需求中；数量较多、需要跨模块复用或独立协作时，形成条件式《数据采集需求表》，可以作为 PRD 附件被精确引用。

产品规划、PRD 或数据采集需求表按适用性说明：

- 分析目的。
- 曝光、交互或调用的对象与行为。
- 什么条件构成一次有效采集。
- 是否需要成功、失败或最终状态。
- 必要的分析字段和明确禁止采集的信息。
- 适用的项目配置和隐私、地区或安全约束。

事件名、字段 Schema、客户端或服务端发送位置、SDK、接口、缓存、批量、重试、去重、压缩、数据管道、存储、查询和 BI 配置属于 Engineering SPEC、数据采集实施规格或后续数据工程工作，不进入通用 PRD 正文。项目协作制度确实要求固定事件标识或字段名称时，可以在条件式数据采集附件中保留，但这不改变实现机制的责任边界。

#### 10.15.4 Agent、Review 与脚手架分工

主 Agent 负责判断是否需要采集、选择有分析价值的行为或调用、定义产品语义、选择必要字段、应用项目配置并识别隐私风险。一般需求由通用 PRD Reviewer 按需检查采集目的、语义、字段必要性和配置一致性；涉及 UID、IP、设备标识、敏感数据、跨地区或大规模画像时，才条件式调用隐私、安全、地区或数据专业 Reviewer。

程序化脚手架可以校验项目数据采集配置的版本、引用和确定性字段约束，但不得自动决定要采集什么、不得为了满足 Schema 补造数据要求，也不得把配置中的可选字段全部变成必填字段。

### 10.16 条件式多语言与地区适配

多语言与地区适配不增加新的顶层 Graph 节点，也不要求每个需求都执行一套固定本地化流程。主 Agent 必须进行一次轻量适用性判断；只有判断适用时，才展开具体规划、Artifact 和专业 Review。未触发时，除必填 Checklist 中标记“不适用”外，可以从产品规划主记录和 PRD 正文中省略。

#### 10.16.1 三层适配模型

主 Agent 必须区分三个相互关联但不能混为一谈的层次：

1. **语言适配**：界面语言、产品文案、术语、语气、复数或性别变化、用户语言选择，以及翻译缺失时的回退。
2. **Locale 本地格式适配**：日期、时间、时区、数字、货币、计量单位、姓名、地址、电话号码、排序、搜索、文字方向、文字长度和版式变化。
3. **市场与地区适配**：目标市场、功能可用范围、价格与支付、法规、隐私、数据驻留、当地内容、文化或宗教敏感性，以及地区性的业务和运营约束。

语言和地区不是一一对应关系。同一种语言可以服务多个市场，同一个地区也可以存在多种语言；用户语言偏好、实际所在地区和产品目标市场必须分别判断，不能用其中一个简单替代另外两个。

#### 10.16.2 项目级语言与地区配置

项目可以配置自己的**语言与地区配置（Locale & Market Profile）**，按需要声明：

- 默认语言、支持语言和目标市场或地区。
- 用户选择语言的入口、选择结果的保持方式，以及缺失内容的回退顺序。
- 不同地区的功能、内容、价格、支付或政策差异。
- 日期、时区、货币、数字、单位、姓名、地址和电话号码规则。
- 项目术语、品牌词、禁止翻译项、文案语气和本地化内容责任人。
- 需要地区专业人员确认的内容，以及法规、文化、隐私和数据驻留约束。

语言选择默认遵循“用户主动选择优先，其次是账户设置、设备或浏览器设置，最后才使用地区信号辅助判断”。IP 或地理位置只能作为弱信号，不得覆盖用户的明确选择，也不得被视为语言、文化或市场身份的可靠替代。

主 Agent 优先读取项目配置，并自行完成公开资料调研和第一轮适配判断。只有内部市场策略、支持地区承诺、当地业务规则或高影响专业判断无法自行获得时，才向人类 PM / Owner 或专业人员请求补充。配置不存在时，Agent 仍应完成低风险判断，并显式保留重要未知。

#### 10.16.3 触发与 Artifact 分级

出现多种语言或多个目标市场、用户可选择语言、动态或用户生成多语言内容、地区格式差异、从右向左文字、跨地区功能或内容差异、跨地区数据处理、地区法规，或者区域性发行限制时，应展开适配规划。

产物按复杂度决定：

- 少量要求直接写入相关模块规划和 PRD，不生成专项 Artifact。
- 中等复杂度在《产品规划主记录》中形成语言与地区适配章节。
- 多语言、多市场或差异复杂时，形成条件式《语言与地区适配矩阵》，表达“地区 × 语言 × 功能或内容差异 × 格式规则 × 内容来源 × 回退规则 × Review 要求”。
- 术语表、地区功能矩阵、本地化文案稿和代表性页面可以作为条件式附件；只有独立协作、维护或审查具有明显价值时才拆成单独文件。

BPG 的产品规划主记录和正式 PRD 继续以中文为主要表达语言。目标产品需要展示的其他语言文案或本地化资产可以作为被引用的条件式附件，不要求把所有语言的完整翻译塞进 PRD 正文。

#### 10.16.4 PRD 与 Engineering SPEC 边界

PRD 负责定义用户可观察的产品行为，包括支持哪些语言和市场、默认选择与用户覆盖规则、回退行为、地区功能差异、格式表现、缺失本地化内容时如何处理，以及哪些文化、法规或市场约束会改变产品体验。精确到 `zh-Hans`、`zh-Hant` 等语言或地区范围的声明，如果会影响产品承诺和交付范围，也属于产品要求。

资源文件、字符串 Key、Locale 检测算法、国际化库、语言包加载与缓存、构建工具、翻译流水线以及内部布局实现属于 Engineering SPEC。PRD 可以要求长文本、从右向左布局和多语言切换下保持可用，但不规定工程实现方式。

#### 10.16.5 Agent、专业 Reviewer 与人类分工

主 Agent 负责适用性判断、公开调研、配置应用、初稿生成、基础语言检查和风险识别。专业 Review 按需拆分：

- **语言精确性 Reviewer**：检查语义、语法、术语和翻译准确性。
- **产品文案 Reviewer**：检查清晰度、自然度、语气、行动文案、提示和错误信息。
- **地区文化 Reviewer**：检查当地习惯、图片、例子、禁忌、文化敏感性以及产品行为是否适合目标市场。
- **合规 Reviewer**：仅在存在法律、监管、隐私、数据驻留或地区政策风险时调用，不由语言或文化 Reviewer 代替。

这些 Reviewer 不是每份 PRD 的固定调用。一般复杂度由通用 PRD Reviewer 检查范围、回退和内部一致性；只有专业审查具有明显额外价值时才调用专项 Reviewer。专项 Reviewer 应审查冻结的本地化 Candidate、代表性页面或精确引用的文案附件，而不只审查中文 PRD 中的抽象描述。

Agent 能够可靠完成的工作仍由 Agent 完成。涉及高影响市场承诺、文化或宗教敏感内容、法律后果，或者缺乏可靠语言证据时，必须请求当地母语者、专业人员或有权限的人类确认；没有实际完成人类专业验证时，必须记录为 `NOT_RUN`，不得推断已经通过。

## 11. 阶段五：产品需求文档与交接（PRD & HANDOFF）的已确认方法

### 11.1 完整规划不等于必须拆 PRD

产品规划必须完整，但 PRD 不一定拆分。

默认规则：

- 一份产品需求文档仍然清晰、可执行、可审查时，使用一份完整产品需求文档。
- 只有拆分能实质提高理解、执行、协作、验证或恢复质量时，才拆分。

典型拆分触发条件包括：

- 多团队或稳定的责任边界。
- 明确的模块或领域边界。
- 分阶段迭代或发布时间显著不同。
- 单稿严重影响阅读和审查。
- 子范围需要独立执行、验证或恢复。
- 不同用户、终端或场景差异显著。

### 11.2 拆分后的结构

如果拆分，必须形成：

```text
父产品规划运行（Parent Product Run）
      ↓
总 PRD
      ├── 子 PRD A
      ├── 子 PRD B
      └── 子 PRD C
```

总产品需求文档是正式的总需求叙事，不是独立的产品计划（Product Plan）。

总 PRD 至少承载：

- 完整背景和目标。
- 用户分群和需求分析。
- 现状、差距、问题和价值。
- 整体解决方案。
- 核心体验路径。
- 逻辑系统、模块和迭代结构。
- 拆分原因和拆分方式。
- 子 PRD 清单。
- 团队责任。
- 子稿关系、依赖和共享契约。
- 组合后的完整体验。
- 全系统验收。

每个子 PRD 必须包含来自同一来源的完整共享叙事，并补充：

- 本地范围和拆分类型。
- 对整体目标与价值的贡献。
- 与兄弟 PRD 的关系。
- 负责团队。
- 共享规则、契约和依赖。
- 本地验收和集成验收。

子 PRD 必须可以独立理解，不能只写“参见总稿”。

“总 PRD”是当前确认的对象含义，最终名称后续可以调整，但不能取消总叙事和全局整合责任。

### 11.3 横向与纵向拆分

横向拆分可以按模块、能力、领域、数据、系统或团队责任进行。它不一定单独创造完整用户价值，但必须能够独立实现和验证，并明确对最终价值的贡献。

纵向拆分可以按端到端用户结果、用户旅程阶段、场景、用户群、成熟度或发布阶段进行，理想情况下独立形成可观察结果。

可以形成横纵二维的切片图（Slice Map），但不能机械地为每个格子生成一份产品需求文档。人类产品经理可以补充团队分工、产能、先后顺序和协调现实。

### 11.4 产品需求文档模板（Template）

BPG 2.0 采用**一套自适应通用基础模板 + 条件式内容模块**，不再为紧凑版、标准版或不同产品类型分别维护互相竞争的固定正文模板。简单需求可以压缩表达，复杂需求可以展开或拆分，但都必须满足同一份 PRD 内容契约。

当前仓库中的 `general@0.2.0 / RELEASED_DEFAULT` 只作为旧运行时现状和覆盖清单参考，不直接继承为 BPG 2.0 的正文骨架。现有模板的有效检查项应转入内容契约、条件式模块或内部 Checklist，而不是继续要求人类阅读大量固定章节、空表和占位内容。

新通用模板分为四层：

1. **PRD 内容契约**：规定必须表达、条件式表达、禁止进入 PRD 以及应移交 Engineering SPEC、Test 或 Product Evals 的语义边界。
2. **自适应基础模板**：提供正式 PRD 的稳定阅读主线和章节结构。
3. **条件式内容模块库**：按产品形态、风险和实际需求调用流程、状态、权限、数据上报、多语言、地区适配、边缘场景、迁移、运营配套、Product Evals 等模块；不适用时不进入正文。
4. **Writing Profile 与 Renderer Profile**：分别控制跨格式写作与排版原则，以及 HTML、DOCX、PDF 等目标格式的具体呈现与导出保真。

正式 PRD 默认从“标题 + 产品概览（TL;DR）”开始，正文采用以下六个稳定一级章节：

1. **产品背景、目标与问题定义**。
2. **方案概述与需求范围**。
3. **核心体验与产品逻辑**。
4. **产品需求与业务规则**。
5. **验收标准与效果衡量**。
6. **风险、依赖与未决事项**。

这里的“产品逻辑”指用户可见或业务可观察的流程、状态、关系和规则，不指内部技术架构或实现机制。一级标题保持正式、稳定；二级标题优先采用能直接表达产品结论的具体名称，而不是继续堆叠抽象分类。

详细需求可以按需使用以下语义块，但不能强迫所有需求机械填写同一张表：需求 ID 与能力名称、一句话产品结果、参与者与触发条件、可观察行为、关键规则与分支恢复、产品状态与权限、产品约束、依赖以及验收引用。主 Agent 应根据关系选择短段落、表格或配图；字段只是思考与覆盖提示，不是固定的七行表单。

运行时状态、完整变更历史、完整证据矩阵、内部 Checklist 和机器治理信息不得进入正式 PRD 正文。它们分别保留在产品规划主记录、Candidate / Review 记录、Handoff Note 或 Machine Manifest 中；最终 PRD 只保留研发理解和实现产品需求所必需的产品结论。

### 11.5 产品评测（Product Evals）

产品评测不是独立主流程节点，而是产品需求文档的条件式附件。主 Agent 对每份 PRD Candidate 先进行一次轻量适用性判断；这项判断不等于生成 Eval Pack，也不增加人类确认步骤：

- `NOT_NEEDED`：普通确定性验收已经足够，不生成额外 Artifact，只保留简短理由。
- `RECOMMENDED`：增加产品评测有明显价值，由 Agent 根据收益、成本和当前信息决定是否生成；未生成时不默认阻断 Ready，但必须保留建议和理由。
- `REQUIRED`：普通验收不足以覆盖关键产品质量，Agent 自动调用 Evals Generator；缺少 Ground Truth、专业判断或其他权威输入时才询问 PM / Owner，并在完成独立规格 Review 前阻断 Ready。

项目模板和 Owner 仍可明确要求生成 Product Evals，但不再是唯一触发来源。适用性、案例、Rubric、覆盖与未知等语义判断由 Agent 完成，程序不得通过关键词、需求长度或固定字段自动决定。

`evals-generator` 采用“BPG 内置、架构可插拔”的原子能力边界：

- 主 Agent 负责 Product Evals 的适用性语义判断；BPG Core 只记录该判断及理由，并负责精确 PRD Candidate 绑定、版本、新鲜度、Review、Release Set 聚合和 Ready 规则的确定性执行。
- 内置 Evals 能力包负责 Agent 的 Eval Pack 生成、修订方法和独立评测规格 Reviewer；首期随 BPG 安装，但保持独立能力版本和兼容声明，可由满足同一合同的项目能力或其他 Agent Provider 替换。
- 它不提供独立公开命令、顶层 Graph 节点、独立 Product Run 或第二套状态系统。
- Product Evals 规格与对应 PRD 绑定为同一个 PRD Release Set Candidate；评测规格由独立 Reviewer 审查，并与其他 PRD Review 结果聚合形成整套 Candidate 的结论。
- Test Graph 或其他获授权执行方继续负责环境、数据、实际执行、execution receipt 和最终测试 verdict；BPG 只生成与审查评测规格，不得把 `NOT_RUN` 表达成已测试或通过。

如果内置生成能力不可用，`NOT_NEEDED` 路径正常运行；`RECOMMENDED` 保留明确状态但不默认阻断；`REQUIRED` 可以继续形成 PRD Candidate，但不能进入 Ready，直到 Agent、PM 或兼容 Provider 依据同一合同补齐并完成独立 Review。

### 11.6 可交接就绪（Ready）与交接（Handoff）

第 11.6 节是 BPG 2.0 唯一的 Ready 合同。其他章节和图示中的“PASS → 自动 Ready”都只是对本节的引用，不得各自复制、删减或另建第二套 Ready 规则。

只有同一个精确 PRD Release Set Candidate 同时满足以下条件，Controller 才能自动提交 Ready：

1. 完整 PRD Release Set 已获得正式 `PASS`，且该 Verdict 与当前 Candidate 精确绑定、没有过期。
2. 不存在未解决的 Blocker、Major、`NEEDS_OWNER` 或尚未处置的重大 Reviewer 分歧。
3. 本次适用且被定义为必需的正式交付物、条件式附件和专业 Review 已经存在，版本匹配，并包含在同一个 Release Set 中。
4. Product Evals 为 `REQUIRED` 时，Eval Pack 已补齐、与当前 PRD Candidate 绑定并完成独立规格 Review；`RECOMMENDED` 未生成时保留真实状态和理由，但不默认阻断。
5. Markdown、assets、默认 HTML 阅读视图及本次实际交付的其他派生格式来自同一编辑真源，文件清单、版本和引用当前有效。
6. 当前 Candidate、接受的 Decision、产品规划主记录快照、Review Result 和必要附件之间不存在陈旧、缺失、被替换或无法解析的依赖。

其中内容质量、Finding 处置是否成立、专业能力是否适用以及附件是否语义充分由 Agent 和 Reviewer 判断；Controller 只验证已经提交的正式 Verdict、状态、版本、文件清单、引用、新鲜度和合法迁移，不通过字段完整度重新评审产品质量。

可交接就绪后只生成本地交接，绑定精确产品需求文档或文档组合、版本、关系和必要附件。它不代表研发完成、测试通过、发布或外部接收。

### 11.7 已确认的阶段五运行规则

1. **以完整 PRD Release Set 为原子审查对象。** 无论交付物是一份 PRD，还是“总 PRD + 多份子 PRD”，正式 PRD Review 和 Ready 都绑定同一个精确、不可变的 PRD Release Set Candidate。存在多份文档时，可以在同一轮中并行执行子文档或专业审查，但必须聚合检查跨文档的一致性、覆盖和组合运行能力，并对整套 Candidate 形成一个正式结论，不能只依靠每份文档各自通过。
2. **满足唯一 Ready 合同后自动 Ready。** 当精确 PRD Release Set Candidate 满足第 11.6 节全部条件时，由 Controller 自动提交 Ready 状态，不增加一次形式化的人类确认；单独一个 `PASS` 不得绕过必需附件、新鲜度或 Product Evals 条件。
3. **规划复盘必须执行但不阻塞交接。** Local Handoff 完成后，主 Agent 对本次规划过程、有效做法、认知错误、遗漏、返工原因和可复用改进进行复盘。复盘不能修改已经冻结和交接的 PRD；需要改变产品需求时，必须形成新的 Signal、主记录变更和 PRD Candidate。复盘可以更新项目内的方法路由、检查项或 Playbook；核心框架只能形成改进提案，不能由单次运行自动改写。

### 11.8 PRD 的责任定义与内容契约

PRD 正式定义为**产品行为与验收契约**：回答产品为什么做、为谁做、做什么、应该如何表现、必须遵守哪些产品约束，以及什么产品结果表明需求得到满足；PRD 不规定内部技术实现机制。

产品交付信息采用四层责任边界：

| 层级 | 核心责任 |
|---|---|
| 产品规划主记录 | 保存完整背景、证据、用户分析、问题诊断、价值判断、方案比较和决策来源，回答“为什么这样判断” |
| PRD | 定义产品目标、范围、体验、可观察行为、业务规则、产品状态、权限、异常、产品约束和验收结果，回答“产品必须成为什么样” |
| 工程规格说明（Engineering SPEC） | 定义技术架构、内部接口、数据存储、算法、代码结构、并发、部署和其他实现机制，回答“系统如何实现” |
| 测试与产品评测（Test / Product Evals） | 定义独立验证方法、测试用例、评测对象、执行过程和实际结果，回答“如何证明它满足要求” |

四层之间允许精确引用，但不能混淆责任：PRD 可以定义验收结果和产品级约束，不能据此展开完整测试用例或技术施工方案。

在具体 PRD 模板之上建立稳定的 **PRD 内容契约（PRD Content Contract）**，用于定义：

- PRD 必须包含的语义。
- 按产品和场景适用的条件式语义。
- 禁止写入 PRD 的内部实现内容。
- 必须转交 Engineering SPEC、Test 或 Product Evals 的内容。
- PRD 达到完整、可理解、可执行和可验收所需的最低标准。

模板只负责辅助思考和表达，包括信息顺序、章节结构、紧凑或标准表达、图表选择和项目专属呈现；模板不能改变 PRD 的责任边界，也不能成为产品分析的替代品。实际模板文件将在迭代一依据已经确认的 PRD 内容契约重建：把偏技术的提示改写为产品行为或产品约束、改为条件式内容，或明确移交 Engineering SPEC。

### 11.9 验收标准、测试用例与 Product Evals 的边界

1. **PRD 必须定义验收标准，但不编写测试步骤。** 验收标准只描述适用的产品条件、用户或其他参与者可观察的产品结果，以及必要的产品边界或最低门槛；不得展开测试步骤、测试数据、执行环境、初始化与清理方式或内部技术断言。
2. **完整测试用例不属于 PRD。** 一个验收标准可以派生多个正常、边界、异常、兼容和回归测试用例。需要完整测试设计时，后续形成独立的 Test Design Artifact；PRD 只保留产品级验收边界和精确引用。
3. **Product Evals 只处理普通确定性验收无法充分覆盖的复杂产品质量。** 例如语义忠实度、推荐价值、生成质量、可用性或其他需要代表性样本、评价维度、评分规则和门槛的质量。主 Agent 按 11.5 的 Agent-first 规则先做轻量适用性判断；项目模板和 Owner 可以明确要求生成，但不是唯一触发来源。Eval Pack 定义如何评价，不代表评测已经执行或产品已经通过。
4. **不默认使用 Given / When / Then。** 只有复杂条件、状态转换或时序关系容易产生实质歧义，并且该表达能明显减少歧义时才使用；不能把它作为所有需求的固定格式，进而机械生成大量测试用例式验收标准。

验收标准的稳定判断是：当测试方法、测试数据或技术实现变化，而产品应有的行为和结果没有变化时，验收标准仍应成立。详细产品行为优先维护在需求、规则、状态或权限定义中，验收标准负责绑定关键接受边界和追溯关系，不重复抄写全部需求正文。

### 11.10 PRD 内容展示与“不适用”规则

PRD 内容契约必须区分“Agent 必须思考”和“最终 PRD 必须展示”。完整性不能依赖在正文中保留所有模板章节；Agent 在主记录和 Review 中完成适用性检查，PRD 只呈现对当前读者、需求理解、执行和验收有意义的内容。

所有 PRD 必须覆盖以下八类核心语义，但不强制形成八个固定物理章节，也不要求重复已经存在的唯一正文来源：

1. 本次增量、当前范围、非目标及与完整产品或其他 PRD 的关系。
2. 理解需求所必需的目标对象、场景、需求、问题、目标、价值和关键方案理由。
3. 目标体验、核心能力和整体解决方案如何运行。
4. 当前迭代、完整目标系统及跨文档或模块边界。
5. 产品需求以及参与者可观察的产品行为。
6. 适用的业务规则、状态、权限、产品层数据语义和共享契约。
7. 产品级验收标准、成功指标和 Guardrails。
8. 影响当前交付的重大风险、依赖、假设、未知和待决定事项。

详细用户旅程、复杂流程或系统图、状态机、权限矩阵、公开产品接口、产品级非功能要求、数据分析、兼容迁移、灰度回滚、多语言、无障碍、原型、实验、Product Evals、运营配套及父子 PRD 关系等内容，只在适用时进入 PRD。内部技术实现、完整测试用例、原始研究材料、完整方案分析、会议或聊天记录、研发任务与排期、机器治理细节和虚假执行状态不得进入 PRD 正文。

**“不适用”的统一规则如下：**

- 除必填 Checklist 外，条件式内容不适用时，直接删除对应标题、空表、占位和“不适用”说明，不占用人类阅读空间。
- 必填 Checklist 必须保留每个检查项；不适用时明确标记“不适用”，并按 Checklist 契约提供必要理由或依据，从而证明该事项已经被检查，而不是被遗漏。
- 高风险适用性判断应当被必填 Checklist 覆盖；其审计理由保留在 Checklist、主记录或独立 Review 证据中，无需在 PRD 正文重复。
- 模板不得为了展示完整而强迫 Agent 生成空章节、空表或重复的“不适用”段落。

### 11.11 PRD 的阅读结构与信息组织

PRD 必须支持三种阅读方式：

1. **TL;DR（快速总览）**：帮助读者快速理解目标对象与问题、本次产品结果、选定方案、范围与非目标、核心体验或流程、成功判断及最关键风险或未决问题。
2. **完整产品叙事**：按照人类理解产品的顺序组织本次增量、背景与目标对象、问题与价值、解决方案与目标体验、范围与边界、核心流程与产品结构、功能与规则、验收与指标、风险与未决事项；不能照搬 Agent 的内部规划步骤和循环历史。
3. **按需详细需求**：优先按用户任务、产品能力或稳定业务模块组织，必要时结合团队责任；不默认按前端、后台、数据库、API 或技术服务组织。

三层是信息能力，不是固定物理模板。简单 PRD 可以合并为紧凑表达，复杂 PRD 可以展开，但不能因合并丢失适用的必要语义。TL;DR 是正文唯一来源的派生视图，详细需求是正文的展开；摘要、主叙事和详细需求不得形成互相竞争的三套结论。

正式提交给研发的 PRD 本体必须保持干净。TL;DR 只呈现产品结论；Candidate 版本、Review 状态、Run 状态、下一执行动作、哈希、Exact refs、完整变更历史，以及其他机器治理信息，不得作为 metadata 区、状态条、侧边栏或可见 sidecar 内容放在 PRD 顶部。它们按照 11.12 的既定边界分别由 Controller、Machine Manifest、Review 记录和 Handoff Note 承载。

### 11.12 干净 PRD 与独立交接包

1. **通用 PRD 默认从“标题 + TL;DR”直接开始。** PRD 本体只承载产品需求和必要产品结论，不显示运行时 metadata、状态条或机器治理信息。
2. **精确身份由 Controller 与 Machine Manifest 保存。** Run、Candidate、文件清单、版本、哈希、Review Result、Ready 依据、模板和附件引用属于机器可验证的交接合同，不进入 PRD 正文。
3. **人类交接信息进入独立 Handoff Note。** Handoff Note 只提供本次文档清单、总稿与子稿关系、阅读顺序、当前交付版本、仍需处理的未决事项和合理下一动作，不复制产品需求和完整运行历史。
4. **PRD 正文默认不显示文档版本信息。** 版本通过交接包、文件身份、Machine Manifest 和 Controller 状态绑定；只有项目专属模板因组织制度或真实协作需要明确要求时，才在 PRD 内增加最小的人类可见文档标识。

Local Handoff Package 按适用性包含 Markdown 与 assets 编辑真源、默认 HTML 阅读视图、Handoff Note 和 Machine Manifest；DOCX、PDF 及其他目标格式按实际协作和分发需要生成。完整变更历史继续保留在产品规划主记录、Candidate 历史、Review Findings 和 Controller 记录中；当前版本变化只有确实影响研发理解时，才在 Handoff Note 中简要说明。

### 11.13 PRD 的通用文字表达规则

1. **采用低疲劳表达。** 结论先行，一句话只承担一个主要意思，一段只讨论一个主题，明确行为主体，优先使用短句和主动表达，删除不产生新信息的重复总结，不以术语堆叠制造专业感。
2. **消除模糊产品语言。** “及时、合理、适当、友好、智能、高效、尽快、大量、必要时、异常情况下、提升体验、保证稳定”等词语不能独立构成需求；必须说明参与者、适用条件、产品行为、可观察结果和不可突破的产品边界。
3. **稳定标题负责导航，正文负责结论先行。** 可以保留便于扫描的稳定章节名称，但每节开头先给出该节最重要的产品结论，再展开解释和细节。
4. **按关系选择表达形式。** 背景、因果和决策理由使用短段落；并列要点使用列表；精确比较和映射使用表格；流程、状态、关系和复杂边界使用图；大型证据和完整矩阵进入附件。不能把所有内容都写成表格，也不能用图、表和列表重复表达同一关系。
5. **只给需要追溯的内容稳定 ID。** 目标、范围、关键需求、产品规则、状态或共享契约、验收标准、风险、假设、未知和父子 PRD 关系在需要跨章节或跨产物精确引用时使用 ID；普通解释和不会被引用的段落不编号。
6. **复杂抽象规则按需配例子。** 容易误解的规则提供一个典型例子；容易产生错误推断时再提供一个反例。例子不能替代正式规则，也不能扩张成完整测试用例。
7. **明确区分事实、决定与未知。** 已确认事实、当前产品决定、待验证假设、未知、待 Owner 决定和已排除范围在可能影响理解或行动时必须明确，不能把“预计、可能、倾向于”写成已确认要求。
8. **冻结 Candidate 前必须执行文档体验整理。** 主 Agent 删除重复和模板废话、前置关键结论、缩短句段、合并碎片章节、选择合适图表、移动非主线细节、统一术语与状态、校验 TL;DR 与正文，并确保零前置上下文读者不需要查看聊天记录。

此外确认以下表达与阅读预算：

- 产品概览（TL;DR）以约 400 个中文字符以内为目标；主阅读路径以约 3,000—4,000 个中文字符为目标。这是写作预算，不是机械截断规则。
- 核心正文超过约 6,000 个中文字符，或预计需要连续阅读超过 10 分钟时，主 Agent 必须评估是否无损拆分为总 PRD、子 PRD 或被精确引用的独立 Artifact。触发评估不等于强制拆分，也不能单独构成质量失败；若保持单份文档更有利于完整叙事，可以记录理由后保留。
- 任何拆分都不能通过删减必要产品语义满足长度要求；总 PRD 必须保留完整背景、目标、需求分析、整体方案、共享契约和子稿关系，保证全局叙事仍然完整。
- 避免很长的同级 Bullet List；长列表必须分组、转成更合适的表格或图示，或者按产品边界拆分。长段落必须拆分，不同段落之间保留空行。
- 配图是降低理解成本的重要手段。复杂流程、分支与恢复、状态迁移、多模块关系、责任边界或其他难以靠短文字快速理解的关系，应优先使用真正解释问题的图，而不是装饰性图片。

PRD 写作规范不能只规定遣词、句段和叙事方式，还必须包含独立的排版规则，覆盖标题层级、段落留白、列表长度与嵌套、表格适用性、图片位置与尺寸、图注、信息密度和不同内容形态之间的视觉节奏。表达风格与排版共同构成 PRD 文档体验规范；具体格式相关的字号、页边距、CSS、分页和导出保真规则，应由对应 Renderer Profile 承担，避免把 Markdown、HTML 和 DOCX 的实现细节混入通用写作规则。

### 11.14 PRD 的编辑真源与多格式交付

1. **Markdown 与 assets 是唯一可编辑真源。** 每份 PRD 以 Markdown 正文和本地图片、图表等 assets 组成一个完整发布单元。所有正式内容修改必须先回到这套真源，不能同时维护多份可编辑正文。
2. **自包含单文件 HTML 是默认人类阅读视图。** HTML 从精确绑定的 Markdown 与 assets 派生，负责提供更好的版式、图片呈现、导航和低疲劳阅读体验。发布用 HTML 应自包含，不依赖外部资源；它是默认阅读格式，不是新的内容真源。
3. **DOCX 是条件式导出适配器（Export Adapter）。** 只有目标组织、协作工具或正式分发流程确实需要 Word 文档时才生成 DOCX，不把 DOCX 作为每次运行的固定必产物或主要编辑载体。
4. **PDF 是条件式只读输出。** 只有归档、签审、打印或固定版式分发等场景需要时才生成 PDF；PDF 不承担协作编辑责任。
5. **所有阅读和分发格式从同一真源派生。** HTML、DOCX 和 PDF 应分别从同一个精确 Markdown、assets 及统一文档模型生成，而不是把 HTML 再转换成 DOCX，或让不同格式形成各自独立的产品结论。
6. **派生格式不得反向成为事实来源。** 如果人类在 HTML、DOCX 或 PDF 上提出修改，主 Agent 必须把有效变更合并回 Markdown 与 assets，形成新的 Candidate，重新完成适用的 Review，再统一生成所有目标格式。不得直接修改派生文件后继续交接。
7. **Review 同时检查语义真源和真实阅读体验。** PRD Review 必须审查精确绑定的 Markdown 与 assets，保证产品语义、边界和验收契约正确；同时检查默认 HTML 阅读视图的排版、图片、导航和内容一致性。若 DOCX 实际进入本次 Handoff，还必须对渲染后的 DOCX 进行视觉和保真检查，至少覆盖图片、表格、字体、分页和内容完整性；“成功导出文件”本身不等于通过审查。

配图采用以下格式与验证规则：

- 复杂图的可编辑源文件优先使用自包含 HTML/CSS，并与对应 PRD Candidate 精确绑定。
- Markdown、DOCX 及其他需要稳定嵌入的正式交付默认使用从源文件导出的 2x 或 3x 高清 PNG。
- SVG 不是默认交付格式；只在图形简单且目标阅读环境已经确认兼容时使用。
- 自包含 HTML 阅读视图可以直接使用 HTML/CSS 图形，不要求先转成 SVG。
- 图形 Review 以最终进入实际阅读或分发格式的渲染结果为准，检查中文、尺寸、裁切、重叠、关系可追踪性和跨格式保真；源文件可打开或成功导出本身不等于验证通过。

写作规范负责跨格式稳定的内容、表达与排版原则；各 Renderer Profile 和 Export Adapter 负责 HTML、DOCX、PDF 的格式实现与保真规则。格式能力不得反向迫使 PRD 改写成适合某一种工具的内容结构。

### 11.15 PRD Review 的位置与审查对象

正式 PRD Review 是 PRD Release Set Candidate 冻结后的独立 Graph 节点。它在五阶段的宏观划分上属于阶段五，但不能与主 Agent 的 PRD 编写动作合并为同一个作者上下文。主 Agent 在冻结前完成自检、全局一致性检查和文档体验整理；正式 Verdict 必须由独立 Reviewer Agent 对只读 Candidate 作出。

正式流程为：

```text
PRD 编写与内部整理
→ 冻结 PRD Release Set Candidate
→ 独立 PRD Review
→ 修订、Owner 处理或返回最早受影响阶段
→ PASS
→ 自动 Ready
```

#### 11.15.1 原子审查对象

PRD Review 的原子对象是完整 PRD Release Set，而不是某一个 Markdown 文件。它按本次交付的实际组成绑定：

- 单份 PRD，或总 PRD 与全部子 PRD。
- Markdown、图片和其他编辑真源。
- 默认 HTML 阅读视图，以及本次实际交付的其他派生格式。
- 被 PRD 精确引用且会影响需求理解、执行或验收的条件式附件。
- 本次实际包含的 Product Evals、数据采集需求表、语言与地区适配矩阵或其他专项产物。

存在多份文档或专业审查时，可以并行检查局部对象，但最终 Verdict 必须针对同一个精确 Release Set 聚合，不能用“每份文档分别通过”替代跨文档一致性、覆盖关系和组合运行能力的整体结论。

#### 11.15.2 只读验证基线

Reviewer 除读取正式交付 Candidate 外，还必须获得足以验证需求忠实度的精确只读基线，包括：

- 当前已接受的《产品规划主记录》快照。
- 已通过的 Decision Candidate 及 Agent 自动决策或 Owner Choice。
- 当前 PRD 内容契约、项目模板和必填 Checklist。
- PRD 精确引用的证据与逻辑 Artifact。

这些材料是审查依据，不是最终交付物本身。Reviewer 不读取隐藏推理，不需要复制完整聊天记录或无关原始材料；缺少会实质影响判断的依据时，应形成明确 Finding，而不是自行补造背景。

#### 11.15.3 问题回流原则

- 表达不清、内容遗漏或 PRD 内部矛盾，返回阶段五，由主 Agent 修订并冻结新 Candidate。
- 产品范围、模块关系、核心流程或系统规划不完整，返回阶段四。
- 用户、目标、问题、价值或解决方案本身存在实质错误，返回最早受影响的阶段，并重新经过适用的 Review 或决策。
- 涉及重大风险承担、取舍权、资源承诺或授权缺失，结果为 `NEEDS_OWNER`。

Reviewer 不得为了让 PRD 通过而在文档中替上游问题打补丁，也不替主 Agent 改稿或替 Owner 决策。

#### 11.15.4 Agent 优先与程序化边界

以上规则不增加一个负责判断产品质量的新程序模块，也不要求程序读取文本后判断完整性、正确性或可读性。主 Agent 和独立 Reviewer Agent 继续完成全部语义工作，包括审查对象选择、专业 Reviewer 适用性判断、Finding、回流阶段建议和修订。

程序化脚手架只承担具有不可替代确定性价值的薄控制：冻结和绑定精确 Candidate、验证 Release Set 与只读基线引用、区分作者与 Reviewer 尝试、记录审查轮次和 Verdict、限制合法状态转换，并在条件满足时自动提交 Ready。专业 Reviewer 的选择、Finding 严重程度、产品问题归因和内容修改不得由程序通过关键词、固定评分或 Schema 完整度代替 Agent 判断。

这些能力原则上复用现有 Candidate、Review、Controller 和 Ready 机制，不新增顶层业务节点。当前运行时是否完全具备 Release Set、HTML 阅读视图和验证基线的精确绑定能力，需要在实现阶段核对；若存在缺口，只补充最小确定性绑定，不扩张为新的语义引擎或复杂运行时。

### 11.16 PRD Reviewer Panel 与可信审查协议

PRD Review 不再使用一个扁平的“七个审查维度”列表，而是由三层结构组成：必须覆盖的基础 Reviewer 责任、按产品形态和风险调用的专业 Reviewer，以及所有 Reviewer 共同遵守的可信审查协议。

#### 11.16.1 六类基础 Reviewer 责任

每次正式 PRD Review 必须覆盖以下六类逻辑责任，但不等于必须固定启动六个子 Agent：

1. **产品目标与需求 Reviewer**：检查目标用户、问题、价值、目标结果、范围与非目标、优先级、已接受决策、Guardrails 和需求追溯关系；识别范围漂移、未来内容偷渡以及把未知写成事实。
2. **用户体验与内容 Reviewer**：检查端到端体验、入口与出口、主路径、分支、空状态、加载、错误、中断、恢复、反馈、产品文案、认知负担和基本可用性。
3. **产品系统一致性 Reviewer**：检查核心流程、模块、角色、对象、状态、权限、产品数据语义、共享规则、依赖以及父子 PRD 是否能够组合运行。它只审查逻辑产品系统，不把 PRD 扩写成代码或技术架构说明。
4. **工程可行性 Reviewer**：检查明显不可实现之处、与已知架构或依赖的冲突，以及性能、容量、兼容、迁移、灰度、回滚和可观测性对产品行为形成的约束；同时阻止 PRD 越界规定内部实现。它不编写 Engineering SPEC，也不替研发承诺工期。
5. **可验收性与 Product Evals Reviewer**：检查产品行为是否可观察、验收条件是否位于产品层，重要边界、错误、权限、恢复和可观测性是否足以验证，并判断何时仅靠确定性验收条件不足、需要 Product Evals。它不编写完整测试用例，也不执行测试。
6. **文档体验 Reviewer**：检查 TL;DR、信息层级、阅读顺序、长度、段落、列表、表格、配图、术语一致性、信息可定位性、干净 PRD 以及默认 HTML 阅读视图；本次实际交付 DOCX 时再检查其渲染保真。它不得为了改善表达而发明缺失的产品要求，实质缺口必须路由给对应 Reviewer 或返回上游。

简单、低风险 PRD 可以让较少的独立 Reviewer Agent 分别承担多个角色画像，但每类责任的 Findings 和结论仍须可区分。标准或复杂 PRD 应根据认知负担和风险拆开角色。主 Agent 是作者，不能同时作为正式 Reviewer。

#### 11.16.2 条件式专业 Reviewer

专业 Reviewer 只在产品形态、目标用户、数据、地域或风险特征确实触发时调用，包括但不限于：

- 安全与滥用。
- 隐私与数据治理。
- 法律与合规。
- 无障碍。
- 语言精确性、产品文案表达和地区文化。
- 可靠性、性能与容量。
- 数据分析与上报。
- AI 行为与 Product Evals。
- 特定业务领域专家。
- 发布与运营准备。

是否调用由 Agent 根据证据、产品类型和风险语义判断，不能把所有专业 Reviewer 机械地塞进每次 Review，也不能由程序仅靠关键词自动决定。

#### 11.16.3 共同可信审查协议

Reviewer Panel 共同遵守以下协议：

1. **冻结承诺基线**：从已经接受的 Decision、产品规划主记录、范围、非目标、Guardrails 和 PRD Candidate 中构造同一份只读审查基线，不重复要求 Owner 确认已经确认的承诺。
2. **同一 Candidate、先独立审查**：所有 Reviewer 绑定同一个冻结 Candidate 与基线。首轮 Reviewer 不能先读取其他 Reviewer 的结论，避免相互锚定。
3. **Finding 必须可验证**：至少包含 Reviewer 角色、具体问题、精确证据或引用、影响、置信度及依据、受影响范围、建议、应返回的修复层级和当前处置状态。
4. **交叉验证而非简单汇总**：主 Agent 将 Findings 区分为多方确认、互补、冲突、独有和证据不足。证据不足的意见只能保留为待验证线索或证据缺口，不能直接变成修订命令。
5. **保留分歧，不按多数投票**：Reviewer 冲突必须进入分歧记录。判断优先考虑直接、当前、可复现、涉及明确用户承诺或关键路径的证据，而不是票数。
6. **有条件重复独立审查**：只有高影响结论、证据含糊、跨角色冲突、弱证据下的“无问题”结论，或单一 Reviewer 提出的重大 Finding，才追加独立复核；不要求每个 Finding 都双重审查。
7. **Review-of-Review 有界运行**：最多两轮，只处理高影响 Finding 的证据、冲突和范围，不重新运行完整 Panel，也不形成无限讨论。
8. **修订后做差异复查与整体回归**：新 Candidate 既要复查实际改动和原 Finding，也必须检查目标、范围、Guardrails、端到端体验、共享契约与验收等全局不变量。Finding 不能因为局部文字已经修改就关闭；只有局部问题得到解决且没有破坏整体，才能判定修复成立。
9. **证据强度保持可见**：`PASS` 不能把缺失、陈旧、间接、单一来源或不可复现的证据伪装成已证实事实。它们必须作为剩余风险、未知或条件留在正式结论中。

Reviewer Findings 是形成 `PASS / REVISE / NEEDS_OWNER` 的输入；正式 Verdict 仍绑定完整 PRD Release Set。Reviewer 不替作者修改，不替 Owner 决策，也不直接提交状态。

#### 11.16.4 Finding 分级、处置与修订回归

Finding 不使用百分制、字母评级或加权总分，只按产品影响分为三类：

- **阻断级（Blocker）**：不解决就会使核心目标、已接受决策、核心用户任务、产品系统完整性、关键验收或重大安全与合规边界无法成立。
- **重要级（Major）**：会显著影响用户体验、产品完整性或研发正确理解，原则上必须修复。只有提供充分证据证明影响有限并完成降级，或者由有权角色明确接受相应限制，才能保留。
- **改进级（Improvement）**：不影响产品成立、正确理解和验收的局部改善，不阻断 `PASS`。

影响级别与证据强度必须分开记录。证据强度只使用“已证实 / 有力支持 / 待验证”等语义说明；潜在影响很大但证据不足的 Finding 应进入补充验证、风险控制或 Owner 路由，不能直接变成无依据的修订命令，也不能因为尚未证实就被删除。

正式 Verdict 根据下一步行动和权限决定：

- `PASS`：不存在未解决的 Blocker、Major 或 Owner 决策；允许保留非阻断改进项和已明确披露的剩余未知。
- `REVISE`：存在主 Agent 可以在既定授权和产品方向内修复的问题。
- `NEEDS_OWNER`：需要价值取舍、风险接受、目标变化、资源承诺或其他 Agent 无权完成的决定。它表示决策权归属，不代表比 `REVISE` 更严重。

相同底层问题、影响范围和修复位置的 Findings 可以聚合，但必须保留全部 Reviewer 和证据来源。措辞相似但成因、影响或修复目标不同的问题不得强行合并。每条正式 Finding 至少记录稳定编号、Reviewer 责任、问题与精确证据、影响级别、证据强度、影响范围、应返回的阶段或模块、建议方向和处置结果。

处置结果限定为：已修复；不成立并给出反证；已降级为非阻断问题；已接受限制；需要 Owner；或因上游变化而失效。Reviewer 的建议不是修改命令；主 Agent 可以依据证据拒绝或调整建议，但必须保留处置理由。

自动修订最多两轮，含义是主 Agent 最多基于正式 Review 生成两个新的 Candidate：

```text
初审 Candidate 1
  → 修订轮 1 → Candidate 2 → 差异复查与整体回归
  → 修订轮 2 → Candidate 3 → 最终复查
```

Reviewer 之间的交叉验证和有界 Review-of-Review 属于同一审查周期，不产生新 Candidate，也不占用修订轮次。第二轮后仍存在实质问题时，不进行第三轮自动修补：需要人类取舍则转 `NEEDS_OWNER`；证据不足则返回调研或等待；属于上游规划错误则返回最早受影响阶段；只有非阻断改进项时才允许 `PASS` 并保留记录。返回阶段一至阶段四并发生实质重规划后，未来形成的是新的 PRD Candidate 和新的 Review 周期，不视为第三轮局部修订。

每次修复都必须遵守“局部修复不得破坏整体”的硬规则：

1. **修复前确定影响包络**：主 Agent 先识别该 Finding 可能影响的目标、用户需求、范围、流程、模块、对象、状态、权限、共享规则、上下游依赖、父子 PRD、验收条件、指标和 Guardrails。
2. **回到事实来源修复**：问题源于产品规划主记录、上游决策或共享契约时，必须先修复源头，再重新生成所有受影响的 PRD 内容；不得只在某份子 PRD 中打补丁。
3. **局部验证**：确认原 Finding 的机制和影响已经消除，而不只是替换了措辞。
4. **整体回归**：检查端到端用户目标仍可完成，范围与非目标没有漂移，各模块输入输出能够衔接，对象、状态、权限、术语与共享规则保持一致，父子 PRD 仍能组合运行，验收、指标和 Guardrails 没有互相冲突。
5. **回归失败不得关闭 Finding**：局部问题虽然消失，但产生新的冲突、缺口、风险或下游失效时，应标记为修复回归，形成新的 Finding 或返回整体规划循环，不能宣称已修复。

所有修订都生成不可变的新 Candidate。全局回归的深度按变更影响范围调整，但检查本身不能省略；纯局部文案修正可以采用紧凑检查，涉及范围、流程、状态、权限、共享契约或父子 PRD 的修改必须由产品系统一致性 Reviewer 参与差异复查。语义影响分析和修复判断由 Agent 完成，Controller 只绑定 Candidate、Finding、修订轮次和合法 Verdict。

Review Findings 作为独立审查记录保存，PRD 正文不附带完整审查日志，只吸收确认后的修订结果以及会影响研发理解、验收或风险承担的剩余限制。

#### 11.16.5 明确不吸收的重型审计机制

BPG 吸收 Product Goal-Based Audit 中的目标承诺冻结、独立审查、证据化 Finding、交叉验证、分歧保留和有界 Review-of-Review，但不把完整审计流水线复制进 PRD Review。

默认不引入重复 Owner 承诺确认、固定七阶段审计、脚本化审查、覆盖率目标、百分制或字母评分、加权总分、每份 PRD 独立审计目录、所有 Finding 强制双审、尚无实现时的代码与部署审计，以及超过两轮的修订循环。这些机制只有在未来形成不同任务目标时另行设计，不能让常规 PRD Review 变成审计项目。

以上能力不增加新的顶层 Graph 节点或语义程序。Agent 负责选择适用 Reviewer、理解 Findings、交叉验证并提出修订；Controller 只负责精确绑定作者与 Reviewer 尝试、Candidate、审查完整性、轮次、Verdict、陈旧失效和合法状态转换。

## 12. 工作产物（Artifact）总原则

### 12.1 已确认原则

- 必要的内部工作必须留下足以支持判断、审查、追溯和交接的工作产物。
- 工作产物不是为了堆文档；每个工作产物必须服务于一个明确的认知、决策、协作或验证目的。
- Artifact 是可以独立识别、检查和审查的语义单元，不等于一个物理文件。
- 内部规划 Artifact 默认写入同一个 Product Run 的《产品规划主记录》，作为结构清楚、边界明确的章节；不默认按阶段或 Artifact 拆成多个文件。
- 相关工作产物应被产品需求文档吸收，或由产品需求文档精确引用。
- 五阶段压缩不能成为删除必要工作产物的理由。

以下内容不能因为“合并工作产物”而失去区别：

- 目标与价值。
- 用户需求与解决方案。
- 当前用户旅程与未来用户旅程。
- 问题诊断与方案推荐。
- 逻辑产品系统结构与工程规格说明。
- 全局系统视图与单模块详细需求。

### 12.2 产品规划主记录（Product Planning Record）

每个 Product Run 默认维护一份当前《产品规划主记录》，作为该 Run 当前已接受事实、分析、未知、结论、产品决策和规划关系的统一语义真源。

产品规划主记录至少按阶段持续组织：

```text
产品规划主记录
├── UNDERSTAND
├── DIAGNOSE & VALUE
├── DISCOVER SOLUTIONS & DECIDE
├── PLAN THE PRODUCT SYSTEM
└── 当前决策、未决问题、Artifact 与正式交付物索引
```

必须遵守：

- 同一事实、假设、结论或决策只在一个当前章节中维护，不在多个阶段文件中重复形成竞争真源。
- 每个逻辑 Artifact 仍需有稳定标题、明确边界、最低内容和适用性状态，以便独立检查和 Review。
- 上游认知变化时，在同一主记录中更新受影响章节和下游关系；不能只修改局部结论而留下互相矛盾的叙事。
- 主记录保存经过分析后当前接受的事实与结论，并精确引用原始来源；它不是所有原始数据、访谈全文和外部材料的物理仓库。
- PRD 是从主记录生成的正式需求投影，不建立另一套独立的背景、问题、价值和决策推理真源。
- 总 PRD、子 PRD 或实验型 PRD 获得正式版本后，若主记录发生会改变需求的实质变化，必须生成新的 PRD Candidate 或版本，不能静默造成不一致。

### 12.3 人机互动中的决策与变更记录

在阶段一至阶段三，以及后续任何会改变产品规划的实质讨论中，主 Agent 必须把与人类 PM / Owner 已经明确形成的决策持续写入同一份《产品规划主记录》。这是一项贯穿运行的内部动作，不等到阶段结束后凭记忆补写，也不要求人类 PM 手工整理会议纪要。

必须区分三类语义：

- **PM 认知输入与工作决策**：对背景、目标、用户、分群、需求、问题、价值、方案、约束、优先级和研究范围的补充、纠正、确认、暂定、拒绝或延后。它们会改变主记录中的产品认知，但不自动形成正式 Graph 路线。
- **Agent 授权范围内的正式规划决策**：Decision Review PASS 后，Agent 在项目预授权、低风险、可逆、无重大未知且只继续本地规划的范围内自动提交 `COMMIT NOW`。必须记录授权来源和决策来源，不能伪装成人类 Owner Choice。
- **Owner 正式决策**：超出 Agent 授权范围，或涉及目标、价值权重、风险承担、资源承诺和其他必须由人类负责的事项时，由 Owner 绑定当前 Decision Candidate 作出明确选择。

阶段一至阶段三至少记录：

| 阶段 | 必须记录的典型互动决策 |
|---|---|
| UNDERSTAND | 规划范围、目标与目标权、用户分群依据、用户权重、需求优先级、内部背景修正、未知项跳过与风险接受 |
| DIAGNOSE & VALUE | H1 / H2 / H3 取舍、核心问题选择、因果判断修正、价值权重、成功标准、Guardrails、证据不足的处置和重新打开条件 |
| DISCOVER SOLUTIONS & DECIDE | 方案原则、内部约束、被排除的方向及原因、关键 Trade-off、Review Finding 处置、Agent 推荐、Agent 自动决策或 Owner Choice、授权来源、接受风险和改判条件 |

每条有实质影响的决策记录至少包含：

- 决策主题和所属阶段。
- 当前状态：已确认、暂定、待决定、延后、已否决或已被取代。
- 明确结论。
- 主要理由和证据。
- 被放弃的主要替代方向及原因；没有实质替代时无需凑数。
- 对目标、用户、问题、方案、范围、风险或后续阶段的影响。
- 作出输入或承担责任的角色和决策来源：PM、Agent 在授权范围内自动决定、Owner，或默认同一位 PM / Owner。
- 重新打开、推翻或复查条件。
- 被更新的主记录章节或逻辑 Artifact。

为了保持一份语义真源，必须同时遵守：

1. 决策的当前结论写回其所属正文，例如目标变化更新目标契约，问题变化更新问题诊断；不能只写在时间线里。
2. 同一文档中的“决策与变更记录”只保存必要的时间顺序、变化原因、影响和正文引用，不复制出第二套完整结论。
3. 人类表达已经清楚时，主 Agent 自动记录；仍存在多种合理解释且会影响行动时，先向 PM 澄清，不能擅自标记“已确认”。
4. Agent 提出的建议、PM 的探索性发言和未达成一致的讨论不能伪装成已确认决策；可以标记为“暂定”或“待决定”。
5. 决策发生变化时，不删除历史；将旧决策标记为“已被取代”，记录新决策及影响，并更新当前正文。
6. 已冻结的 Problem Candidate、Decision Candidate 或 PRD Candidate 保持不可变；后续 Agent 正式决策或人类决策引发实质修改时，更新当前主记录并形成新的 Candidate 版本。
7. 不复制原始聊天记录，不记录隐藏推理过程，只保留支持理解、审查、追溯和改判所需的事实、结论、理由、分歧和影响。

主 Agent 负责识别、总结、写入和维护这些决策。Reviewer 可以挑战决策依据和一致性，但不替 Agent 或 PM / Owner 作正式路线决定；Controller 只负责精确版本、Candidate、Review、授权范围、Agent 自动决策或 Owner Choice 的绑定，不判断产品结论是否正确。

### 12.4 必须独立保存的例外

以下内容因为物理形态、独立权限、不可变审查或正式交付边界，可以单独保存：

1. **原始证据和大型附件**：数据导出、访谈全文、截图、录屏、HTML、PNG、原型和外部研究材料。主记录只保留分析结论、证据强度和精确引用。
2. **不可变 Candidate 快照**：进入 Problem Review、Decision Review 或 PRD Review 时，系统才冻结主记录的精确版本或精确相关视图。工作中的主记录保持可持续修改，不为每次编辑、内部 Artifact 更新、补充证据或推演自动建立快照。正式 Candidate 具体通过最小版本文件、哈希、Git 快照还是内容寻址副本实现，留给后续系统架构确定；用户不需要手工维护多份候选文件。
3. **独立 Reviewer 记录**：Reviewer 必须只读冻结 Candidate 并独立保存 Findings。已接受的修改和 Finding 处置结果回写到下一版主记录；Reviewer 记录是审查证据，不是第二套当前产品结论。
4. **正式交付物**：实验型 PRD、总 PRD、子 PRD、必要的 Product Evals 和 Local Handoff 具有独立读者、版本、审查与交付边界，必须独立保存并精确关联主记录。

除以上情况外，只有拆分能实质提高理解、独立审查、权限隔离、交付、版本管理或大型附件处理质量时，才允许增加物理文件。不得为了体现流程完整而按 Artifact 机械建文件。

### 12.5 五阶段工作产物（Artifact）索引

五个阶段的必须工作产物、条件式工作产物、合并规则和最低内容已经分别在第 7—11 章确认。下表只作为快速索引；发生冲突时，以各阶段的正式定义和第 12 章的总原则为准。

| 阶段 | 已确认的工作产物范围（Artifact） |
|---|---|
| 理解（UNDERSTAND） | 背景与证据图（Context / Evidence Map）、目标契约（Goal Contract）、用户分群（User Segmentation）、用户需求矩阵（User Needs Matrix）、当前用户旅程、现状与差距图（Current State & Gap Map）、未知项登记表（Unknowns Register） |
| 诊断与价值判断（DIAGNOSE & VALUE） | 问题诊断（Problem Diagnosis）、竞争假设 H1/H2/H3、因果图（Causal Map）、第一性原理链（First-Principles Chain）、价值模型（Value Model）、成功与保护性约束契约（Success & Guardrail Contract） |
| 探索解决方案与决策（DISCOVER SOLUTIONS & DECIDE） | 方案情报（Solution Intelligence）、跨领域机制迁移记录、替代方案比较（Alternative Comparison）、取舍分析（Trade-off）、假设图（Assumption Map）、决策候选版本（Decision Candidate）、审查发现（Review Findings）、正式路线决定及来源（Agent 自动决策 / Owner Decision） |
| 规划产品系统（PLAN THE PRODUCT SYSTEM） | 范围与需求矩阵（Scope / Requirements Matrix）、目标用户旅程、核心产品流程（Product Flow）、信息与体验结构、服务蓝图（Service Blueprint）、逻辑产品系统图、前后台责任、模块图（Module Map）、全局规则/状态/权限/依赖、模块详细规划（Module Detail）、一致性与覆盖检查（Coherence & Coverage Check） |
| 产品需求文档与交接（PRD & HANDOFF） | 完整产品需求文档，或总产品需求文档 + 子产品需求文档；文档关系图（PRD Relation Map）、必要图片与附件、审查结果（Review Result）、可交接就绪记录（Ready Record）、本地交接（Local Handoff）、规划复盘与方法增量（Planning Retrospective & Method Delta） |

以下是跨阶段的快速适用性提示，精确触发条件以各阶段定义为准：

- 存在有意义的用户分群或需求差异时，通常需要用户需求矩阵（User Needs Matrix）。
- 存在多角色、多状态、分支、异常或系统交接时，通常需要核心流程图。
- 存在多个前后台产品责任或外部系统时，通常需要逻辑产品系统图。
- 存在人工、运营、跨渠道或多组织协同时，通常需要服务蓝图。

工作产物是否独立成文件继续遵守 12.4：默认写入同一份产品规划主记录；只有独立权限、不可变审查、正式交付、大型附件或显著降低理解成本时才拆分物理文件。

## 13. 上线与运营准备度（Launch & Operations Readiness）的边界

上线与运营准备度是条件式产品需求文档检查，不是独立业务节点，也不是每次必须生成的商业发布方案。

可能触发的场景：

- 重要外部发布。
- 需要市场、销售或合作方配合。
- 存在迁移、用户教育或培训。
- 客服影响较大。
- 依赖人工运营。
- 采用效果依赖推广和运营动作。
- 存在品牌、声誉、法律或合规风险。
- 多市场、多语言或复杂灰度发布。

不适用时，不在 PRD 正文保留空章节或“不适用”占位；适用性判断和理由保留在必填 Checklist 或产品规划主记录中。

适用时，BPG 只定义产品交付所需要的协调、约束、准备和验收，不负责输出完整市场推广或商业化执行方案。

## 14. 知识边界与规划复盘

### 14.1 不在 BPG 内设计知识库

通用知识库由用户单独建设。BPG 可以读取它提供的材料或 Signal，但不负责：

- 知识库存储结构。
- 跨项目知识模型。
- 自动采集和监听。
- 知识生命周期。
- 外部连接器和写回。
- 反馈自动转 Signal 的完整机制。

当前 BPG 运行结束后可以产出新的发现、未验证假设和方法改进建议，供未来外部知识系统使用，但 BPG 2.0 当前不进行外部写入。

### 14.2 自动规划复盘与学习（Planning Retrospective & Learning）

每次产品规划完成后，主 Agent 必须进行规划复盘。这是内部方法，不是业务图式流程（Graph）节点。

复盘至少关注：

- 哪些必要背景缺失。
- 哪些问题问错、重复或价值低。
- 哪些研究没有产生有效信息。
- 哪些框架真正帮助了判断，哪些造成误导。
- PM 的哪些修正改变了认知。
- 独立审查 Agent 反复发现了哪些问题。
- 哪些假设被推翻。
- PRD 拆分、关系和依赖哪里处理得不好。
- 文档哪里难以理解或难以执行。

复盘输出为：

- 运行复盘（Run Retrospective）。
- 方法增量（Method Delta）：对方法路由、项目方法手册（Playbook）或模板的改进建议。

自动进化分为三层：

1. 当前 Run 内反思和修正。
2. 形成项目方法、方法手册（Playbook）、方法路由器（Method Router）或模板的改进建议。
3. 对核心框架只形成变更提案，不能静默自动修改核心方法。

跨 Run 的持久存储和知识管理属于外部知识系统，不在本次 BPG 范围内。

上线后不保证一定获得反馈。没有反馈只能表示“没有反馈”，不能推断产品成功。

## 15. 产品规划阶段需要的专业能力

BPG 的能力库只覆盖形成高质量 PRD 所必需的产品规划能力。

### 15.1 范围内

- 背景、行业和领域理解。
- 用户研究材料解释，以及必要的研究设计。
- 用户分群、场景、需求、优先级和旅程分析。
- 目标、问题、因果、第一性原理、价值和决策质量。
- 竞品、行业最佳实践、相邻领域和跨学科方案研究。
- 用户体验、流程、信息架构、交互、内容、状态、异常与恢复。
- 服务蓝图（Service Blueprint）和可访问性等产品体验检查。
- 逻辑产品系统、能力、对象、数据流、状态、规则、前后台责任和依赖。
- 产品级非功能要求。
- 范围、规则、模块、功能、信息和验收标准。
- 需求追溯、PRD 拆分、总稿与子稿关系。
- 指标、数据定义、埋点需求、实验、停止与回滚条件。
- 隐私、安全、合规、兼容、迁移、灰度、回滚等产品风险适用性判断。
- 条件式运营、客服和市场协同要求。
- PRD 的叙事、图表、可读性和版本关系。

### 15.2 范围外

- 人员与团队领导力。
- 组织政治和向上管理。
- 通用谈判、沟通和会议能力。
- Portfolio 管理。
- 完整商业化和 GTM 执行。
- 市场推广计划。
- 通用项目管理。
- 工程规格说明（Engineering SPEC）和代码架构。
- 上线后的增长运营体系。
- 完整产品生命周期管理。

这些能力可能影响真实产品工作，但不应为了“完整”而被塞进以 PRD 为目标的产品规划方法。

## 16. 五阶段定义的统一合同结构

第 7—11 章已经使用以下结构完成当前五阶段基线冻结。后续若修改任何阶段，仍必须按同一结构整体校验，避免只改变流程名称或局部字段：

### 16.1 阶段目的

- 这个阶段必须解决什么问题。
- 它不负责解决什么问题。

### 16.2 必须执行的内部动作

- 主 Agent 必须完成哪些认知和分析动作。
- 哪些动作可以调用专业子 Agent。
- 何时必须询问 PM。
- 何时调用独立审查 Agent。

### 16.3 必须产出的工作产物（Artifact）

- 工作产物名称和目的。
- 最低内容要求。
- 与 PRD 的包含或引用关系。
- 作者、独立审查 Agent 和版本要求。

### 16.4 条件式工作产物（Artifact）

- 明确触发条件。
- 不触发时如何记录“不适用”。
- 是否允许与其他工作产物合并。

### 16.5 退出标准

- 哪些内容已经足够稳定。
- 哪些高影响未知已经被处置。
- 哪些追溯关系必须成立。
- 什么条件下可以进入下一阶段。

### 16.6 退回与重做条件

- 哪类新证据、矛盾、产品责任人修正或审查发现（Reviewer Finding）会使阶段失效。
- 应退回本阶段还是更早阶段。

### 16.7 角色与权限

- 谁执行。
- 谁独立审查。
- 谁提供信息。
- 谁承担决策和风险。
- 哪些状态只能由状态控制器提交。

### 16.8 Agent 与程序化脚手架分工

- 哪些动作由 Agent 完成。
- 是否真的需要新增程序化脚手架。
- 程序化脚手架具有哪项不可替代的独特优势。
- 如果不能证明独特优势，如何由 Agent 或现有工具完成。
- 新脚手架的最小边界、成本和退出条件是什么。

当前五个阶段已经全部按本合同结构完成基线冻结。进入开发后若发现逻辑缺口，应回到对应章节修订完整合同并检查上下游影响，不能只在实现层增加补丁。

## 17. 路线图（Roadmap）

本章节记录已经确认迭代位置、但尚未全部完成详细设计和实现的后续事项。路线图条目代表未来需要处理，不代表功能已经实现、测试或发布；每项进入开发前仍需形成与其范围相称的详细设计和验收合同。

### 17.1 `eli-me` 无情产品经理质询命令

- 状态：已安排进入小迭代 2.5，待详细设计、待实现。
- 形式：提供一个可以单独调用的 `eli-me` 命令。
- 目标：开启最高严格度、毫不留情的产品经理深度质询（Grilling）模式。
- 核心效果：不接受模糊目标、未经验证的假设、表面需求、方案先行、证据不足或回避取舍；持续挑战背景、目标用户、真实需求、问题定义、价值、方案选择、关键风险和改判条件，直到判断足够稳固，或产品责任人明确停止。
- 当前边界：本阶段只记录产品意图；具体触发方式、质询流程、停止条件、输出工作产物和运行实现留待后续单独设计。

### 17.2 后续详细设计与实现事项

以下内容的产品边界和迭代位置已经确认；其余工作属于对应迭代的详细设计、实现与验证，不阻塞迭代一内部 Alpha，除非条目中明确列入迭代一：

1. **Evals Generator 轻量化重构**：产品与打包边界已经确认采用“BPG 内置、架构可插拔”的原子能力；BPG Core 管理适用性、Candidate、版本、Review 和 Ready，能力包负责 Agent 生成，Test Graph 负责真实执行。生成器本体重构已安排进入小迭代 2.2；迭代一只保留适用性、条件式挂载点、Release Set / Ready 边界和缺失能力时的真实降级。
2. **产品形态场景知识包**：产品形态画像、条件式场景与韧性推演、Artifact 和 Reviewer 分级已经确认；后续仍需详细设计桌面端、iOS、Android、Web、Agent、本地、云端、API / SDK 和内部运维等场景知识包，建立可扩展的方法卡、适用信号和示例，并继续积累不同领域的真实边缘场景。
3. **更好的 PRD 模板**：PRD 内容契约、可读性方法、正式章节、图形格式和 Review 规则已经确认；新默认模板与自包含 HTML 阅读视图属于迭代一内部 Alpha 的实现与验证范围，不直接沿用现有模板。
4. **语言与地区配置及适配矩阵实现**：轻量适用性判断、语言 / Locale / 市场三层模型、PRD 与 Engineering SPEC 边界、条件式 Artifact 和专业人员升级规则已经确认；后续仍需设计可配置的 Locale & Market Profile、适配矩阵模板、Checklist、项目配置方式和产品形态知识包之间的组合规则。
5. **项目级数据采集配置与模板实现**：曝光、交互、调用和必要结果数据的产品边界、条件式数据采集需求表及 PRD / Engineering SPEC 分工已经确认；后续仍需设计可配置的 Data Collection Profile，支持项目必填、可选、禁采、敏感确认、平台差异和组织命名规范，并决定它与项目 PRD Template Profile 的组合方式。
6. **语言与文化类专业 Reviewer 实现**：语言精确性、产品文案、地区文化和条件式合规 Review 的职责与调用原则已经确认；后续仍需设计各 Reviewer 的输入合同、方法卡、Finding 类型、聚合规则、可用语言或地区能力声明，以及缺少合格专业人员时的 `NOT_RUN` 处理。
7. **多格式 Renderer 与导出实现**：Markdown 与 assets 编辑真源、默认自包含 HTML 阅读视图进入迭代一；DOCX、PDF、资源内嵌、版本绑定及跨格式渲染保真进入小迭代 2.5。

### 17.3 BPG 2.0 开发基线与旧版本边界

BPG 2.0 采用全新 Run 边界，历史版本的 Run 全部不迁移：

- 不导入、转换、恢复或续跑任何旧 Run。
- 不为旧状态、旧节点、旧命令、旧 Schema 或旧 Artifact 增加兼容别名、迁移器和双写逻辑。
- 历史 Run、文档、审查记录和产物保持原样、只读可查；它们可以作为研究与取舍证据，但不能成为 BPG 2.0 的运行状态。
- BPG 2.0 只创建符合新 Graph、角色、Artifact 和 Candidate 合同的新 Run。

正式开发前，当前工作区的已有修改和未跟踪产物必须先完整保全。优先方案是：在检查秘密信息、异常大文件、生成缓存、软链接和远程目标后，将需要保留的当前状态提交到开发仓的专用历史快照分支，再从独立、干净的 BPG 2.0 分支或工作区开始开发。不得为了获得干净工作区而删除、覆盖或重置现有用户内容。

### 17.4 开发迭代结构

BPG 2.0 采用一个内部 Alpha 和五个后续小迭代。每个迭代都必须产生可以独立理解和验收的产品增量，不能按前端、后台、Schema 或状态机等技术层机械拆分。

#### 迭代一：单 PRD 完整主链路内部 Alpha

目标是让一个最终可以收敛为单份高内聚 PRD 的真实需求，完整经历 Signal 与 Route、产品认知与决策循环、六类决策结果、整体—局部—整体规划、单 PRD 或实验型 PRD、独立 Reviewer Panel、最多两轮修订、整体回归、Ready 和本地 Handoff。

迭代一必须交付：

- 一份持续更新的《产品规划主记录》。
- Markdown 与 assets 编辑真源。
- 新的通用 PRD 模板和自包含 HTML 默认阅读视图。
- 不可变 Candidate、独立 Review Findings、`PASS / REVISE / NEEDS_OWNER` 和整体回归。
- 最小 Controller 所需的当前 Run、精确绑定、合法状态提交、暂停恢复、Ready 与本地 Handoff。
- Product Evals 的轻量适用性判断、条件式附件挂载点和真实降级；不移植旧 Evals Generator 的重型流水线。

迭代一不支持多 PRD 父子 Run，不迁移旧 Run，不实现 DOCX / PDF、外部 Connector、Test Graph、知识库、完整产品形态 Profile、专业 Reviewer 能力包或独立 `eli-me` 命令。

迭代一采用以下程序化实现红线，作为防止过度工程化的开发约束：

**允许的最小确定性能力：**

- 当前 Run、当前阶段、安全暂停点和恢复位置。
- Problem Candidate、Decision Candidate、PRD Release Set Candidate 三类正式审查对象的冻结、版本与精确引用；实验型 PRD 复用 PRD Candidate 合同，不建立第四套系统。
- 作者、Reviewer、Findings、Verdict、最多两轮 Candidate 修订和陈旧失效的绑定。
- Agent 自动决策或 Owner Choice 的精确授权来源，以及六类路线的合法状态提交。
- 第 11.6 节 Ready 合同、最小 Release Set 文件清单和 Local Handoff 的确定性提交。
- 只保存恢复、追溯、不可变审查和本地交接确实需要的最小 Machine Manifest；不得复制产品语义正文。

**迭代一明确禁止：**

- 为每个阶段、内部动作或逻辑 Artifact 机械建立独立文件、Schema、Gate 或状态机。
- 用程序判断应调用的分析框架、Artifact、产品形态、专业 Reviewer、Finding 严重度、返回阶段或 Product Evals 适用性。
- 把阶段退出标准、PRD 内容契约或 Checklist 变成依靠字段完整度宣称质量通过的语义 Gate。
- 为 Review-of-Review 建立第二套审查状态机、独立轮次计数器或评分流水线；它只作为同一 Review Artifact 内的有界语义活动。
- 把 PRD 内容契约、自适应基础模板、条件式模块和 Writing / Renderer Profile 分别实现为独立运行时、注册中心或 Provider 系统。Alpha 只需要一份内容合同、一份通用模板和一个机械 HTML Renderer。
- 实现多 PRD 父子 Run、完整产品形态规则引擎、专业 Reviewer 调度引擎或轻量化 Evals Generator；这些分别属于后续 2.1—2.4。
- 对工作中《产品规划主记录》的每次编辑、证据更新或内部推演进行冻结、哈希和正式版本提交。

新增任何不在允许清单中的程序层，仍必须逐项回答 0.2 节规定的五个问题；不能仅以“未来可能需要”作为 Alpha 的实现理由。

迭代一是内部 Alpha，不对外声称 BPG 2.0 正式完成。验收必须同时覆盖主流程、认知回流、Owner 改判、Review 修订后的整体一致性、六类决策结果、实验型 PRD、暂停恢复和真实状态表达；产品效果通过独立盲审比较 PRD 质量、产品经理重大纠偏、阅读体验、时间和 token 成本，质量优先。

#### 小迭代 2.1：多 PRD 与复杂产品系统

在迭代一不退化的基础上，加入总 PRD / 总览文档、多个 PRD sub-run、横向模块与纵向迭代拆分、共享背景和目标、兄弟 PRD 关系、共享契约、依赖以及完整 PRD Release Set 的全局 Review。

最低验收结果是：复杂产品可以拆分而不丢失完整叙事；任一子 PRD 的实质修改都会触发受影响关系和整体回归；各子稿分别成立不能替代整套系统成立。

#### 小迭代 2.2：轻量化 Evals Generator

按“BPG 内置、架构可插拔、Agent-first、最小脚手架”重构现有 Evals Generator。删除没有不可替代价值的重复合同、状态和程序层，保留适用性、精确 Candidate 绑定、Eval Pack、独立规格 Review、新鲜度、Ready 边界和 `NOT_RUN` 真实性。

最低验收结果是：`REQUIRED` Product Evals 能生成最小完备、可追溯、可独立审查的 Eval Pack；缺少 Ground Truth 或专业权威时准确阻塞并指出恢复方式；BPG 永远不冒充 Test Graph 给出真实执行结果。

#### 小迭代 2.3：产品形态知识包

建立桌面端、iOS、Android、Web、Agent、本地、云端、API / SDK 和内部运维等可扩展方法卡、适用信号和代表性场景。Agent 根据实际产品形态组合调用，不机械执行完整 Checklist。

最低验收结果是：同一需求在不同产品形态下能识别真正不同的路径、平台约束、韧性和边缘场景；不适用内容不会污染 PRD，也不会因缺少专属知识包而伪造确定性结论。

#### 小迭代 2.4：条件式配置与专业 Reviewer

实现语言 / Locale / 市场、数据采集、安全域和其他项目级条件配置，并建立语言精确性、产品文案、地区文化、安全、隐私、合规、无障碍及其他按需专业 Reviewer 的能力合同和调用规则。

最低验收结果是：条件式能力只在适用时出现，项目可以配置必填、可选、禁用、敏感确认和平台差异；缺少合格专业 Reviewer 时显示真实的 `NOT_RUN / NOT_AVAILABLE`，不能用通用 Agent 冒充专业结论。

#### 小迭代 2.5：增强交付与 `eli-me`

实现条件式 DOCX / PDF 输出、资源内嵌、精确版本绑定和跨格式保真检查，并提供独立 `eli-me` 命令进入最严格、无情的产品经理 Grilling 模式。

最低验收结果是：所有派生格式与同一 Markdown / assets 真源一致且不形成第二事实来源；复杂图表、分页和中文排版可用；`eli-me` 能显著提高质询强度，但不绕过证据、Owner 权限、停止条件或正常 BPG Graph。

完成小迭代 2.5 且全部前序回归仍成立后，才进入 BPG 2.0 正式 Release Candidate 判断。任何小迭代如果实际范围过大，可以继续拆成内部任务或垂直切片，但不能把未完成能力包装成已交付。
