# PRD 写作规范 v0.2：先看懂全局，再进入细节

## 1. 这份规范管什么

PRD 模板决定“需要写哪些内容、放在哪些栏目”；本规范决定“怎样表达，才能让第一次接触项目的人准确理解、复述并作出判断”。两者独立版本化，切换模板不会自动切换写作 Profile。

默认读者是一位聪明、有产品判断能力，但没有参加前置讨论的中文产品经理。降低理解门槛不等于降低真实性：证据、未知、权限、风险和停止条件不能因为“好读”而消失。

本规范不是新的 Graph Node、审批 Gate、PRD 模板或工程 SPEC，也不依赖外部 `plain-talk` Skill。

## 2. 十三条写作规则

### 2.1 从具体事情开始

先写谁在什么场景想完成什么、卡在哪里、造成什么结果，再给问题或能力命名。不要从行业背景、系统架构或内部缩写开场。

### 2.2 先给结论，再解释原因

文档首屏和每个主要章节先回答“当前判断是什么”，再展开依据、成立条件、反方意见和细节。可以用“阅读摘要”“我们建议”“当前判断”等自然表达，不要求机械出现某一个关键词。

### 2.3 先建立全局框架，再逐层展开

读者进入模块、字段和异常分支前，必须先能回答：

1. 这次解决什么问题；
2. 本期改变什么结果；
3. 哪些模块和阶段共同完成它；
4. 明确不做什么；
5. 下一步由谁做什么。

复杂 PRD 先提供一张小型全景图或简短流程，再按“目标与范围 → 全局流程 → 模块规则 → 验收与风险”展开。不要一开头连续列出内部合同、Schema 或对象表，让读者先在局部细节中迷路。

### 2.4 一个段落只讲一个重点

步骤使用编号，并列信息使用项目符号；只有比较、映射或追溯时才使用表格。不要把多段解释塞进一个表格单元格，也不设简单总字数门槛。

### 2.5 一次只引入一个新概念

推理有三步就写出三步。相邻概念容易混淆时，先分别说明它们解决什么问题，再解释如何连接。

### 2.6 术语第一次出现时先说人话

先说明术语对用户、业务或系统行为意味着什么，再在括号中保留正式英文或 Machine Name。不要用另一个未解释术语解释术语。

### 2.7 控制中英文夹杂

普通叙述优先使用中文。正式字段、枚举、Schema、Machine Name 和翻译后失真的行业名称可以保留英文，但首次出现仍要说明中文含义。

### 2.8 用例子承担解释工作

抽象规则难懂时，用一个贴近真实使用的例子说明它怎样发生，并明确例子与真实机制的映射。例子不是证据，也不能替代精确合同。

### 2.9 复杂关系才配真正有用的图

流程、分支、时序、状态、数据去向、模块关系或责任边界仅靠文字难以快速理解时，必须配图。简单线性功能不因没有图失败。

每张图要说明它回答什么、覆盖什么、不覆盖什么，并提供不看图也能理解的文字摘要。禁止装饰图和逐节点重复正文。

### 2.10 区分事实、判断、假设和未知

- 来源明确、适用边界清楚的内容才写成事实。
- 产品判断要能看出依据和有权判断者。
- 暂时采用但仍需验证的内容标为假设。
- 当前没有答案的内容标为未知，并说明是否阻塞下一步。

多个方法得到相同观点不能自动提高证据置信度，Owner 授权也不能被写成用户价值证据。

### 2.11 简单不能失真

不能为“好读”删除控制条件、权限、异常恢复、证据来源、风险、改判条件、稳定 ID 或可验证验收。

### 2.12 正文省略不适用项，Checklist 保留处置

条件式正文确实不适用且省略后不影响判断时，删除空标题、空表和占位文字；覆盖 Checklist 继续记录 `不适用｜理由：具体原因`。未知、未设计、未执行和必填语义不能伪装成“不适用”。

### 2.13 PRD 定义产品要求，Engineering SPEC 决定内部解法

PRD 定义产品问题、用户结果、范围、产品规则和可观察验收。它还应保留会改变对外行为、安全底线、跨模块兼容或责任边界的精确产品合同。

以下内容默认由研发在 Engineering SPEC 中决定：

- 内部类、函数、存储对象和字段拆分；
- 数据库、缓存、锁、队列或 CAS 的具体选型；
- 内部线性化点、事务步骤和文件布局；
- 不影响外部行为的模块拆分和实现算法。

如果某项工程选择会改变用户可见行为、不可逆风险或跨团队承诺，PRD 写清必须满足的结果和底线，但不替研发预选唯一实现。

## 3. 信息密度怎么判断

不设“超过多少字就失败”的门槛。长文档可以成立，但必须满足：

- 首屏可复述目标、范围、状态和下一步；
- 标题能形成从全局到局部的展开路径；
- 同一结论有一个正式来源，其余位置引用而不重复；
- 正文不连续堆叠未解释术语；
- 读者能快速定位模块、规则、验收、风险和未知。

短文档也可能很难读。五千字的术语墙、无主次表格和重复结论仍应产生 Readability Finding。

## 4. 表达形式怎么选

| 内容关系 | 优先形式 | 不建议 |
|---|---|---|
| 一个结论及原因 | 短段落 | 多层括号和连续分号 |
| 有先后顺序的动作 | 编号步骤或流程图 | 一整段串联所有步骤 |
| 多项平行信息 | 项目符号 | 每项写成长表格单元格 |
| 固定维度比较 | 表格 | 多段散文反复比较 |
| 状态与转换条件 | 状态图 + 摘要 | 只列状态名 |
| 多参与者调用顺序 | 时序图 + 异常 | 只讲模块不讲先后 |
| 数据来源与去向 | 数据流图 + 边界 | 只列字段不讲流向 |

## 5. PRD 交稿前自检

零背景读者应能独立回答：

1. 谁遇到什么具体问题，为什么现有方式不够？
2. 本期改变什么结果，明确不做什么？
3. 整体方案由哪些阶段或模块组成？
4. 用户从开始到完成经历什么，失败后怎样继续？
5. 哪些是产品必须决定的规则，哪些留给 Engineering SPEC？
6. 第一次出现的术语是否已经用普通中文解释？
7. 复杂关系是否有真正有用的图，简单关系是否避免装饰图？
8. 哪些是事实、判断、假设和未知？
9. 验收、权限、风险和恢复是否因简化而丢失？
10. PRD Ready、代码实现、测试/Eval、交付和上线是否分别准确表达？

## 6. Validator 与 Reviewer 的边界

- **确定性 Validator**：检查 exact Policy/Profile/Template binding、必要阅读入口、状态/证据/未知/权限/版本边界和 Changelog 等可靠机械事实。
- **Readability Reviewer**：判断是否先总后分、术语堆叠、段落主次、图是否有用、信息密度和 PRD/SPEC 越界。

Validator 不用单一中文词语冒充语义判断。Reviewer 继续 `ADVISORY_ONLY`，复用现有 Review 与 disposition；它的 Finding 必须被看见和明确处置，但不新增 Graph Node 或审批 Gate。

## 7. 证据边界

`v0.2.0` 继承 v0.1 的完整真实性边界，并新增“先建立全局框架”“信息密度”和“PRD / Engineering SPEC 边界”。冻结表示版本身份和运行时绑定确定，不表示真实中文产品经理阅读效果已经验证。

当前 Product Evals 与观察式阅读测试仍为 `NOT_RUN`。不得因为文档通过机械校验就声称产品可读性已得到用户证明。
