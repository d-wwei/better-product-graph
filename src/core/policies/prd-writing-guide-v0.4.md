# PRD 写作规范 v0.4 Candidate：保留完整产品合同，降低读者负担

## 1. 目标与边界

本规范不是让 PRD 尽可能短，而是让一位聪明但没有参加前置讨论的产品经理，以合理阅读成本形成正确的产品理解，并能继续判断和交接。

作者必须保留会改变目标、范围、规则、风险、权限、恢复、验收或下一步的信息。需要减少的是重复、平铺、表达冲突和不属于主路径的实现细节，不是产品语义。

本规范是 `CANDIDATE_NON_DEFAULT`。八条写作规则和新的 Reviewer 合同目前均为候选设计；在安装版 Agent Eval 和真实 PRD Review 完成前，不得写成已经验证或已经成为默认规范。

## 2. 六个读者结果

PRD 是否好读，以读者读完后能否完成以下事情为准：

- **看懂（`UNDERSTAND`）**：说清谁在什么场景遇到什么问题，产品要改变什么结果。
- **看见（`SEE`）**：直接看出主要流程、关系、分支、责任或取舍；确实不需要图时，也能说明原因。
- **建模（`MODEL`）**：说出三到五个关键组成部分或阶段，以及各自作用。
- **复述（`RETELL`）**：用自己的话解释主路径和重要的失败、恢复路径。
- **判断（`DECIDE`）**：找到当前选择、成立条件、后果、风险和改判条件。
- **定位（`LOCATE`）**：不用重读全文，就能找到规则、验收、风险、未知和下一步的正式位置。

真实性横切六个结果。读者能够流畅复述，却把 `NOT_RUN` 理解成“已通过”，或者把产品决定理解成“已实现”，仍然失败。

## 3. 作者必须遵守的八条规则

### 3.1 一个语义一个正式位置

同一规则只在一个正式位置完整定义。摘要、图、流程和其他章节只给结论并引用正式位置，不再改写第二份近似合同。

### 3.2 主路径只保留核心产品结果

目标、范围、流程、产品规则、边界、核心验收和下一步留在正文。Fixture、oracle、对抗组合和执行证据进入 Eval Pack、seed 或附录。主路径不能被验证材料淹没。

### 3.3 分组压缩，不靠删除语义

大量同层条目先按读者能命名的结果分组，再映射到下层精确合同。不能为了缩短篇幅删除权限、例外、恢复或验收语义。

### 3.4 一种关系只选一种主要表达

图、表、列表只选一种作为同一关系的主要表达。其他形式只补充主要表达没有覆盖的信息，不能把相同模型重复三遍。

### 3.5 表格只用于比较和映射

表格适合稳定字段之间的比较与映射。叙述、解释、风险推理和长句应回到正文；行数多不是失败，密集到无法理解才是问题。

### 3.6 保留功能，不保留重复

删除内容前先判断它承担的是解释、定位、决策、追溯还是交稿确认。只有这些功能已有清晰承接，才能删除重复表达；否则必须保留或恢复其功能。

### 3.7 精确状态必须说真话

`[x]` 必须有完成语义图例和证据边界。产品决定不能看起来像已实现或已测试；拟定但尚未落地的合同标记为 `PROPOSED_NOT_IMPLEMENTED`；`NOT_RUN` 不能渲染成 PASS/FAIL；本地 Handoff 不能写成远程已发送、已接收或已批准。

### 3.8 先说人话，再给机器名

第一次出现精确字段、枚举或 Machine Name 时，先说明它对用户或产品意味着什么。Schema、存储、算法和并发通常属于 Engineering SPEC；只有改变外部行为或责任边界的精确产品合同留在 PRD。

## 4. Reviewer 两遍阅读

Writing Reviewer 必须独立于作者，并针对同一个 exact Candidate 执行两遍阅读：

1. **读者遍**：不先看 expected，也不先拼检查清单；先独立写出 readback，判断六个读者结果是否成立。
2. **诊断遍**：只对失败结果定位理解断点，选择问题类型和最小修订手段，形成现有 Review 流程中的正常 Finding。

通过项不需要生成逐条 PASS 墙。出现 Finding 时，必须绑定 Candidate 的精确位置、受影响的读者结果、严重级别和最小有效修改。

Reviewer 保持 `ADVISORY_ONLY`。它提出建议，不拥有产品批准、Ready、Release 或组织审批权。Candidate 实质变化后，旧 Review 对新 hash 失效。

## 5. 九类理解断点

- `SEMANTIC_REPETITION`：同一语义在多处重复定义，读者无法判断权威位置。
- `FLAT_PEER_OVERLOAD`：大量同级条目没有分组，主次关系消失。
- `REPRESENTATION_COLLISION`：图、表、列表重复表达同一关系，甚至互相冲突。
- `DETAIL_IN_MAIN_PATH`：Fixture、执行证据或实现细节挤入正文主路径。
- `DENSE_TABLE`：本应叙述或推理的内容被塞进难以阅读的表格。
- `JARGON_INTRUSION`：机器术语先于产品含义出现，读者必须反推它是什么意思。
- `CHECKLIST_FUNCTION_LOSS`：删减 Checklist 时同时丢失解释、定位、决策、追溯或交稿确认功能。
- `COMPLETION_SEMANTICS_AMBIGUOUS`：勾选、状态或完成用语没有清楚的证据和边界。
- `ARTIFACT_MATURITY_OVERCLAIM`：把拟定、未执行或本地完成写成已实现、已验证或已对外交付。

不得按总字数、总行数、章节数、表格行数或 Checklist 项数自动判错。长但分层清楚的 PRD 可以通过；短但重复、跳跃或术语密集的 PRD仍应产生 Finding。

## 6. 十二种最小修订手段

- `REORDER`：调整阅读顺序，让结论、全局和细节按理解路径出现。
- `GROUP`：把平铺同级项归为可命名的结果组。
- `EXPLAIN`：补上读者缺失的产品含义或因果说明。
- `EXAMPLE`：用具体事件说明抽象规则，并映射回正式合同。
- `VISUALIZE`：用最小必要图表达非平凡关系。
- `LAYER`：把主路径、精确合同和执行证据分层呈现。
- `MERGE`：合并重复的正式定义。
- `REFERENCE`：保留唯一权威位置，其他位置只引用。
- `MOVE`：把内容移动到 Eval Pack、附录或 Engineering SPEC 等正确产物。
- `TRIM`：删除已经有功能承接的重复表达。
- `RESTORE_FUNCTION`：恢复删减时意外丢失的 Checklist 功能。
- `BOUNDARY`：补清状态、成熟度、权限或产品/研发责任边界。

每个 Finding 选择能解决主要断点的最小组合，不为了显得全面而罗列全部手段。

## 7. Checklist 功能保护

Checklist 不只是文字列表，还可能承担五种功能：

- 解释某项为什么需要考虑；
- 帮助读者定位正式规则；
- 记录做过什么产品决定；
- 保持从需求到验收的追溯；
- 在交稿前确认关键事项已经处置。

移除 Checklist 内容前，必须指出这些功能由哪里承接。没有承接就不能删除，应分组、引用或恢复功能。真正不适用的正文可以省略，但 Checklist 保留“不适用”和具体理由；未知、未设计、未执行和必填语义不能借“不适用”隐藏。

## 8. 图、表与长文档

非平凡顺序、分支恢复、状态迁移、三个以上相互作用的模块或责任边界，通常需要视觉表达。图是否有帮助由独立 Reviewer 观察实际渲染后判断；文件存在、hash 正确或机械安全校验不能代替语义判断。

大表格不是自动失败。字段稳定、需要逐项比较或映射，且读者能快速定位时，大表格可以通过。长附录也不是自动失败：只要正文主路径短而完整、附录有明确入口，并且没有在正文重复定义精确合同，长度本身不构成 Finding。

## 9. 产物责任与真实性

- PRD 定义产品问题、用户结果、范围、产品规则、外部行为和可观察验收。
- Eval Pack 定义怎样验证可观察结果，并如实记录 `NOT_RUN`、PASS 或 FAIL。
- Controller companion 提供运行时权威状态，避免 PRD 正文成为第二条可变状态真源。
- Review Policy 定义 Finding 和处置，不给 Reviewer 产品批准权。
- Engineering SPEC 决定不改变产品行为的内部 Schema、存储、类、算法和并发方案。

确定性程序只校验身份、引用、结构、资产安全和 Finding 对账；它不能冒充真实读者判断文章是否好懂。多个 Agent 给出相同意见也不等于真人阅读已经验证。

## 10. 当前证据状态

v0.3 的历史 Agent Product Eval 为 `3/5 FAIL`，真实 PRD Review 和观察式真人阅读均为 `NOT_RUN`；该证据保持不可变。

v0.4 当前只完成写作政策定义，Agent Product Eval、真实 PRD Review 和观察式真人阅读均为 `NOT_RUN`。在预注册的安装版评测全部通过前，v0.2 继续是默认 Profile。
