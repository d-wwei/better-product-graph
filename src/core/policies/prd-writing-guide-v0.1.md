# PRD 写作规范 v0.1：让零背景读者准确读懂

## 1. 这份规范管什么

PRD 模板决定“需要写哪些内容、放在哪些栏目”。

这份规范决定“这些内容应该怎样表达，才能让第一次接触项目的人读懂、复述并作出判断”。

两者独立版本化。同一模板可以搭配不同语言、受众或表达密度的写作规范；换模板不自动更换写作规范，更新写作规范也不要求修改模板结构。

本规范不是：

- 新 PRD 模板或章节目录。
- 新 Graph Node、Run、Gate 或正式产品 Artifact。
- 允许删掉条件、风险和精确合同的“简化模式”。
- 单独依赖 Agent 记忆的提示词。

## 2. 默认读者

默认读者是一位聪明、具有产品判断能力，但第一次看到这个项目的中文产品经理。

不要假设他已经理解项目历史、BPG、Agent、Graph、Host、内部模块、状态枚举、Schema 或工程实现方式。

“零背景”降低的是理解门槛，不是真实性标准。表达可以简单，事实、来源、不确定性和风险不能被简单化掉。

## 3. 十一条写作规则

### 3.1 从具体事情开始

先写谁在什么情况下想做什么、卡在哪里、造成什么结果，再给问题或能力命名。

不要从行业背景、系统架构、功能清单或内部缩写开场。读者应先看见问题怎样发生，再理解抽象判断。

### 3.2 先给结论，再解释原因

每个主要章节先用一句话回答该节最重要的问题，然后再展开依据、条件、例外和细节。

不要让读者读完整节以后，才在最后一句找到结论。

### 3.3 一个段落只讲一个重点

当一段话同时包含多个结论、步骤、条件或例外时，拆开表达：

- 步骤使用编号。
- 并列信息使用项目符号。
- 一条完整因果关系使用短段落。
- 只有比较、映射或逐项追溯时才使用表格。

不要把多段解释塞进一个表格单元格，也不设置机械字数限制。判断标准是读者能否一眼看出主次。

### 3.4 一次只引入一个新概念

如果推理有三步，就把三步写出来。不要在一句话里连续塞入多个新模块、状态、缩写和合同，让读者自己补中间过程。

相邻概念容易混淆时，先分别说明每个概念解决什么问题，再解释它们如何连接。

### 3.5 术语第一次出现时先说人话

先说明术语对用户、业务或系统行为意味着什么，再在括号中保留正式英文或机器名称。

示例：

> 系统为这次接入保存一份不可修改的资料清单（`Source Inventory`）。

不要用另一个没有解释的术语解释术语。

### 3.6 控制中英文夹杂

普通叙述优先使用中文。以下内容可以保留英文：

- 正式字段和枚举。
- Schema、Machine Name 和代码标识。
- 已形成稳定共识、翻译后反而失真的行业名称。

首次出现仍要给出简短中文解释。后文需要精确引用时再单独使用英文名称。

### 3.7 用例子承担解释工作

抽象规则难懂时，用一个贴近真实使用的例子说明它怎样发生，然后明确映射：例子中的人、动作和结果分别对应产品中的什么。

例子帮助理解，但不是证据，也不能代替精确合同。例子的边界与真实机制不一致时，要明确指出。

### 3.8 复杂关系必须提供真正有用的图

当流程、分支、时序、状态、数据去向、模块关系或责任边界仅靠文字难以快速理解时，必须配图。

每张图都要说明：

- 它回答什么问题。
- 覆盖哪些范围，不覆盖什么。
- 读者不看图时仍能获得的文字摘要。

不画装饰图。图不能代替文字，文字也不要逐节点复述图。

### 3.9 区分事实、判断、假设和未知

- 来源明确、适用边界清楚的内容才写成事实。
- 产品判断要能看出依据和有权判断者。
- 暂时采用但仍需验证的内容标为假设。
- 当前没有答案的内容明确标为未知，并说明它是否阻塞下一步。

流畅的文案不能把未知写成已确认，也不能把 Owner 授权写成客观事实。

### 3.10 简单不能失真

不能为了“好读”删除以下内容：

- 控制条件和例外。
- 权限和责任边界。
- 异常、恢复、降级和回滚。
- 证据来源与适用范围。
- 不确定性、风险和改判条件。
- 稳定 ID、验收条件和必要的精确合同。

专业细节可以在读者已经建立产品画面后出现，但不能凭空消失。

### 3.11 正文省略不适用项，Checklist 保留处置结果

正文服务连续阅读。条件式章节、小节或字段如果确实不适用，而且省略后不会影响范围、风险、决策或执行，应直接删除标题、空表和“不适用”占位说明。

Checklist 服务覆盖审计。对应检查项应继续保留，并写成：

> `不适用｜理由：具体原因`

这样既能证明该视角已经检查过，也不会让普通读者在正文中连续阅读没有实际内容的章节。

以下内容不能按本规则省略：

- Template / Output Contract 明确要求的必填产品语义。
- Document Experience Policy 的最低理解项。
- 缺失后会改变范围、风险、权限、决策或下一步的内容。
- 不是“不适用”，而是尚未确认、尚未设计或尚未执行的内容。

“不适用”与“还没做”不能混用。后者必须保留真实状态、Owner、影响或下一步。

与模板发生关系时，以 Output Contract 判断是否属于必填语义：如果只是模板里的条件式呈现提示，而且 Output Contract 允许省略，本 Profile 可以删除正文占位并把处置移到 Checklist；如果是 Output Contract 或 Policy 要求的必填语义，则必须保留。

## 4. 表达形式怎么选

| 内容关系 | 优先形式 | 不建议的写法 |
|---|---|---|
| 一个结论及其原因 | 短段落 | 多层括号和连续分号 |
| 有先后顺序的动作 | 编号步骤或流程图 | 一整段串联所有步骤 |
| 多项平行信息 | 项目符号 | 每项写成长段表格单元格 |
| 两个以上对象的固定维度比较 | 表格 | 用多段散文反复比较 |
| 状态和转换条件 | 状态图 + 文字摘要 | 只列状态名，不解释如何变化 |
| 参与者之间的调用顺序 | 时序图 + 关键异常 | 只讲模块，不讲谁先谁后 |
| 数据来源、处理和去向 | 数据流图 + 隐私边界 | 只列字段，不说明数据流向 |

## 5. PRD 专属检查

交稿前，假设读者没有参加任何前置讨论，检查他是否能独立回答：

1. 谁遇到了什么具体问题？
2. 为什么现有方式不够？
3. 本期准备改变什么结果，明确不做什么？
4. 用户从开始到完成会经历什么？失败后怎样继续？
5. 系统做了哪些事，哪些决定必须由人确认？
6. 第一次出现的专业词是否已经用普通中文解释？
7. 哪些关系需要图，图是否真的减少了理解成本？
8. 哪些是事实，哪些是产品判断、假设或未知？
9. 验收、风险、权限和恢复条件是否因为简化而丢失？
10. Ready、实现、测试、交付和上线状态是否被分别准确表达？

## 6. 与 Template、Skill 和 Validator 的关系

- **Template**：提供栏目与产品语义承载位置，不内嵌本规范全文。
- **Document Experience Profile**：为某类产物选择本规范的版本、受众、语言、密度和必要图示要求。
- **Skill / Host Agent**：读取 Controller 提供的确切 Policy、Profile 和 Template，再按本规范写作；不能只凭模型记忆。
- **Validator**：确定性检查规范版本绑定、最低理解项、状态边界和必要视图是否存在。
- **Readability Reviewer**：判断术语堆叠、结论埋藏、主次混乱、图是否有用等无法只靠 Schema 判断的问题。

只把规则写进 Skill 不够可靠；只把规则写进模板又会把结构与表达绑死。正确关系是：独立规范作为版本化真源，Skill 执行，Profile 选择，Validator 和 Reviewer 分别检查。

## 7. 当前证据边界

本规范来自 `plain-talk` 的 ELI5 原则、本地可读性审计和 BPG 已确认的 Document Experience 架构。`v0.1.0` 已作为 BPG 的默认中文 PRD 表达规范冻结；后续修改必须发布新版本，不能原地改写本版本。

冻结表示版本身份、运行时绑定和执行规则已经确定，不表示表达效果已经通过真实用户验证。当前仍没有真实中文产品经理的观察式阅读测试，因此不能宣称这套规则已经证明可用，也不能因为文档变好读而声称产品功能已经实现或测试通过。
