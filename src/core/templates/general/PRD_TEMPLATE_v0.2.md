# {{PRD 标题}}

> 本模板是 Better Product Graph 通用 PRD 模板 v0.2 工作草案，当前用于结构与内容 review，尚未成为运行时默认模板。
> 生成正式 PRD 时，Markdown 文件名仅去除最后一个 `.md` 扩展名后得到的文件名主体，必须与本文档 H1 标题逐字符完全一致；文件名主体继续遵循 `<PRD-ID>_<short-title>_v<version>_<YYYY-MM-DD>`。
> PRD ID、版本、状态、机器维护的 Owner、模板身份、上游 Exact refs 与 Review / Ready / Release 生命周期 refs 由系统写入 frontmatter、sidecar 或 manifest，不在正文中另建 metadata 区。
> 生成正式 PRD 时应删除本说明和所有 `{{...}}` 提示，不得保留空表或裸 `TBD`。
> 未决内容统一写成：`待确认｜Owner / 有效来源：...｜影响：...`。`待确认` 表示缺少有权事实或决定；已有明确假设但仍需证据检验时使用 `待验证`，两者不得混用。
> 条件式章节或小节不适用时，默认删除空表与占位内容，并保留一行：`不适用｜理由：...`。若局部规则明确要求“删除整个条件式小节”，则局部规则优先，不再保留空标题或不适用行；不得为了填满模板编造信息。

## 3. 方案总览与关键流程

> **第 3、4 节结构模式（生成时二选一，不保留另一套空骨架）**
>
> - **标准拆分模式**：当 PRD 包含多个有意义的模块、跨模块关系或共享规则、多个不同流程，或者方案总览与研发施工细节回答的是不同问题时，保留本节的全局概览 / 可视化 / 共享规则，并按第 4 节逐模块展开。
> - **紧凑合并模式**：仅当 PRD 是一个可独立交付、高内聚的模块或切片，只有一个主导场景 / 流程，并且拆开总览与模块详述主要会造成重复时使用。将本 H2 改为 `3. 方案与功能规则`，把第 4 节模块骨架并入本节，统一编号后删除独立的第 4 节。建议顺序为：`3.1 方案概述`、`3.2 模块职责、目标与场景`、`3.3 关键流程与交互视图（含适用的模块级可视化）`、`3.4 业务规则`、`3.5 交互、状态与权限`、`3.6 依赖关系（条件式）`、`3.7 分支与异常`、`3.8 验收标准`。紧凑模式可在 `3.3` 内合并呈现端到端行为与模块内部机制，但每张图仍须说明自己回答的问题，不能重复绘制同一信息。
>
> 不能仅因篇幅短或字数少而合并。只要存在有意义的模块边界、共享合同、跨模块规则，或多张视图需要单独的全局视角，就使用标准拆分模式。合并只能消除重复呈现，不能删除适用语义：方案说明、合适的全局与模块级可视化、模块职责与目标、参与者故事或等价场景、触发 / 前置条件、业务规则、交互 / 状态 / 权限、模块依赖、分支 / 异常 / 恢复和可观察验收标准都必须保留。下述可视化选择规则与模块级依赖规则在两种模式下同样有效。

### 3.3 关键流程与交互视图

非平凡行为必须至少提供一张适合所解释问题的可视化图，不限定为流程图。按读者需要理解的问题选择图型：

- **用例图**：说明参与者、能力与范围边界。
- **状态图**：说明生命周期、状态转换与转换条件。
- **其他项目支持的图**：当其他图型能更准确地说明行为时使用。
